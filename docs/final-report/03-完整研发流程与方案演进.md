# 03｜完整研发流程与方案演进

这条叙事按问题和证据组织，而不是把仓库目录里的 Stage ID 逐项抄成日志。关键问题始终是：当时遇到什么瓶颈、做了哪种检查、检查实际支持什么结论，又有哪些结论不能外推。

## 1. 先证明可以运行一条完整闭环

项目先固定比赛 Runner、依赖和本机环境，再做最小基线。环境记录包括 Runner 来源 SHA、Python 3.12.13、Windows 环境和锁定依赖；这些身份信息让之后的运行能够区分“环境不同”和“策略不同”。S01 的 no-op 基线取得 26.95 quantitative、18.86 competition partial、19 个月、E、L3，并在第 19 个月自然终止。

这次运行的重要作用不是提供一个可比较的策略成绩，而是建立最初的工具与游戏闭环：可启动新局、观察状态、提交行动、推进月份并得到终局。M2 起出现的公开风险提示以及之后的信任危机，为后续提出风险复核假设提供了同局时间线；这条时间线不能单独证明某一个动作造成终局，也不能证明某个风险清理选项一定有效。

在 S03-01 的复核中，时间线被进一步写成可核对的观察点：M2 有公开警告，M10、M12、M18 有与 landmine 风险相关的反馈，M19 出现 trust-crisis 提前终止。它支持的问题是“公开警告出现后，Agent 是否需要重新核对候选及其可见后果”，而不是“某个指定动作必然能把游戏救回来”。同一局内的先后关系可以提出假设，却无法排除状态变化、前序选择和其他事件同时影响结果。保留原有时间序列与限定语，正是避免把复盘叙事误读成隐藏规则。

公开 Dev 可以帮助工程师检查可观察流程，却不能代表保密 Test。环境与基线的精确记录见[运行历史](../project/RUN_HISTORY.md)和[环境记录](../project/ENVIRONMENT.md)。

这一步还提供了比较时不可省略的上下文：Runner 有固定来源 SHA，项目环境记录了 Python 3.12.13 与依赖身份，后续候选的运行才有共同的工程参照。若只保留“基线很低”这句话，就会丢失它实际上在哪个环境、走到哪个月份以及如何终止。相反，也不能把后来高分直接解释为相对基线的策略增益，因为两个运行之间可能同时改变了候选、上下文、运行路径和其他条件。基线是项目闭环和问题发现的起点，不是一项能够单独回答因果问题的对照实验。

## 2. 从“文件存在”到“运行中确实参与”

一份 SKILL.md 写得正确，只证明文件内容存在。要说 Skill 参与了游戏，还需要区分包格式、安装状态、运行时发现、内容加载、游戏调用和调用后行为。前几个环节通过，不会自动替后几个环节背书。

早期 Risk Review 尝试正好暴露了这个差别。S03-01 从一个真实基线中整理出公开风险提示与后续信任危机的时间顺序，并把“在当前公开风险和合法替代项同时出现时，要求一次有限的候选复核”写成可证伪假设。原始记录明确把该关系标为时间上的观察，而不是单动作因果。[S03-01 历史取证](https://github.com/MyKr-YSteinsK/CareerSim-BDCI26/blob/488017113fe3ab491dada55be478870f1447c0cf/experiments/S03-01-risk-forensics/RESULT.md)

S03-02 实现最小 risk-review Skill 后，frontmatter、安装、Runner 校验、运行时发现和 Skill 内容加载均通过；但唯一一次有界 smoke 使用了与 CareerSim Runner 不匹配的通用工具路径，没有创建游戏 session，也没有进入 observe 或 take_action 链。因此没有有效的风险触发窗口、风险标记或候选变更可审。结论是风险策略收益 RISK_BENEFIT=NOT_PROVEN，而不是“风险复核已被证明有效”或“风险复核已被证明无效”。[S03-02 历史结果](https://github.com/MyKr-YSteinsK/CareerSim-BDCI26/blob/488017113fe3ab491dada55be478870f1447c0cf/experiments/S03-02-risk-review/RESULT.md)

这一步留下了一个重要工程习惯：分别报告静态合同、安装、发现、加载、真实情境触发和行为结果。任何一层失败，都不能用另一层的 PASS 掩盖。

可把这段验证链理解为逐层缩小的事实范围：包检查回答“材料是否可解析”；安装与 Runner 检查回答“框架是否接受这个 Skill”；发现和加载回答“运行时是否能找到并读取”；真实情境调用才回答“模型是否在相关时点采用了它”；最后还要观察采用后的候选和环境结果。每个环节都有自己的失败类别，结论只延伸到通过的那一层。S03-02 的重要结果是暴露了 smoke 路径与任务接口不匹配，而不是成功验证 Risk 策略；把这个失败写清楚，后续才不会误以为早期 Risk 已经做过有效比赛局评估。

当时没有 CareerSim session，就没有能够呈现 Risk 触发条件的观察窗口；缺少 observe、候选和 take_action，意味着日志里也没有可供核验的审核输出与行为结果。于是 S03-02 的有效工程信息主要是“最小 Skill 可以通过一组静态及加载门禁”以及“所选 smoke 入口不适用于本项目真实游戏链”。因此这个尝试仍有诊断价值，但它不贡献风险策略的正面或负面收益样本。后续设计将合法 CareerSim 工具链作为运行证据的必要条件，也把这一点视作对早期流程的修正。

## 3. 把 Risk 做成有限检查，而不是自动保守策略

最小 Risk Review 的输入是同一局的新鲜公开状态、当前情境、合法选项和公开反馈；输出是 ALLOW、WARN、RECONSIDER 或 UNKNOWN，并附公开理由。RECONSIDER 不是自动拒绝，它要求当前候选存在重大公开风险，同时有直接相关的合法替代项；Agent 只比较一次，再由唯一动作提交者决定最终合法动作。

这一约束既回应了基线里可见风险线索没有形成有效复核的假设，也避免把所有普通成本、职业分歧或不确定性都升级成“危险”。若 Skill 没有进入合法游戏链，输出枚举写得再完整也不能证明它改善了风险或分数。后续架构保留了候选专属 Risk gate，但策略收益仍按运行证据判断。[S06 控制架构审查](../project/reviews/S06-16_FINAL_CONTROL_ARCHITECTURE_REVIEW.md) · [实验复盘](../project/EXPERIMENT_RETROSPECTIVE.md)

这一设计同时限定了风险处理的成本。它不要求 Agent 对每个剧情都启动一次额外调查，也不把“存在任何不利描述”视作覆盖全局目标的命令；只有风险与当前候选及可用替代项直接相关时才要求有限复核。若替代项本身不合法、没有直接缓解关系，或证据只是宽泛关键词，审核仍需给出 WARN 或 UNKNOWN，而不能创造不存在的安全动作。项目保留这种限定，是为了让风险门能改变真正相关的决策，同时不承担未由证据支持的预测能力。

## 4. 后续取证把问题从单一 Risk 扩展到决策顺序

逐步积累的公开轨迹显示，单纯增加“看到风险就处理”的规则不足以覆盖这个问题。健康、绩效、交付和成长机会可能在不同时点变化；Energy 与 Main 的可见效果也不保证每次都兑现。一次早期的 v4 运行在第 6 个月因 Health 归零结束，支持继续研究公开生存趋势和状态刷新，但它只是一局，不证明某个规划规则会提高成绩。

S06 的架构审查把待解决问题描述得更具体：动作顺序可能依赖陈旧观察；规划目标可能在多个维度之间漂移；Risk 应该检查当前候选的直接重大后果，却不应接管一般策略；运行日志还需要能把观察、审核和动作对应起来。审查没有把 v5 的分数归咎于某个 Skill，也没有承诺 v6 一定提高成绩。

因此，方案转为一个清楚的责任分配：Board 说明当前公开事实，Planning 负责唯一主要目标和候选路线，Risk 只检查具体候选，Single Agent 最后提交动作。这里改变的是控制顺序和证据边界，不是“Risk 无效”的结论。[S06 控制架构审查](../project/reviews/S06-16_FINAL_CONTROL_ARCHITECTURE_REVIEW.md) · [S06 收口](../project/S06_CLOSEOUT.md)

这次架构调整也把“决定权”列为工程问题。若 Risk 能自行指定长期目标，Board 又能在自己的摘要里暗中改变目标，系统就会出现多个规划者；若每个模块都能调用 take_action，则回放时难以确认哪个输出代表最终决策。S06 审查因此围绕输入、输出、触发时机和禁止权限审视候选组件，并要求动作仍由一个主体提交。S06 的接受记录说明这条结构满足当时的架构验收，并不能推导为多 Agent 在所有项目中都不可取。

早期 v4 的一次运行在第 6 个月因 Health 归零结束，为“公开生存趋势是否需要进入规划约束”提供了进一步的问题线索。它和 S01 一样，属于单条轨迹；它不能说明把 Health 放进 Planning 后就必然延长寿命，也不能与之后运行做简单分数比较。更可靠的结论是：只针对事件文本做风险扫描，可能不足以表达持续变化的公开状态；Board 与 Planning 需要把状态变化和具体候选联系起来，并在真实运行中检查是否做到。这个变化来自问题定义逐步明确，而不是某一局分数本身决定了架构。

## 5. Structured State 与滚动 Planning 形成完整方法

状态板的出发点是避免把整段 transcript 当作当前状态。它只记录当前 session 可公开确认的字段、来源、新鲜度及少量可直接归因的近期变化；观察前后不可比时保留 UNKNOWN。

Planning 则维护一个公开 Primary Gap、进展、当前公开生存预算和剩余可兑现窗口。它不是一个固定每月动作表：季度 Energy 与 Main 要共同比较；一个动作改变状态后，必须重新 observe；半年实际反馈或晋升结果到来后，旧的进展比较失效，应建立新基线。只有两个相邻、同目标且可比较的观察点都没有目标进展，才足以把当前路线标为停滞并比较一个替代项。

这套职责形成了后来冻结方案的三 Skill 核心。S06 closeout 接受了 Single Agent + structured-state-board + rolling-planning + risk-review 的架构，同时明确 durable Memory、第五 Skill、Team/Swarm 没有进入最终实现。它接受的是设计和已观察到的运行证据，不是策略收益的因果证明。[S06 closeout](../project/S06_CLOSEOUT.md) · [架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md)

它的时间管理也刻意选择事件触发，而不是机械月历：季度首次 Energy、半年评审前的最后决策机会、实际反馈或晋升已被观察、严格的停滞证据、上下文恢复，分别提示不同层次的复核。多个原因出现在同一决策点时可以合并；一个派生标签变化则不能无穷打开新一轮完整复核。这样减少了同一信息被重复读取和讨论的成本，也使之后的运行审计能够追问“这次复核为何发生、有哪些新事实”。这些是架构合同里规定的控制方式，是否在整条运行轨迹中逐次遵循，仍要查运行证据。

它也没有把每个反馈都升级为完整路线重选。当前正式反馈发生时，重建目标比较基线是合理的；两个相邻、同一目标、可比较的观察点无进展，才构成严格停滞；如果只有一次没有增长或输入缺失，就不能宣告路线失败。类似地，生存预算只表达公开趋势，不等价于某个可见属性的固定阈值；剩余窗口用于判断收益是否仍来得及兑现，不是日历到点后自动切换配方。报告保留这些条件，是因为计划逻辑必须说明何时触发、何时仍应等待证据，而不能只描述理想状态下的决策结果。

## 6. 运行正确性成为独立问题

exact v6 是第一条被最终选中的成熟三 Skill 候选路线。它的一次运行走满 48 个月，取得 75.29 quantitative、52.70 competition partial、A、L6；这个结果很强，但审计并没有因此停止。

实际记录包括 203 次 take_action 尝试，其中 202 次成功状态改变并在之后取得 fresh observe；另一次 Energy 多选参数被拒绝，没有改变游戏状态。除此之外，半年 H 标记遗漏、普通 Story 在没有新证据时反复重开讨论、自由文本 CTRL 与动作无法可靠配对，以及两次上下文压缩之后没有重读三个 Skills，都使运行审计结论保持 RUNTIME_ADHERENCE_FAIL。

之后的 v6b 静态修订增加了动作标记、Energy 单项提交和压缩恢复合同；这能改善书面执行约束，却没有把原 v6 的运行结果变成 v6b 的运行证据。最终 ZIP 也没有吸收 v6b 的 runtime 改动。这一步让项目明确区分策略质量、工具正确性、审计可观察性和上下文恢复。[v6 运行记录](../project/runs/v6-run1-validation.md) · [S06 closeout](../project/S06_CLOSEOUT.md)

“202 次成功之后均有 fresh observe”是一个经过逐次配对的正面结果；它不应该被压缩成“整局遵循通过”。总体审计同时覆盖尝试总数、请求合法性、半年标记、故事讨论是否由新证据触发、自由文本动作关联以及压缩后的 Skill 恢复。一个被拒绝的请求没有导致已知状态改变，但它仍是一次调用错误；运行其他部分正确，也不能抵消遗漏的运行约束。反过来，RUNTIME_ADHERENCE_FAIL 也不抹去该局确实走满 48 个月并得到明确终局值这一事实。两种结论在不同审计维度上同时成立。

这个审计还解释了为什么只看动作数量会误导：203 次请求并非 203 次成功推进；那次错误的 Energy 多选请求被拒绝，不能计作状态改变，也不能忽略为“不影响分数的小瑕疵”。同时，202 次成功状态改变都有后续观察，是可复核的正向遵循证据。遗漏半年标记和压缩后未重读 Skill，则属于其他合同项。把这些项目分别列出，可以让工程审阅者针对运行工具、模型指令、状态恢复或日志可观察性分别提出修正，而不将所有问题归为策略质量。

## 7. 从三 Skill 扩到历史四 Skill

后来的一条 v7/v8a 工程路线加入 delivery-progress，专门维护当前局公开承诺、交付证据及其生命周期。它与 Planning 的目标排序和 Risk 的候选审核有不同责任，加入它的动机是让“做过、承诺过、已经验证”不再只靠长对话记忆。

新增模块不等于自动进步。历史 v7 候选包含静态架构迭代和有限运行；v7g 的一次完整局到达 48 个月，量化成绩为 54.52，但策略与运行遵循均有失败发现。后续 v8a 保留四 Skill 结构，成为与 exact v6 不同的成熟工程身份。最终提交审计仍冻结了原三 Skill exact v6；它没有把当前 checkout 更新过的第四 Skill 偷换进 ZIP。[架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md) · [v7g 验证记录](../project/runs/v7g-run1-validation-r2.md)

四 Skill 的工程主张是把“承诺、进行中、完成及其公开证据”从长对话中单独整理出来；这回答的是交付跟踪问题，不是把它升级为策略 owner。是否值得保留要看它是否提高可追踪性、是否造成重复状态、运行时能否加载并稳定使用，以及新增上下文成本是否值得。现有 v8a 两局完成了较长轨迹，但一局 72.65 / A / L5，另一局 59.00 / C / L4；差异提醒读者候选身份相同也不意味着轨迹确定。由于没有 v6 与 v8a 的同条件对照，不能用这两个结果判定第四 Skill 导致分数上涨或下跌。

项目里同时有不同成熟度的候选证据：Candidate v1 的 76.04 是一条较高结果，另一条 v1 轨迹为 35.31、25 个月、D、L4，但其原始轨迹并未保留；v7g 有完整 48 个月结果 54.52，同时发现运行与策略遵循问题；v7q 在 24 个月以 E、L1 结束；v7m 则在 M20 技术失败，没有终局成绩。它们分别可以说明“同名候选结果会有差异”“高分记录完整度不同”“提前终局与技术中断需要不同分类”，但不能串成候选版本逐次升级的严格实验序列。报告因此同时保留候选身份、轨迹是否完成和原始证据是否可用。

表中的斜线值是不同字段依次并列的紧凑写法，不表示同一分数的三个精度版本。比较之前必须先核对运行完整性：48 个月终局可以提供最终量化值；中途技术停止则没有同类终局分数；仅有摘要而没有原始轨迹的旧 Candidate，也无法事后补建工具顺序和动作因果。不同证据完整度可以用于解释项目决策为何倾向某条路线，但不能无条件放进同一个“谁最好”的榜单。尤其是运行月份、grade 和 Level 也只是轨迹属性，不能替代已定义的量化目标或平台正式结果。

本项目实际呈现的数字也没有统一成一个“总分”口径。75.29 和 52.70 分别对应运行记录里的 quantitative score 与 competition partial score；48m、A、L6 是完成时长、grade 和职业 Level。阅读者不能把 52.70 当成官方成绩，也不能因为 A 与 L6 就推断隐藏 Test 中会有相同等级。把字段名称和数值一起引用，能避免二手简历或答辩材料在转述时悄悄改变口径。

## 9. 评估过的高级路线为何没有进入冻结包

这些探索处理的是不同问题。结果只约束各自实际测试的边界，不应被压缩成“高级方法都失败”。

| 路线 | 为什么考虑、实际检查与结果 | 为什么没有进入最终提交 |
|---|---|---|
| Reviewer / 子 Agent | 检查冻结提交运行轨道是否有已注册且机械只读的审核者入口；安全门未通过，后续质量评测没有运行。 | 说明该提交路径下的部署条件不足，不是说独立审查没有价值。 |
| 自动 Memory 锚点 | 检查冻结运行轨道是否能自动把 MEMORY.md 正文带入关键阶段；自动锚点缺正文，显式读取可用。 | 这条自动路径未达到部署门，不代表所有 Memory 方案无效。 |
| Deterministic helper | 在隔离工具轨道验证有界公开状态读写、跨模拟压缩保留和安装重置。工具层成立，但没有部署为正式 Candidate。 | 云端权限、模型是否调用和是否遵循没有验证，不能称为游戏收益。 |
| Replay controller | 在 24 个案例中只有 1 个状态级修正，8 个案例仍为 UNKNOWN，主要决策错误没有证明被修正。 | 控制器逻辑信号不足，未形成 Candidate，也未验证模型或工具运行收益。 |
| 策略挖掘 | 对 13 个运行的 82 个已完成窗口作描述性分析；暴露、状态和延迟结果仍然混杂。 | 没有支撑可安全部署的新策略增量，不能作因果归因。 |
| Simulator policy search | 公共输入的确定性 harness 通过边界检查，但冻结 Story 基线只完成 2/16；12 个宏配置中只评估基线。 | 停在可行性门，没有做宏策略筛选、确认或 holdout，不代表搜索空间已被证明无效。 |
| Team / Swarm | 没有完成部署和对照实验。 | 保持 DEFERRED / NOT_TESTED，不能称为已证实无效或不可行。 |

每条路线都有自己的详细研究记录；紧凑入口见[实验复盘](../project/EXPERIMENT_RETROSPECTIVE.md)和[最终证据审阅](../project/FINAL_EVIDENCE_REVIEW.md)。

这些探索并非同一种实验：Reviewer 先过安全部署门，未过就没有质量评测；Memory 锚点实际检查自动注入链，发现的是指定路径缺正文；helper 检查隔离工具上的确定性状态操作，并未证明游戏模型会调用；Replay controller 以案例回放衡量能否纠正已有状态级错误；策略挖掘复用历史运行作描述性匹配，仍受选择与状态混杂；Simulator search 则先要通过廉价 harness 和冻结基线可完成性门槛。把这些结果统一写成“高级方案失败”会丢掉它们分别回答的问题，也会把“没有执行”误当成“执行后无效”。更准确的综合结论是：现有证据尚未支持把任何一条路线纳入最终提交身份。

其中，策略挖掘共整理 13 个运行的 82 个已完成窗口，并构造 28 组匹配对；这些匹配只能使描述更具体，无法消除动作选择、当时状态和延迟后果相互混杂。Simulator policy search 定义了 12 个宏配置，但冻结 Story 基线只完成 2/16，最终只运行了基线，没有后续策略对照或 holdout。Replay controller 的 24 案例中仅有一次状态级修正，八个仍为 UNKNOWN；这些结果足以说明目前的纠错信号薄弱，却不足以断言该方法原则上无效。Reviewer 安全入口未找到，也只约束所审查的冻结提交路径。

## 10. 为什么最终回到 exact v6

最终决定使用 exact v6，原因是它在 Main 已接受的成熟三 Skill 路线中有可绑定的完整身份和一条有效的 48 个月高位样本。标签 HIGHEST_OBSERVED_MATURE_THREE_SKILL_CEILING 的人话含义是：在现有记录所覆盖的成熟三 Skill 路线里，Main 选择了观察到的高位且身份能够精确冻结的方案。

这不等于所有 Candidate 的最高分。v1 曾有 76.04，高于 v6；但另一局只有 35.31，原始轨迹不可用，不能用单次峰值替代身份和证据质量。v8a 有两个 48 个月样本，但它是四 Skill 版本，分数不同，不能当成 v6 的受控重复。v6d 是历史 fallback，不是这次用户冻结的 exact 身份。

Main 选择的是 source commit 1114a04b75548cf52f030d123564e527060fc061 对应的 Candidate、三个 Skill 字节和最终 ZIP，而不是“把所有历史分数排队后选最大”。选择理由是证据范围内的工程决策，不是统计胜出、理论最优或因果效果。[最终方案审阅](../project/FINAL_SOLUTION_REVIEW.md)

因此，最终选择考虑的不只是峰值。v1 的 76.04 是当前摘要中更高的单次数字，但其另一局提前终止、分数较低，而且原始运行材料缺失；v6 的样本分数略低，却有明确冻结的源代码身份、可审计的完整轨迹和可核对的包哈希。这个权衡是项目治理中的交付选择：用身份和审计证据换取可说明性，不声称它是随机意义上的最佳候选。标签里的 ceiling 也只能在“当前记录所覆盖的成熟三 Skill 候选”这个范围内理解，不能扩大成全仓库最高分、赛事最优或未来上限。

这里的“可审计”并不意味着 v6 运行完美；恰恰相反，运行缺陷被保留并进入最终评审，让选择者可以看到一个强完整样本仍然有明确限制。作决定时要同时考虑：它是不是同一提交身份；是否有完整的终局记录；原始工具轨迹能否支持运行审计；包成员和摘要能否重复核对；选择理由是否与实际受测候选相符。用这些维度进行治理，不会自动解决策略质量问题，但能避免把来源不明的历史峰值误打包成当前交付物。

## 11. 冻结提交与工程收口

最终 ZIP 为 FZU-Loss-final-v6.zip，7 个文件，18,082 字节，SHA-256 为 31e836b591703dfe520916828da033a57de260bb451d97047bbaee9daaa11b9b。运行来源 commit 是 1114a04b75548cf52f030d123564e527060fc061；干净 main 打包 commit 是 113052a9a8943efc7fb2d7d1140f126e62e92040。冻结审计记录了身份、成员校验、离线验证范围以及人工上传清单。

提交包在本地完成允许范围内的离线材料与隔离校验；没有运行完整环境型 CLI 校验，也没有启动共享服务、调用 Provider 或提交新游戏。官方门户没有可读的最新通知，记录没有官方上传回执。因此项目只说“已冻结并本地验证的提交包”，不说“比赛已上传”或“平台已评测”。[冻结审计](../project/reviews/S10-23R_FINAL_SINGLE_SHOT_FREEZE.md) · [manifest 与上传清单](../project/FINAL_SUBMISSION_MANIFEST.md)

S11 随后整理代表性证据、展示编号、保留限制和人读报告入口。S03 旧工作区的配置依赖先已改回主仓库默认位置，必要的 20 份 session payload 留在被 Git 忽略的本地保留目录；之后自动删除被策略拦截，用户在 S11-12 手动删除了精确目录，收口核验通过。该操作不代表 held raw evidence 已释放，也没有触发全仓清理。[工作区退役记录](../project/LOCAL_WORKSPACE_RETIREMENT.md) · [项目复盘](../project/PROJECT_RETROSPECTIVE.md)

文件冻结本身也不等于证据生命周期结束：包的哈希能确认某份 ZIP 与记录身份一致，但不能复建唯一 raw 轨迹；保留摘要可供审阅，也不会自动关闭 FORENSIC_HOLD。S11-12 只收口了旧 workspace 目录的退役操作。仍有 20 份被指定保留的 session payload 按记录留在另一个本机位置，并维持原有 hold 状态；未授权的大范围清理、共享会话删除或凭据处理都不属于这次收口。这样把“旧目录已删除”与“底层取证责任已经解除”严格分开。

S11-12 采用人工删除是用户在精确目录上实施的退役动作，随后按记录核对路径已不存在、主仓库配置与忽略边界处于预期状态。报告能够据此描述旧工作区退役收口，但不能声称 20 份保留材料已复析、复制到远端或由 Main 接受解除 hold。该差别对未来复盘很实际：若之后的结论仍依赖这些原始 session，就必须先确认保留目录和访问路径；若责任 Task 要求清理，则应按记录里的解除条件走 Evidence Closure，而不是因为旧 S03 工作区已经消失就自行推断不再需要来源。

## 12. 项目真正留下的经验

- **架构要跟着可观察瓶颈走。** 多加一个 Skill、Agent 或控制器，不是目标本身；新组件需要清楚的 owner、输入、输出、禁止权限和能改变决策的证据。
- **观察不等于因果。** 同局里先发生 A 再出现 B，只能先说明时间关系。要说 A 导致 B，需要更强的对照和身份一致性。
- **运行正确性独立于策略质量。** 完整通关、工具格式、fresh observe、上下文恢复和成绩分别审计。
- **负结果要按实际边界书写。** 未部署、没有运行、技术失败、信号弱和策略比较失败不是同一结论。
- **来源身份比一个分数更重要。** Candidate source、验证局、构建提交、manifest 和 ZIP 是不同对象；只靠“v6”标签无法证明它们对应。
- **复杂度需要能回应一个具体问题。** 如果一项实验不能改变决策，也不能排除竞争解释，就保留未知并停止扩展。
- **本项目经验不自动成为跨项目规律。** 这些结论来自 CareerSim 的特定运行轨迹、Runner 和提交边界；其他系统要重新核对自己的接口与失败模式。

如果从头再做，较省成本的路线不是跳过验证，而是更早把验证分层：先用最低成本证明包可校验、运行时能发现并加载 Skill；再用严格有界的真实情境检查其是否被调用和应用；同时从第一个状态改变开始保存动作回执与 fresh observe 配对。只有看到一个可定位、会改变架构或候选选择的瓶颈，才增加模块或启动昂贵游戏。最终构建身份与当前开发 checkout 也应分开记录，避免把新工作树误当成最终 ZIP 来源。

这是一种基于已知返工点的反事实建议，不是对“按新顺序就会得更高分”的承诺。早期把 S03-02 的调用路由验证放在真游戏行为结论之前，可能更早发现 smoke 接口不匹配；从首个动作开始保留 observe/action 配对，也会让运行遵循更易审；freeze build 与开发 checkout 的身份分离，则降低误把后续代码当成已提交包的风险。但项目没有可靠的工时台账来量化这些改动会节省多少时间，也没有反事实对照来估计对成绩的影响。可复用的工程建议应限于证据链更早、更清楚，而不是精确节省时长或提高分数。

因此，项目复盘能提供的是一组流程改进点，而非可移植的 CareerSim“万能策略”：先确认运行身份和权限，再验证提交包与 Skill 接口；在开始昂贵运行之前证明观察、动作和回执路径正确；对真实运行限定次数与停止条件；为每条候选保留能独立审阅的终局摘要和必要 raw 来源；最后把源提交、构建提交与 ZIP 哈希分开锁定。换到另一赛题时，这些流程建议仍需结合它自己的工具副作用、运行合同、数据保留要求和官方评分口径重新核验。本项目只证明了这些边界对这条 CareerSim 工程线有解释力。

仍未解决的问题应继续保持显式：最终包是否进入官方平台、平台是否完成评测、隐藏 Test 上的表现、exact v6 的跨局分布、三 Skill 相对其他架构的因果收益、Team/Swarm 与 durable Memory 的部署价值，都没有当前证据可作肯定回答。S11 阶段材料整理完毕，也不等于全仓取证 hold 自动解除或项目路线被宣布最终完成。若之后出现官方回执、新的可比较运行或 Main 对保留证据的接受记录，应把它们作为新证据单独登记，避免改写这里依据旧快照形成的结论。
