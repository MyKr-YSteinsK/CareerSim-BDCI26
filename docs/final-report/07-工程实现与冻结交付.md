# 07｜工程实现与冻结交付

## 1. 从工程仓库到可复核提交包

CareerSim 工程实现包含几个彼此相关但不能互相替代的对象：官方 Runner 与依赖环境、Candidate 配置、Skills 与其装载方式、实际运行轨迹、打包 manifest、最终 ZIP。源码能解释设计，运行日志回答曾发生什么，manifest 和 hash 则确认交付成员与身份。审阅者要沿这些对象逐层核对，不能只看当前 `skills/` 目录或一张分数表。

项目使用的 Runner 取证 SHA 为 `f61c738c72e51b77298cc1c14c7c6ebf4b6c527d`；环境记录包括 Python 3.12.13 与锁定依赖。运行时不允许静默改变 frozen Runner、依赖或 `uv.lock`。这些约束把环境身份纳入工程审计，避免把安装漂移或工具链差异误当成策略变化。[环境记录](../project/ENVIRONMENT.md) · [官方来源锁](../project/OFFICIAL_SOURCE_LOCK.md)

## 2. 最终架构的实现分工

提交物是 Single Agent + 3 Skills。它们不是三个独立 Agent，也不是三个工具调用者：

| 组件 | 实现职责 | 交付边界 |
|---|---|---|
| `structured-state-board` | 从同一 session 的 fresh public observe 整理字段、来源、新鲜度和有限近期变化 | 不读隐藏状态、不规划目标、不提交动作 |
| `rolling-planning` | 作为唯一策略 owner 管理公开 Primary Gap、进展、风险预算和可兑现窗口 | 不直接调用 take_action，不把固定阈值写成隐藏规则 |
| `risk-review` | 对已经生成的当前合法候选审查直接相关的公开重大后果 | 不设长期目标，不替代一般动作排序，不提交动作 |
| Single Agent | 汇总当前公开事实、选择合法动作并作为唯一提交者 | 每个状态改变后重新观察；Skill 本身不获得动作权限 |

理想控制链是 `fresh observe → Board → Planning → Risk gate → 单一动作 → fresh observe`。这是包内责任合同，不表示模型在所有时点都成功执行。历史 v8a 的 `delivery-progress` 属于不同 Candidate；它不是冻结 v6 的第四个 Skill。[架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md) · [最终 Skill 身份](../project/FINAL_SUBMISSION_IDENTITY.json)

## 3. 工具调用与运行证据

Agent 的自然语言意图、MCP 请求、模拟器回执和后续状态是不同的证据。动作日志应能确认所用工具、请求参数、成功或拒绝结果，以及动作后是否取得新 observe。状态没有变化时不能把请求写成成功；超时或部分回执则先核对同一 session 的状态，仍不明就停止并记录 UNKNOWN，不盲目重发。

exact v6 样本中有 203 次 `take_action` 尝试，其中 202 次成功状态改变，之后都有 fresh observe；另一次 Energy 多选请求被拒绝，没有改变游戏状态。这是好的逐动作审计例子：正向通过项与失败项同时保留，不能把 203 次都叫成功，也不能因为其中一次被拒就否认其余配对事实。

审计还发现半年 H marker 遗漏、普通 Story 无新证据时反复重开讨论、自由文本 CTRL 与动作不能可靠配对，以及两次压缩后均未重新读取三个 Skills。这些缺陷使运行结论为 `RUNTIME_ADHERENCE_FAIL`。完整跑到 48 个月说明轨迹有终局，不代表运行契约通过；书面合同有要求，也不能替代运行日志中的行为证据。[v6 运行记录](../project/runs/v6-run1-validation.md) · [S10-23R 冻结审计](../project/reviews/S10-23R_FINAL_SINGLE_SHOT_FREEZE.md)

## 4. 上下文恢复与静态修订的边界

模型上下文压缩后，恢复要以同一 session 的 fresh observe 为准，再重新建立 Board、Planning 当前状态并读取相关 Skills。v6 实际运行两次 CurrentRoundCompressor 后均没有重读三个 Skills，因此审计将恢复流程计为未完成。后来 v6b 增加 canonical CTRL prefix、单项 Energy 提交、DECISION_CLOSED 与压缩恢复合同；这属于静态执行合同修订，不是一次新的策略运行，也没有进入最终 exact-v6 ZIP。

因此实现状态应分别写成“设计合同存在”“静态材料通过”“框架已发现/加载”“运行时有实际调用”“调用后的策略效果可验证”。一份 Markdown Skill 或一个本地 helper 成功，无法自动证明云端权限、模型是否采用、长程遵循或分数收益。该分层能防止把可读源文件与真实部署效果混成一个结论。

## 5. 打包、manifest 与本地验证

最终包 `FZU-Loss-final-v6.zip` 有 7 个文件、18,082 bytes，SHA-256 为 `31e836b591703dfe520916828da033a57de260bb451d97047bbaee9daaa11b9b`。运行源为 `1114a04b75548cf52f030d123564e527060fc061`；干净 main 打包提交为 `113052a9a8943efc7fb2d7d1140f126e62e92040`。身份、成员 allowlist、单文件 hash 和 ZIP hash 分别记录，便于复核包是否与冻结身份一致。

提交前做过冻结范围内的本地离线材料检查和隔离校验。没有运行完整环境型 CLI 校验，没有启动共享服务，没有调用 Provider，没有创建新 game，也没有执行平台上传。检查通过仅支持已执行的离线材料范围，不等于本机完整 runtime 验证，更不等于官方平台接收或评测。[manifest](../project/FINAL_SUBMISSION_MANIFEST.md) · [S10-23R audit](../project/reviews/S10-23R_FINAL_SINGLE_SHOT_FREEZE.md)

## 6. Git、运行时和本机证据边界

项目按 Main/Stage 分工冻结事实。当前 main checkout 是历史 v8a 四 Skill 工程状态，最终 ZIP 则绑定旧 exact-v6 source 与构建提交。目录、文件名或分支较新都不能覆盖冻结身份。来源、Candidate、运行、打包与平台提交各自需要对应证据；报告不会用当前 checkout 倒推早期包成员。

本地 workspace 迁移与清理也按精确路径和 `FORENSIC_HOLD` 责任处理。S03 旧工作区目录已由用户人工删除并完成该目录的退役收口，但 20 份被要求保留的 session payload 仍在另一个本机保留位置，相关 hold 未释放。旧目录退役不自动意味着 raw 来源无需复析，也不授权全仓清理。完整范围与后续解除条件见[本机工作区退役记录](../project/LOCAL_WORKSPACE_RETIREMENT.md)和[最终证据台账](../project/FINAL_EVIDENCE_REVIEW.md)。

## 7. 可以复现的是什么

当前记录可以让审阅者核对：Runner 锁定身份、Candidate source、最终包成员、Skill 摘要、构建提交、ZIP hash、离线检查范围及那条 exact-v6 运行的已知行为。它没有提供可复现的随机分布，也没有证明历史局可逐动作重跑；源 commit 和 ZIP hash 不能代替已删除或 held 的唯一 raw 轨迹。

官方上传未执行，没有上传回执和平台评测证据；保密 Test 的成绩未知。最终交付状态应称为“已冻结并按记录完成本地离线核验的提交包”，而不是“官方已提交”“平台已通过”或“隐藏测试表现已验证”。[官方来源锁](../project/OFFICIAL_SOURCE_LOCK.md) · [当前状态](../project/CURRENT_STATE.md)
