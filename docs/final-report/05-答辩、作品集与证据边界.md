## Part A｜答辩 FAQ

### 1. 这个项目到底做了什么？

项目针对最长 48 个月的 CareerSim 职业模拟，构建了单 Agent、三个职责模块和动作后观察的决策方案，并将真实运行、遵循审计、来源记录与最终打包结合起来。它既有完整本地运行，也有明确保留的执行缺陷和负路线。

对外可以把成果概括为“长程 Agent 方案与证据驱动的工程交付”。不能概括成“已获得官方高分”或“已证明稳定策略”。简明结果与主要限制见 [01](01-项目总览与最终成果.md)。

### 2. 为什么使用 Single Agent？

方案保留一个动作提交者，让当前状态、候选选择与实际执行有明确责任。Skill 拆分判断职责，没有增加多个能够改变环境的 actor。

这是已接受的工程选择，便于解释和审计。项目没有与 Team/Swarm 做受控性能比较，不能声称单 Agent 已被证明更强。职责图见 [02](02-Agent技术方案与系统架构.md)。

### 3. 为什么拆成三个 Skill？

三个模块分别负责公开事实、策略规划和候选重大风险。规划只保留一个责任方，风险不会再成为总体策略 owner，事实摘要也不隐含推荐动作。

这使评审能检查每项判断的输入与权限。它不证明三个一定是最佳数量；数量要结合责任和运行证据讨论。完整设计见 [02](02-Agent技术方案与系统架构.md)，逐条机制学习见 [Track A](../tutorial/track-a-skill/00-学习地图.md)。

### 4. 为什么没有采用 Team/Swarm？

当前状态是 **DEFERRED / NOT_TESTED**。项目没有完成专门可行性实验，也没有得到比较收益证据。延后是一项范围与治理决定，不是“测试失败”或“官方禁止”。

若未来重开，需要明确共同状态 authority、动作提交权、隔离及收益问题。当前报告没有执行这项工作。研究路线边界见 [03](03-研发演进、实验与失败复盘.md)。

### 5. 为什么没有选历史单局更高的 v1？

v1 的高局不能脱离同源低局展示；其原始 raw 在当前比较中不可用，证据来自 Tier-B 摘要。最终选择没有采用“所有历史单局最大值”这一排序规则。

Main 冻结的是成熟三 Skill 的 exact-v6 身份。这个决定有明确来源，但不能读成 v6 统计胜出；高低两局及理由见 [04](04-最终方案、候选选择与工程交付.md)。

### 6. 为什么 v6 有 adherence fail 仍然被选？

选择没有把缺陷删除。该样本是有效完整 gameplay，同时运行契约遵循失败；冻结记录接受它作为有限参考并保留问题。

选定一份身份与认证所有行为正确是不同决定。不能说缺陷无关紧要，也不能借后续补丁把原样本改成通过。具体缺陷与接受理由见 [04](04-最终方案、候选选择与工程交付.md)。

### 7. 为什么没有用后来的 v8a？

v8a 是四 Skill 的另一行为身份，不是 v6 复验。其两个完整样本有不同轨迹及运行、证据限制，不能提供证明它更优的干净对照。

最终冻结决定没有把当前 checkout 等同于提交包。比较数据与身份区别见 [04](04-最终方案、候选选择与工程交付.md)。这个回答不证明四 Skill 必然不如三 Skill。

### 8. 为什么结果会有明显波动？

项目面对不同轨迹、模型行为、状态反馈和执行问题。少量历史样本还涉及架构与环境差异，因此有多个竞争解释。现有资料不能精确拆出每项因素造成的波动。

同一冻结候选的两条结果可以说明观察不同，不能估计完整分布，也不能直接归因于代码变化。答辩中应保留“未识别原因”，不要编出统计结论。[Track D](../tutorial/track-d-project-method/00-学习地图.md)

### 9. 如何证明 Skill 真正起作用？

文件存在、格式合法、安装、发现、读取、行为应用与收益要逐层举证。某一层通过不会自动把后面全部推成 PASS。

本项目保留静态与运行记录，也记录未遵循部分；没有给出单 Skill 的因果贡献估计。如果问“是否提高分数”，应回答目前没有受控证据支持这种拆分。系统链见 [Track B](../tutorial/track-b-system-runtime/00-学习地图.md)，验证意义见 [Track D](../tutorial/track-d-project-method/00-学习地图.md)。

### 10. 为什么要做这么多 Candidate？

不同 Candidate 用于表达不同被冻结的行为假设或责任改动。版本号不是成绩，也不是每个版本都已经真实运行；一些只有静态原件，不能借相邻版本的结果证明自身。

项目后期已经停止增量规则循环与新候选搜索。可解释的是代表性的转折、证据和停止条件，不需要把所有版本名变成答辩流水账。[03 研发主线](03-研发演进、实验与失败复盘.md)

### 11. 为什么要做 forensics？

分数或完成标志有时不能解释实际执行链。取证用于检查会话归属、工具回执、状态变化、压缩与审计标记，排除错误归因。

项目曾排除旧 session 分数误归给新 Candidate 的情况，也保留技术部分样本而不补造终局。取证可以确定一些事实，仍可能留下未知根因；它不是为每个低结果找到理由。[03 代表案例](03-研发演进、实验与失败复盘.md)

### 12. Reviewer 为什么没有被正式采用？

被测冻结提交路径没有建立安全的机械只读 Reviewer 部署边界，研究在前置安全门停止。后续盲评质量阶段未运行。

准确表达是“该测试路径未安全部署”，不能说独立审查普遍无效，也不能说已经测过并降低分数。研究原件与范围见 [03](03-研发演进、实验与失败复盘.md)。

### 13. Memory 为什么没有被正式采用？

测试对象是自动 MEMORY.md anchor；其正文没有按要求自动进入捕获的系统内容，显式读取却可用。因此未通过这个自动持续性门，没有进入后续收益检验。

“文件可读”和“自动、持续可见”是不同事实。其它记忆设计与模型收益仍未知，不能把结果压缩为“Memory 无效”。详细来源见 [03](03-研发演进、实验与失败复盘.md)。

### 14. Helper 或 controller 不可以解决执行问题吗？

确定性 helper 仅获得隔离工具层支持，没有正式 Candidate 部署或模型调用、遵循证据；controller 的回放信号弱，也没有形成部署依据。

它们提供了不同层的局部信息，不能组合成一个已经验证的控制器。将来是否值得重开，需要针对部署与行为重新设门，当前不声称收益。[03 研究路线](03-研发演进、实验与失败复盘.md)

### 15. 项目最失败的路线是什么？

更准确的回答是按门槛区分结果，而不是给所有路线排“最差”。Simulator 搜索停在基线可行性门，宏策略没有比较；Reviewer 停在安全部署门；controller 和策略挖掘信号弱；技术断连又是另一类。

如果被追问“哪条没有回答原定问题”，可以用 Simulator 解释前置门如何阻止无效比较，但必须说宏策略优劣仍未知。原始问题、门与非结论见 [03](03-研发演进、实验与失败复盘.md)。

### 16. Human Play Lab 的意义与关闭原因是什么？

HPL 是独立人工游玩研究与假设来源，不走正式 Agent 的同一控制路径，所以不能直接作为正式候选或 adherence 对照。实现细节见 [Track C](../tutorial/track-c-repository-tooling/00-学习地图.md)。

路线后来由用户关闭：**CLOSED_BY_USER；closure reason = UNKNOWN**。当前 canonical source 没有具体原因，不能猜测没价值、太慢或结果不好。

### 17. 怎样防止只对本地 Dev 有效？

项目约束策略依据本局 participant-visible（参赛者可见）公开事实，保留低结果与失败，不因单局峰值推广，也不把隐藏分析转成运行答案表。有限比较和停止条件限制了无界事后加规则。

这些做法可以降低误判风险，没有证明 hidden-test transfer。正式隐藏测试结果仍未知；不能把 anti-overfit 意图当成已完成泛化验证。[Track D](../tutorial/track-d-project-method/00-学习地图.md)

### 18. 如果再给时间，最应该改什么？

**建议，不是已执行结论：**先明确新问题与授权，决定是否针对已知执行缺陷开展独立修复与重复样本，保持身份可比较。不能一边修补一边把旧成绩继续当作新方案结果。

若要研究 Reviewer、Memory 或 Team，也应先改变并验证相应部署边界。当前比赛实验与包重建已关闭，这个回答不是继续运行许可。[04 的限制](04-最终方案、候选选择与工程交付.md)

### 19. 最终提交到底是什么？

它指历史 exact-v6 的冻结 ZIP，采用 agent 模式和三个 Skill。当前 main 中较新的历史工程文件不是这份包。

包的精确 source、build、成员与哈希只看 [04](04-最终方案、候选选择与工程交付.md) 及其权威来源。称“最终方案”不等于声明平台已经收到。

### 20. 官方成绩是多少？是否获奖或进入排名？

**没有官方上传或平台分数证据。**本地运行、离线检查和包冻结不能替代上传回执、平台评测或奖项通知。官方成绩、排名和获奖情况均不能据现有材料认领。

答辩中应明确说“项目展示的是本地工程成果与观测”。若未来新增官方回执，也应把它作为新证据单独记录，而不是追认本轮文档已经证明。[04 提交边界](04-最终方案、候选选择与工程交付.md)

## Part B｜简历与作品集素材

### 1. 项目事实与个人贡献分开

仓库能支持“项目形成了某个架构、运行记录或交付流程”，不能单独证明这些工作全部由某个人独立完成。项目使用了 Main、Stage、Plan 与 Codex 的协作方式，个人理解、设计、审查、编码与工具生成的贡献需要区分。

**PERSONAL CONTRIBUTION — USER MUST VERIFY**

以下简历素材是项目级模板。使用“我设计”“主导”“实现”前，应核实实际负责的部分、对应材料及参与方式。如果无法确认，只用项目描述或“参与”，并在面试中明确工具和协作者的作用。

个人贡献的核验可以围绕三个问题：本人实际作过哪些判断，哪些材料可以支持这些判断，哪些实现或验证借助了他人或工程 Agent。不要只因为能打开仓库或看到 commit，就把全部工程写成独立完成。

### 2. 项目名称与一句话定位

**名称：**CareerSim 长程 Agent 决策与证据工程。

**项目级定位：**面向 48 个月职业模拟，形成单 Agent 与状态、规划、风险三职责协作的方案，结合真实运行审计、负结果保留和精确身份交付。

**个人版使用规则：**只把已核实负责的责任加在定位之后，例如“负责已核实的职责设计与运行证据审查”。不要在未核实时改写为“独立完成整套系统”或“从零实现官方框架”。

官方 Runner、JiuwenSwarm 和模拟器是运行基础，项目工作是方案材料、工程集成、实验与证据处理。外部框架使用经验可以写，但不能认领其源码为自研成果。

### 3. 四条简历 bullet 模板

使用者应选择与本人真实贡献相符的条目，补充可证明的参与边界，不需要把四条全部写入简历。

- **架构方向：**参与长程 Agent 方案设计，将公开状态、策略规划与候选风险划分为三个 Skill 责任，保留单一动作提交者和动作后观察的执行链。
- **运行方向：**参与基于官方 Runner、JiuwenSwarm 与 MCP 的本地运行集成，区分模型选择、工具回执和环境新状态，记录执行缺陷与恢复限制。
- **实验方向：**参与冻结候选的有界评估与负路线审查，分开处理静态有效性、运行遵循、终局结果和未证收益，保留低结果及技术部分样本。
- **证据与交付方向：**参与运行来源、会话与工件身份核对，整理可追溯证据及离线冻结交付材料，明确本地准备与官方上传之间的验证边界。

如果需要提成绩，单独补一句“最终所选方案有一个本地完整观测，同时存在运行遵循失败”，并链接 [04](04-最终方案、候选选择与工程交付.md)。不要把成绩嵌成每条 bullet 的收益证明，也不要写“稳定高分”或“提升百分比”。

### 4. 30 秒项目介绍

> 这个项目研究 Agent 如何在最长 48 个月的职业模拟中持续做决策。方案把公开事实、规划和候选风险分给三个 Skill，最终动作仍由一个 Agent 提交。项目还建立了运行身份、遵循审计和交付追溯，保留了完整本地样本与失败证据。最终冻结的是历史 exact-v6；它有完整结果，也有执行缺陷，没有官方平台成绩证明。

这段是项目介绍，未使用未经核实的个人主语。转成面试自述时，在末尾补充本人已经核实承担的工作，并清楚说明 Codex 或其它工具参与了哪些部分。无需在短介绍中念 source hash；需要复核时打开 [04](04-最终方案、候选选择与工程交付.md)。

### 5. 两至三分钟技术介绍框架

| 顺序 | 要说的内容 | 适合展示的材料 |
|---|---|---|
| 问题 | 长程状态变化、公开/隐藏边界、结果与执行的不一致 | 01 的赛题和主要限制 |
| 方案 | 状态、规划、风险三职责与单一动作提交权 | 02 的决策职责图 |
| 工程难点 | 一个真实归因或恢复问题，说明怎样查证 | 03 的五个代表案例，选择一个 |
| 研究判断 | 一条研究路线停在哪个门，为什么不继续部署 | 03 的 Reviewer、Memory 或 Simulator |
| 交付 | 最终包身份、完整样本与遵循限制同时成立 | 04 的身份、缺陷和提交边界 |
| 本人贡献 | 只讲实际负责与能够解释的工作 | 本人确认过的材料与决策 |

这套框架优先讲“问题—方案—证据—判断”，避免介绍全部 Candidate 或逐个念 Task。若评审追问具体 Skill 条款、安装命令或目录含义，再进入教程，不把技术介绍变成安装课。

### 6. 作品集页面建议

正文可包括项目定位、责任图、一个取证案例、一个有边界的负结果和最终交付概况。每个图表都让读者知道它描述的是设计、观测还是解释；成绩旁展示样本数与遵循限制。

建议把完整工件身份链接到 04，将内部运行台账链接到权威来源，而不是复制到首页。作品集对外公开是另一个授权与信息审查环节，本任务没有发布页面、上传仓库或分享原始日志。

公开材料不要包含凭据、本机用户目录、服务配置或未经筛选的 session payload。原始日志可能混合 Provider、模型上下文或其它本机内容；工程证据有留存价值，不代表适合直接展示。

### 7. 技术追问应准备到哪里

本人需要能解释所认领的责任：为什么这样拆模块，证据哪里支持这个判断，运行出现什么缺陷，为什么没有继续扩展。仅记住三个 Skill 名或最高分不足以支撑“主导架构”声明。

如果被追问尚未复核的实现细节，应明确说“当前没有这个层次的证据”，再给可查来源。对于未进入的质量阶段、没有平台分数或 HPL 未记录关闭原因，不要用推测补齐故事。

## Part C｜证据边界与 Claim Safety

### 1. 常见声明的安全改写

| Claim（声明） | Safe? | 建议措辞 | 为什么 |
|---|---|---|---|
| “最终方案得分 75.29” | 有条件 | “最终所选方案的一个本地完整样本量化分为 75.29，同时 RUNTIME_ADHERENCE_FAIL” | 必须绑定字段、样本与执行限制 |
| “方案稳定 75+” | 否 | “稳定性能与期望分数尚未证明” | 最终候选只有一个完整样本 |
| “超过 baseline 179%” | 否，作为提升声明 | “基线与后续方案有不同观测结果，比较不识别因果收益” | 多个机制、环境与轨迹差异未控制 |
| “获得比赛高分” | 否，若暗示官方成绩 | “取得一个有边界的本地 Dev 观测” | 本地量化分不是平台评测成绩 |
| “进入 Top N” | 否 | 删除排名声明 | 没有排名或入围证据 |
| “已提交官方平台” | 否 | “本地包已准备并冻结；官方上传未执行或未获证明” | 无上传回执 |
| “Team/Swarm 不如 Single Agent” | 否 | “正式方案采用 Single Agent；Team/Swarm 延后且未测试” | 没有受控比较 |
| “Memory 无效” | 否 | “被测自动 MEMORY.md anchor 未通过；显式读取可用” | 结论仅覆盖该自动路径 |
| “Reviewer 无效” | 否 | “被测冻结路径未安全部署，质量阶段未运行” | 安全部署门不等于建议质量 |
| “v6 是最优方案” | 否 | “在现有证据和冻结约束下被选中的成熟三 Skill 方案” | 不是统计或全局最优证明 |
| “Helper 已改善策略” | 否 | “隔离工具层可行性获得支持，正式部署与收益未测” | 工具能力不证明模型应用 |
| “Simulator 证明宏策略没用” | 否 | “基线可行性门失败，宏策略未比较” | 目标比较没有发生 |
| “我独立完成全部项目” | 未核实 | 只陈述本人核实参与的责任与产物 | 项目级事实不证明个人全部归属 |
| “已实现隐藏测试泛化” | 否 | “hidden-test transfer = UNKNOWN” | 无官方隐藏集运行证据 |

表中的不安全表达是审查对象，不是项目宣称。正确措辞可以更短，但不能删去使它成立的关键限制。尤其不能把“本地”缩写成比赛成绩，或把“被测路径”删成全机制否定。

### 2. 五类证据各有范围

| 证据 | 可支持的声明 | 不能支持的声明 |
|---|---|---|
| 静态材料与代码 | 某个责任、字段或检查已经实现 | 模型一定读取、遵守或获得收益 |
| 运行事件与观察 | 对应 session 的动作、回执与状态发生 | 所有相邻变化都由某动作造成 |
| transcript 与 adherence 审计 | 可见执行线索、明确缺陷与无法认证项 | 标记存在即协议全面通过 |
| 冻结身份与工件 manifest | 来源、成员、字节与所选包一致 | 官方受理或云端效果通过 |
| 回顾性分析与摘要 | 已有记录中的有限现象与决策依据 | 严格受控效果或稳定分布 |

引用多个相同来源的摘要，也不会增加独立样本数。权威复盘、报告与教程可能都引用同一次 Run，它们是不同解释入口，不能被描述为三次验证。

### 3. 保留实验与官方事实边界

官方规则按 [官方来源锁](../project/OFFICIAL_SOURCE_LOCK.md) 的核验语境理解。框架支持某种模式，不等于本项目测试过它；赛题目标或历史入围条件，也不等于本项目实现了相应名次。

项目实验只使用获准来源形成决策。隐藏计数、内部规则分析或局后取证不能直接成为可部署答案表；participant-visible 的新鲜观察优先。报告对这种约束的解释不等于已证明隐藏测试迁移。

### 4. 取证保留不是展示许可或删除许可

S11 仍保留 active/pending forensic holds。本轮报告重写没有解除任何 hold；原件能否删除要依据准确来源、释放条件及 Main/Stage 接受，不能由报告篇幅或结论已吸收推断。

摘要便于阅读，hash 用于身份核验，两者都不能替代仍需要复析的唯一 raw。部分 hold 范围仍未知，不能根据“有 Git 历史”就认定本机证据可恢复。完整台账只在权威工程层维护，不在作品集中复制。[最终证据审阅](../project/FINAL_EVIDENCE_REVIEW.md)

### 5. 项目层面的安全表达规则

- 把设计要求写成“方案规定”，把执行事实写成“对应运行观察到”。不把前者直接改写为后者。
- 把分数绑定到本地 Dev、Candidate、样本和字段。不同来源或版本的数据不拼成复验。
- 把部署门、技术失败、弱信号和未测试分别描述。没有运行的阶段保持未测，不填成零收益。
- 把复杂度控制或成熟度解释标为工程判断，不把它包装成统计结果。
- 把包准备、上传、评测、排名分开。缺任何一项就保留相应未知。
- 把项目事实、使用工具和个人贡献分开。没有贡献来源时不替本人认领。

这些约束使项目可以展示真实工程深度，而不依赖扩大结论。答辩遇到限制，应说明它如何影响决策和下一步条件，无需将每个缺口包装为优势。
