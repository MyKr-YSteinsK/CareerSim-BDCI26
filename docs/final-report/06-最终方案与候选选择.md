## 2. 选择理由的准确含义

Main 使用的决策标签是 `HIGHEST_OBSERVED_MATURE_THREE_SKILL_CEILING`。它表达的是：在当前记录所覆盖的成熟三 Skill 候选中，选择观察到的高位方案并精确冻结其身份。标签不是全部历史最高分、统计胜出、因果优势、全球最优或对未来上限的保证。

exact v6 的唯一完整样本是 75.29 quantitative、52.70 competition partial、48 个月、A、L6。样本具有可复核的 Candidate 身份与完整运行轨迹，但运行审计为 `RUNTIME_ADHERENCE_FAIL`。因此最终选择同时考虑了成绩、身份明确性、轨迹可审计程度和包可复核性；它没有把运行缺陷藏在结果后面，也没有把一个数字当成全部决策依据。

## 4. 为什么不是直接选 v1 的峰值

若目标只有“挑出历史上显示过的最高数字”，v1 的 76.04 会排在 v6 之前。但最终提交要求确定所交文件来自哪个 Candidate、Skill 内容是什么、包成员与 hash 是否吻合，以及运行证据是否足够支撑解释。v1 的 76.04 不能代表第二局 35.31；Tier-B 摘要也无法重建其完整工具顺序。Main 因此没有把单次峰值当成冻结身份优先级。

反过来，这不等于证明 v6 在策略效果上优于 v1。缺少同条件重复、单变量机制比较和完整的 v1 raw 轨迹时，正确结论是最终选择是一项受证据质量约束的工程决策，而不是一项统计结论。v6 自身的运行遵循缺陷也作为冻结材料的一部分公开保留。

## 5. 为什么当前 checkout 不等于最终包

最终包绑定到 source commit `1114a04b75548cf52f030d123564e527060fc061` 和三份具体 Skill blob。之后 checkout 的工程路线增加了 `delivery-progress`，进入历史 v8a 四 Skill 状态。再新的目录内容只说明仓库此刻有什么，不能自动证明它属于旧 ZIP。构建 commit `113052a9a8943efc7fb2d7d1140f126e62e92040`、manifest、逐文件 hash 和 ZIP hash 分别回答不同的 provenance 问题。

项目将“源身份”“本地 Candidate”“构建快照”“最终 ZIP”分开记录，避免后来修订的 Skill 被误认为早期冻结包成员。若未来要发新包，应产生新的、可比较的身份记录，不能覆写旧包事实或悄悄把当前 main 当成已提交内容。[最终身份记录](../project/FINAL_SUBMISSION_IDENTITY.json) · [manifest](../project/FINAL_SUBMISSION_MANIFEST.md)

## 6. 这个选择支持什么、不支持什么

可以支持：项目冻结了一个来源与包哈希明确的 Agent 提交材料；该 Candidate 有一条 48 个月完整 Dev 样本；工程审计保存了这条轨迹的正向机制观察与运行缺陷；Main 在现有证据边界下接受了 exact v6。

不能支持：exact v6 稳定达到 75+ 或 80+；分数由某个 Skill 导致；v6 在统计上优于 v1 或 v8a；隐藏 Test 可迁移；比赛已上传、已受理或已评测；获得奖项或名次；Team/Swarm 或 durable Memory 已被证明无效。官方平台结果、隐藏评测与重复分布保持 UNKNOWN。
