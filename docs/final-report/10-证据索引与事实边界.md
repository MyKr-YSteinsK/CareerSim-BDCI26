# 10｜证据索引与事实边界

本篇是人读报告的核验入口，不复制完整 Run ledger，也不替代逐项工程记录。若摘要与权威来源冲突，按事实所属领域回到官方合同、最终身份、具体运行记录或 Main 接受的证据台账核对；不要用本文重新定义历史状态。

## 1. 证据层级与适用范围

工程证据不是单一的全局排名。以下层次按问题分工；具体冲突时要优先选择对该问题有权威性的来源：

| 层次 | 主要回答的问题 | 使用规则 |
|---|---|---|
| 官方合同与来源锁 | 比赛名称、公开 Dev/保密 Test、Runner 接口、提交格式和官方评测条款是什么？ | 用 `OFFICIAL_SOURCE_LOCK.md` 中注明来源和核验日期的证据；门户不可读、日期过期或合同变化时保留 UNKNOWN 并重新核验。 |
| 最终身份与 manifest | 冻结包对应哪个 Candidate、source、Skill 字节和 ZIP 成员？ | 用最终 identity JSON、manifest 和 freeze audit；不从当前 checkout 推断旧 ZIP。 |
| Canonical project synthesis | Main 接受了什么决策、哪些结论被汇总、保留边界是什么？ | 用 FINAL/PROJECT/ARCHITECTURE/EXPERIMENT_RETROSPECTIVE 和 evidence review 定位，精确运行细节仍回到 run/review 原件。 |
| Canonical run / review | 某次游戏实际发生什么、采用什么 Candidate、回执与观察如何？ | 以该 run、review 的身份、时间窗、记录提交和保留状态为准；摘要不替代 raw。 |
| 历史 provenance | 已从当前树移走的历史文件原来在哪个 commit，是否仍可追溯？ | 用记录里的原始 commit 和路径；文件仍在 Git 历史不代表其 raw hold 已解除。 |
| 人读解释层 | 怎样对非仓库读者解释工程证据？ | `docs/final-report/00–10` 只作导航和解释；不能覆盖上述权威事实或把解释升格为测量值。 |

“官方合同”只对官方来源核验时点及其明确范围负责；`FINAL_SUBMISSION_IDENTITY.json` 对包身份权威，但不能说明平台是否收件；一个 run record 对该次运行权威，但不能说明稳定分布。权威性是按问题确定的，不能把任何一份综合文档提升成所有事实的唯一来源。

## 3. 读者使用的证据状态

- **已确认事实：**身份、文件 hash、提交材料、官方来源快照等有直接权威记录可核对的内容。事实仍有适用范围和记录时间。
- **实测单局：**某个 Candidate、Run、环境下实际观察到的分数、月份、动作回执和状态。它是真实测量，但范围只到该次运行。
- **有证据支持的解释：**多份记录支持的工程归纳，例如“某条路径停在部署门”；要写清支持来源及它没有覆盖的后续阶段。
- **假设：**准备通过未来实验区分的机制或因果解释；不得写成“研究发现”或“模型已经学会”。
- **未知：**来源缺失、不可恢复、未授权执行、未部署或没有可比较运行时的状态。使用 UNKNOWN 比补猜更准确。

四个常见边界要始终保留：

1. single-run score 不等于稳定表现或成绩分布；
2. 轨迹相关/先后关系不等于某项 Skill 或动作的因果增益；
3. 静态合同、安装与加载通过不等于模型在运行时遵循；
4. 本地公开 Dev 不等于官方保密 Test，冻结 ZIP 也不等于官方已收到。

## 4. 关键非结论

以下说法目前没有足够证据，不能写成项目成果：

- exact v6 稳定 75+，或稳定达到 80+；
- 某个 Skill 使分数提升固定分值或百分比；
- v6 因果上优于 v1、v6d、v8a 或其他 Candidate；
- v6 是全历史最高分、统计赢家或全局最优方案；
- 公开 Dev 结果已经验证 hidden-test transfer；
- 75.29 是官方平台得分，或官方包已经上传/受理/评测；
- 团队进入 TOP5、获得奖项；
- Team/Swarm 不可行或性能较差；
- 这条自动 Memory anchor 失败证明 Memory 普遍无效；
- Reviewer 路径未注册证明独立审核没有价值；
- Skill 文件、静态校验或 helper 通过就证明端到端运行有效；
- 哈希和摘要足以替代仍在 FORENSIC_HOLD 下的唯一 raw 来源。

## 6. Display-ID 怎么使用

`FINAL_ID_MAP.md` 的编号是面向展示的稳定导航标签：`CAND-####` 指 Candidate，`RUN-####` 指 Run，`EXP-####` 指 Experiment 或 research result，`SUB-####` 指提交工件；主索引还定义了重大决策用的 `DEC-####`。Display-ID 不替代原 Stage/Task、Candidate ID、Run ID、commit、文件名或 hold，也不代表质量排名。

本项目较重要的映射包括：

| Display-ID | 指向 | 引用时的补充说明 |
|---|---|---|
| `CAND-0001` | exact-v6 Candidate | 同时写出完整 Candidate ID 和 source commit。 |
| `RUN-0001` | S06-24 exact-v6 Run #1 | 附 75.29 / 52.70 / 48m / A / L6 与 `RUNTIME_ADHERENCE_FAIL`。 |
| `RUN-0003` | S01-03 no-op baseline | 用于说明项目起点，不称为策略增益对照。 |
| `RUN-0004` / `RUN-0002` | v8a sample #1 / #2 | 两局配对读，注明四 Skill Candidate 与不同结果。 |
| `RUN-0005` | v7q 自然提前终局 | M24、E/L1；不归因为某一个动作。 |

## 7. 以后引用项目的规则

写答辩稿、简历、README、作品集或技术博客时遵守以下规则：

1. 每个分数连同 Candidate、Run、评估字段、存活月份和样本数；v6 必须注明 Dev 与 adherence fail。
2. 官方规则和最终包身份分别引用官方来源锁与 identity/manifest，不以截图或二手文案代替。
3. 把观察与解释分开写；机制“在触发案例出现”不等于它造成了最终分数。
4. 报告负结果时说明停在哪道门，以及后续哪些阶段没有执行。
5. 写 v1 76.04 时同步承认它高于 v6，且该组 raw 不可用；写 v8a 时保留 72.65/59.00 两点与身份差异。
6. README 和面试只引用已公开安全的摘要；不要放 `.env`、内部绝对路径、私有 GitHub URL、凭据、原始日志或未发布工件。
7. 证据仍在 `FORENSIC_HOLD` 时不要公开 raw、宣布 hold 解除或把 hash 当成证据替身。
8. 新出现的上传回执、官方评测或重复运行应作为新事实登记，不回写成旧记录当时已知的状态。

人读层的职责是让读者更容易找到证据，而不是把边界变模糊。遇到来源不全时，链接到最接近的权威记录，写清尚缺什么，并保留 UNKNOWN。
