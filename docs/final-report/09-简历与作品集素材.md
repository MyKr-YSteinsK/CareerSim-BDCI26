# 09｜简历与作品集素材

本文把项目事实整理为可供个人材料作者筛选的素材，不替任何人认领仓库里的全部贡献。工程记录没有完整的个人分工台账；使用“设计、实现、审计、打包”等动词前，应先确认对应工作确由本人完成或参与。项目数字也必须保留 Candidate、Dev 和样本边界。

## 1. 项目定位

该项目可支持对下列工程主题的讨论，但**不自动证明求职者适合某个职位或级别**：

| 方向 | 可展示的项目材料 | 应同时说明的边界 |
|---|---|---|
| Agent / LLM Application | 长程决策闭环、Single Agent 与三个 Skill 的职责拆分 | 设计存在不等于每次运行正确遵循 |
| AI Engineering | Agent 与 MCP、CareerSim 模拟环境和 Runner 的连接与回执审计 | 本地工具链证据不等于云端或平台验证 |
| LLM Systems | Skill 发现/加载的分层、fresh observe、压缩后状态恢复审计 | v6 压缩后未重读 Skill，不能写“恢复完全解决” |
| Software Engineering | Candidate/source/manifest/ZIP 的身份绑定、离线校验、文档化交付 | 不把提交包说成线上生产系统 |
| Experimentation / Evaluation | 基线、不同候选轨迹、负结果和因果边界的分类 | 少量运行不构成稳态分布或因果结论 |
| Data / Evidence Engineering | Run、Display-ID、hash、hold 与来源路径之间的索引 | 本机 raw 和私有证据不应直接公开 |

## 2. 一句话项目描述

以下是项目层面的描述草案；选用前按本人实际角色调整主语、动作和贡献范围。

- **Agent / LLM 版：**围绕 48 个月职场模拟构建长程 Agent 决策方案，以 Single Agent + 3 Skills 组织状态整理、滚动规划与候选风险审核，并对工具回执和行动后观察进行审计。
- **AI Engineering 版：**打通 Agent、MCP 工具请求、CareerSim 状态观察与本地 Runner 的证据链，区分材料校验、框架加载、真实调用和运行遵循。
- **Software Engineering 版：**为长程模拟项目建立 Candidate source、Skill 身份、构建提交、manifest、ZIP 哈希和运行记录之间的可核对交付链。
- **综合版：**参与长程 Agent 工程项目的架构梳理、有限实验和冻结交付复核；一条 exact-v6 Dev 完整样本为 75.29 / 48 个月，同时保留 `RUNTIME_ADHERENCE_FAIL` 和官方评测未知的边界。

如果简历空间有限，可删掉分数，优先保留工程动作和可审证据；若使用分数，必须同时写 exact v6、单条 Dev 完整样本与 adherence fail，不能让读者误以为官方评分。

## 3. 简历 Bullet 草案

以下三组均按“动作 + 技术对象 + 结果/证据”组织。它们描述项目工作，不代表仓库已验证每位成员的个人 ownership。只保留本人可以在面试中解释并由记录支持的条目。

### 极简 2–3 条版

- 将 48 个月职场模拟拆解为 observe、状态整理、滚动规划、候选风险复核、单动作提交和 fresh-observe 闭环，并冻结 Single Agent + 3 Skills 责任边界。
- 对 Agent 工程按静态材料、Skill 装载、真实情境、动作回执和运行遵循分层核验，保留 exact v6 203 次动作尝试及 202 次成功状态改变后的观察配对记录。
- 绑定最终 Candidate source、manifest、七个包成员和 ZIP SHA-256，完成冻结范围内的本地离线材料核验；官方上传与平台评测未执行。

### 技术 4–6 条版

- 整理同一游戏 session 的公开状态、来源和 freshness 约束，要求状态改变后重新观察，避免基于过期状态连续提交动作。
- 将策略 Planning 设为唯一 owner，让 Risk Review 限定于当前合法候选的直接重大公开后果，减少职责冲突并保留单一动作提交者。
- 按包格式、静态合同、安装、运行时发现、Skill 加载、游戏触发和行动后状态逐层分类验证结果，避免把文件通过写成行为收益。
- 审计 exact v6 的 203 次 `take_action` 尝试：202 次成功状态改变后均观察到新状态；同时记录被拒绝请求、半年标记缺漏和压缩恢复遵循缺陷。
- 将 75.29 / 52.70 / 48 个月 / A / L6 绑定为一条 exact-v6 Dev 样本，并显式保留 `RUNTIME_ADHERENCE_FAIL`，不据此声称稳定或因果提升。
- 用 source commit、Skill blob、manifest、build commit 和 ZIP hash 分离表示运行来源与交付工件身份。

### 实验 / Research Engineering 版

- 将高成本游戏实验拆为身份冻结、问题定义、运行条件、可比较结果变量、停止条件与证据保留，降低无决策价值的重复运行。
- 汇总 13 个运行、82 个已完成观察窗口与 28 组匹配样本的策略挖掘结果，限定为描述性信号并保留状态、暴露和延迟结果混杂。
- 复核 Replay controller 的 24 个案例（1 次状态级修正、8 个 UNKNOWN）和 Simulator policy search 的可行性门，区分信号不足与未完成策略比较。
- 归档 v1 与 v8a 的不同轨迹，用以反驳“单局高分即稳定”推断；不将版本间结果转换成因果效应。
- 把 Reviewer、自动 Memory anchor、deterministic helper、Team/Swarm 的结论限定在各自实际部署或测试范围。

### 个人贡献的核对方法

这些 Bullet 中的工程行为有项目记录，但日志、commit 或报告本身不一定能证明是谁写了每一项内容。准备投递前按个人可解释的代码、文档、审阅和决策工作删改；没有证据支持“独立主导”“全栈负责”“从零开发”时不要使用这些表述。可以如实写“参与”或“协作”，也可以只写本人负责并能展示的子项。

## 4. 数字怎么用

| 指标 | 可否上简历 | 推荐写法 | 禁止写法 |
|---|---|---|---|
| 26.95 / 18.86 / 19m / E / L3 baseline | 通常不需要；作为工程对照背景时可用 | “公开 Dev 的 no-op 起点，19 个月自然终局；不是后续增益的因果对照” | “把成绩从 26.95 提升到 75.29” |
| exact v6 的 75.29 / 52.70 | 可谨慎使用，必须标注一条 Dev 样本及 adherence fail | “exact v6 单条完整 Dev 样本 quantitative 75.29、partial 52.70，运行遵循审计失败” | “官方评分 75.29”“稳定 75.29” |
| 48 个月 | 可用于描述该条运行时程 | “一条 exact-v6 轨迹完成 48 个月” | “证明系统稳定生存 48 个月” |
| A / L6 | 不宜单独堆叠；只能随具体 Run 身份使用 | “同一条 exact-v6 48 个月样本达到 A / L6” | “比赛等级 A”“多次 L6” |
| 202 次成功状态改变 + fresh observe | 技术简历可用，但应附总尝试 203 与其他缺陷 | “202 次成功状态改变动作之后均有 fresh observe；整局仍为 adherence fail” | “203 次动作 100% 成功”“运行完全正确” |
| 20 个导出 session payload | 不适合公开简历数字；这是本机 evidence hold 与退役治理事实 | 通常不写具体数量；如讨论证据治理，只描述经过授权的去敏保留和校验流程 | 声称拥有公开数据集、上传原始日志或暗示 hold 已解除 |
| 最终 ZIP SHA / exact identity | 适合技术作品集元数据，不是简历核心指标 | 在获准公开的页面说明如何核验工件身份，并给出必要的短 hash 或公开链接 | 把 hash 当作模型质量、平台验收或在线部署证明 |

简历最有价值的数字应能帮助读者理解工程工作。若一个数值只有在展开多个内部缩写后才能理解，通常把它留在作品集的证据页更好。

## 5. STAR 面试故事

以下五个故事以项目记录组织，没有替个人确定角色。回答时用本人真实动作替换“项目/团队做法”；如果不确定个人归属，就用项目口径讲事实，不认领未做的实现。

### 故事一：从 no-op 基线到长程架构

- **Situation：**S01 no-op 在 M19 结束，给出 26.95 / 18.86 / E / L3；它证明闭环可跑，但暴露长期生存与状态决策是后续问题。
- **Task：**需要把“长程策略”拆成可以由公开输入驱动、又能在运行日志中审阅的职责。
- **Action：**项目逐步形成事实整理、唯一 Planning owner、候选级 Risk gate 与唯一动作提交者，并把动作后的 fresh observe 写进循环。
- **Result：**最终冻结 Single Agent + 3 Skills；有一条完整 v6 轨迹和明确架构来源。
- **What I learned：**先从可观察的失败形式提出假设，再增加职责，避免因分数变化就随意加组件。
- **Evidence boundary：**S01 与 v6 环境和方案不同，不能说这一路线造成了成绩提升。[S01 运行](../project/RUN_HISTORY.md) · [架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md)

### 故事二：从 Risk-only 假设扩展到 Planning

- **Situation：**公开风险时间线促成了 Risk Review 假设，但 S03-02 的 smoke 工具路径不匹配，没有形成 CareerSim 行为证据；后续轨迹还显示状态与反馈会持续变化。
- **Task：**判断问题是否只在候选风险检查，还是也涉及事实陈旧、目标漂移和长时程规划。
- **Action：**S06 架构审查将 Board、唯一 Planning owner、候选专属 Risk 和 Single Agent 动作权分开。
- **Result：**形成职责清楚的三 Skill 冻结架构；架构被 Main 接受，策略因果收益没有被宣称。
- **What I learned：**一个工具通过安装和加载，并不足以证明目标策略有效；架构扩展要对应更清楚的问题。
- **Evidence boundary：**S03 smoke 未进入真实游戏链，S06 设计验收也不等于每局遵循成功。[研发演进报告](03-完整研发流程与方案演进.md) · [S06 closeout](../project/S06_CLOSEOUT.md)

### 故事三：高分样本同时触发 adherence fail

- **Situation：**exact v6 走满 48 个月，得到 75.29 / 52.70 / A / L6。
- **Task：**审计分数背后的运行过程，避免用终局结果覆盖执行缺陷。
- **Action：**逐项复核动作请求、观察配对、半年标记、普通 Story 讨论和压缩后的 Skill 重读。
- **Result：**确认 202 次成功状态改变后都有 fresh observe，同时记录一次 Energy 参数被拒、H 标记遗漏、重复讨论、CTRL 配对不可认证和两次压缩后的重读缺失；结论为 `RUNTIME_ADHERENCE_FAIL`。
- **What I learned：**成绩、工具正确性、规则遵循和策略效果必须分别汇报。
- **Evidence boundary：**这是一次完整轨迹审计，不估计缺陷频率或 Skill 的分数贡献。[v6 run record](../project/runs/v6-run1-validation.md)

### 故事四：同一 Candidate 的结果差异

- **Situation：**v8a 四 Skill Candidate 两条完整轨迹为 72.65 和 59.00。
- **Task：**说明同一身份下结果变化时，哪些结论仍可信。
- **Action：**把两条运行作为同一候选样本对呈现，并保留轨迹差异、运行遵循问题和证据持有状态。
- **Result：**项目可以说“观察到了分数不同的两条完整轨迹”，但不说由第四 Skill 导致差异或这两点就是稳定分布。
- **What I learned：**重复观测是讨论变化的起点，不是自动控制了所有混杂因素。
- **Evidence boundary：**只有两局，且不同于 exact v6；不用于架构因果比较。[v8a sample 1](../project/runs/v8a-full-horizon-sample1.md) · [sample 2](../project/runs/v8a-full-horizon-sample2.md)

### 故事五：负结果如何帮助止损

- **Situation：**项目探索 Reviewer、自动 Memory、helper、Replay controller 和策略搜索，路线各自遇到不同门槛。
- **Task：**避免把尚未部署或尚未比较的方案继续包装成已验证 Candidate。
- **Action：**保留安全部署、自动锚点、工具层、逻辑信号和模拟器可行性各自的实际检查结果，按测试范围给出停止结论。
- **Result：**Replay controller 保持弱信号；Simulator search 在基线完成率门停止；Team/Swarm 仍未测试，没有新路线被混入最终 ZIP。
- **What I learned：**写清“停在哪道门”能减少重复成本，也避免把未运行写成运行失败。
- **Evidence boundary：**负结果限制各自被测路径，不证明整类技术不可行。[实验复盘](../project/EXPERIMENT_RETROSPECTIVE.md) · [最终证据审阅](../project/FINAL_EVIDENCE_REVIEW.md)

## 6. 面试技术展开方向

| 方向 | 可以展开的技术问题 | 推荐收束点 |
|---|---|---|
| Agent | Skills 如何分工、为什么只有一个动作提交者、长程反馈如何重置目标 | 规则合同与运行遵循分别举证 |
| Systems | MCP 请求、回执、fresh observe、context compression、Runner 与包身份 | 工具副作用和运行状态要可观察 |
| Experimentation | 单局、重复样本、控制变量、终局类别、负结果门槛 | 不把描述性观察写成因果估计 |
| Engineering | source/manifest/hash、离线校验、README 人读层、FORENSIC_HOLD | 身份、发布状态和证据保留不能混为一谈 |

追问时先给事实，再说明它支持什么，再画清推论停止点。若面试官问个人贡献，明确哪些部分由本人完成、协作或仅在报告里审阅；项目成果不能自动替代个人贡献说明。

## 7. 作品集页面结构

建议按读者问题安排页面，而不是按 commit 日期堆截图：

1. **Hero：**一行项目定位，标注公开 Dev 工程项目，避免放奖项/排名徽章。
2. **Problem：**说明 48 个月状态变化、风险约束和反馈窗口。
3. **Architecture：**用一张公开安全的 Single Agent + 3 Skills 图表示职责与禁止权限。
4. **Agent loop：**展示 observe 到 action 后复观察的循环，并标注请求与回执边界。
5. **Experiments：**用验证阶梯表区分静态、装载、真实情境、运行遵循和策略收益。
6. **Failures：**用分类表比较技术中断、自然终局、adherence fail、部署门和可行性门。
7. **Final solution：**展示 exact v6 与不同候选的有界比较，不做简单排行榜。
8. **Engineering：**说明 source、manifest、build commit、ZIP hash 如何绑定。
9. **Evidence：**给出可公开的来源链接和去敏指标，并用事实/解释/未知标签。
10. **Limitations：**明确单样本、隐藏 Test 未评、官方上传未执行、Team/Swarm 未测。

可复用的材料包括责任分工表、证据层级表、候选身份与边界表、失败分类表、action-loop 图。后续画图时可重新绘制公开流程图，不要把本机 runtime 路径、私有运行截图或原始会话直接嵌入页面。

## 8. 公开与隐私边界

默认不公开 `.env`、密钥、API token、local raw logs、共享数据库、session payload、未扫描的工具输出、本机绝对路径、私有 GitHub URL、私有工件链接和未发布评测材料。也不要因为报告中出现某个数字，就把支撑它的 held raw 一并上传。

公开作品集只使用经确认可公开的架构说明、方法摘要、去敏指标、自己重绘的安全图示和明确的结果边界。分享仓库、日志或 ZIP 前先确认可见范围、密钥扫描与证据保留责任；哈希不是隐私保护，也不是原始来源替代品。

## 9. 禁用求职表述

除非未来有新的官方或受控证据，不要写：

- BDCI TOP5、award winner、获得赛事奖项；
- official score、平台已接收、云端评测通过；
- stable 75+、stable 80+、稳定 A / L6；
- hidden-test validated、隐藏集泛化已经验证；
- production-grade、已在线生产部署；
- “Skill X causally improved score by Y%”；
- “三 Skill 比四 Skill 好”或“多 Agent 不适合该题”；
- “Memory 已被证明无效”或“Reviewer 没有价值”；
- “本人独立完成整个项目”，除非个人贡献证据确实支持。

可用的替换句是：“项目冻结了一份身份可核对的 exact-v6 本地提交包；一条公开 Dev 完整样本记录为 75.29，同时存在运行遵循缺陷；官方上传、平台结果和隐藏集迁移未知。”
