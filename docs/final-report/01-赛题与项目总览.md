# 01｜赛题与项目总览

## 1. 赛题是什么

CareerSim BDCI26 对应 2026 CCF BDCI「华为 openJiuwen Agent 职场长程生存与晋升挑战」。参赛者要构建 Agent（智能体），通过 JiuwenSwarm 与 CareerSim 提供的 career-emulator MCP 交互，在一个模拟职场里连续行动，目标是在最长 48 个月的职业历程中生存、成长并应对绩效、晋升和风险。

它不是一轮问答题。Agent 每次决定都会面对当前状态与合法选项，环境执行后又生成新状态。早期的行动会改变之后可见的资源、反馈和机会；风险也可能在数月内逐步显现。项目开发使用公开 Dev 环境，正式评测使用的保密 Test 与本地 Dev 不是同一证据来源。本地跑完一局不能代替隐藏集评测。

赛事交付是一份符合格式要求的 Agent solution 压缩包，其中包括 manifest、说明材料和 Skill 文件。包的结构与本地校验结果可以证明工程材料符合指定格式；它们不证明比赛平台已接收或评价该作品。[官方来源与比赛合同](../project/OFFICIAL_SOURCE_LOCK.md) · [比赛身份记录](../project/COMPETITION_IDENTITY.json)

在项目工作流里，公开 Dev 用来开发和检查 Agent 行为；保密 Test 是另一套正式评测数据。Dev 与 Test 的具体轨迹不能互相替代，平台的策略工程、资源效率与云端运行结论也不能从一个本地分数推导出来。项目冻结时赛事门户没有提供可读的最新通知，上传窗口被记录为未知，所以“准备好 ZIP”与“提交已完成”始终分开表述。

题目中的“长程”不是单纯把回合数量拉长。它让几个判断互相影响：短期健康和信任风险可能影响能否继续；技能、输出和人脉等成长需要时间积累；绩效和晋升结果又会改变下阶段机会。Agent 必须重复运行决策闭环，并在新反馈出现时改计划。它既不是一次性生成完整职业路径，也不是只追逐一个静态分数。

## 2. 为什么它不像普通聊天机器人

普通问答常见的过程是“收到问题 → 给出回答”。CareerSim 则要求一个持续闭环：

    读取当前公开状态
          ↓
    判断目标与可行动作
          ↓
    提交一个动作
          ↓
    环境处理该动作并更新职业状态
          ↓
    重新读取状态和反馈
          ↓
    进入下一次决策

如果 Agent 在一次状态改变后继续使用旧观察，它可能基于已经过期的 Health、绩效或晋升信息作出下一项决定。即使最终走满 48 个月，也要另外检查动作格式、工具回执、观察顺序和上下文恢复是否正确。

## 3. 关键对象

| 名称 | 面向读者的解释 |
|---|---|
| CareerSim | 提供职场情境、合法选择和状态变化的模拟环境。Agent 在当前局里工作；环境负责实际更新状态并返回可观察结果。 |
| Agent（智能体） | 负责理解状态、选择方案并发起工具调用的模型驱动程序。最终方案只保留一个 Agent 作为动作提交者。 |
| Skill（技能模块） | 给 Agent 的一组职责和操作规则。它们帮助整理事实、规划目标或检查候选风险，不是独立游戏角色，也不直接改变 CareerSim。 |
| JiuwenSwarm | 运行 Agent 与 Skill 的框架。框架能启动模型流程和工具接口，但“文件存在”不等于内容一定进入当前模型上下文或被正确遵循。 |
| MCP（Model Context Protocol，模型上下文协议） | Agent 与外部工具交换请求和结果的接口协议。本项目通过 career-emulator MCP 观察模拟状态并提交合法动作。 |
| career-emulator | CareerSim 的模拟服务接口，把 observe、行动请求和游戏状态连接起来。它返回的状态和回执是判断行动结果的依据。 |
| Runner（运行器） | 官方仓库提供的执行与提交校验工具，负责准备 Agent 提交物、发起本地运行并记录结果。Runner 自身不是最终提交的策略。 |
| submission solution | 按官方目录与 manifest 规则打包的交付物。当前冻结 ZIP 与仓库现有 Candidate 配置是不同工件，身份要通过 source commit、Skill 摘要与 manifest 逐项核对。 |

这里还要区分“框架”和“模拟器”。JiuwenSwarm 负责把 Agent、Skill 与工具执行接起来；CareerSim 负责模拟职业状态、返回事件和执行被接受的动作。MCP 是它们之间的工具通信协议，不是一个额外的决策模型。Runner 则把本地运行和提交包检查组织成可重复调用的入口。把这些概念分开，才不会把框架正常启动误读为游戏行动成功。

工具调用链可概括为：

    模型推理 → Agent 形成工具请求 → MCP → CareerSim 处理 → Agent 读取回执与新状态

模型在文字里说“我选择了某项行动”，不等于模拟器已经执行成功；只有工具回执及其后的新观察才能说明环境中发生了什么。

## 4. 一局游戏通常怎样进行

玩家以月份推进。开始时先观察当前职业属性、月度情境和可行动作。故事事件可能要求处理沟通、交付、合规、健康或协作问题；情境描述是可用于当下判断的公开信息，不是通往固定答案的题目编号。

在季度行动窗口，Agent 还要安排 Energy（精力）相关行动和 Main（主行动）。这两类选择可能改变不同状态维度，因此不能把固定搭配当成通用最优配方。一次行动改变状态后，Agent 应重新观察，再决定下一项行动。

大约每半年会出现绩效反馈和晋升观察窗口。新的等级、正式反馈或未晋升结果会改变规划的起点；Agent 需要重新判断仍可实现的目标，而不是机械延续上一阶段计划。CareerSim 还可能因为生存或职业风险提前结束模拟；如果到达 48 个月，则是一条完整时程观测。本文不提供任何隐藏阈值或未公开的晋升公式。

| 决策时点 | Agent 要做什么 | 后续要确认什么 |
|---|---|---|
| 新月份或故事事件 | 观察当前状态、情境和合法选项，按公开事实判断当下目标 | 工具是否接受了所选选项，事件处理后状态是否变化 |
| 季度 Energy / Main 窗口 | 联合考虑精力行动与主行动，不照搬过去的固定搭配 | 每项状态改变后先取得新观察，再决定下一项 |
| 半年反馈或晋升窗口 | 读取实际公开结果，重新判断主要缺口和剩余路径 | 是否晋升、当前等级和正式反馈是否改变了规划基线 |
| 终局或 48 个月结束 | 保存最终状态、分数和运行记录 | 本局属于自然终局、有效完成还是技术中断 |

表格描述的是便于理解的决策结构，不表示每个月一定含有所有这些环节。合法选项随具体情境变化；较早的行动也可能改变后续状态，所以不能从一张静态流程图推断某个候选一定可用。

对第一次看运行报告的人，可以把一局拆成“环境给出输入、Agent 作出选择、工具返回结果、环境公开新状态”四段。若只保留 Agent 的解释，就缺少请求是否被接受的证据；若只保留最终分数，就缺少中间过程和失败类型。项目记录季度 Energy、主行动、事件和半年反馈时，关注的不是把每个动作都变成复杂日志，而是让关键决策能够与当时状态及后续观察对应起来。这样可以复查它是否基于当时可见信息做决定，也可以区分路线选择问题和执行问题。

## 5. 怎样理解成绩

项目运行记录并列保存几种不同结果：

- quantitative score：本地运行报告中的量化分数。
- competition partial score：运行报告中的竞赛部分分数；不应自动等同官方最终评测成绩。
- survival months：本局存活月份。
- grade 与 Level：该局结果里的等级和职业级别。

这些指标描述不同方面。完成 48 个月不代表运行契约完全遵循；A 级也不证明对其他随机轨迹有相同结果。项目把 Dev 分数、运行正确性、策略效果和官方平台评测分开记录。

阅读分数时，最稳妥的说法是把数字和身份放在一起，例如“exact v6 的一条完整样本是 75.29 / 52.70 / 48 个月 / A / L6”。如果只说“项目得分 75.29”，容易让人误以为当前 checkout、所有 Candidate 或官方平台都得到同一个成绩。等级和 Level 也不能替代 survival months；反过来，走满时程也不能代替量化分数。

## 6. 我们最终做了什么

最终提交物绑定到 Candidate candidate-v6-auditable-control-loop，架构是 Single Agent + 3 Skills：

1. structured-state-board 整理本局刚刚观察到的公开事实、来源和新鲜度。
2. rolling-planning 根据公开目标缺口、可比进展和剩余机会窗口提出有限候选；它是唯一的策略规划负责人。
3. risk-review 检查已经提出的候选是否带有与当前情境直接相关的重大公开风险。

Agent 仍是唯一的动作提交者。三个 Skills 分别提供事实整理、策略规划和候选风险复核，不是三个互相投票的 Agent。最终 ZIP 的身份见[提交记录](../project/FINAL_SUBMISSION_IDENTITY.json)和[方案审阅](../project/FINAL_SOLUTION_REVIEW.md)。

这套设计把“看见什么”“追求什么”和“某个候选有什么重大风险”拆成不同职责。它的优点是职责可以分别审阅，代价是仍须证明运行时确实载入和遵循这些规则。Skill 文档写得完整、Runner 校验通过或提交材料成功打包，都不能单独替代真实运行审计。

## 7. 最终结果与不能推出的结论

exact v6 只有一个被接受的完整样本：75.29 quantitative、52.70 competition partial、48 个月、A、L6。审计结论是运行契约遵循失败：样本中虽有 202 次成功状态改变动作后的新鲜观察，但同时出现一次被拒绝的 Energy 参数、漏掉的半年标记、缺乏新证据却反复重开的普通故事讨论，以及压缩后未重新读取 Skills。

因此项目没有把这次完整通关写成运行审计通过，也没有把 75.29 写成稳定成绩或因果收益。Candidate v1 的一个高分高于它；v8a 四 Skill 版是另外的 Candidate 和另外的运行样本。最终 ZIP 已在本地按固定身份校验，但官方上传未执行，隐藏 Test 的成绩未知。

最终包的来源提交、精确 Skill 名称、manifest 和 ZIP 哈希都有单独记录。与此同时，当前仓库检出的配置和四个 Skill 属于历史 v8a 工程状态。读者若要了解最终提交，应看冻结身份和打包 manifest；不应仅从当前的 skills/ 目录推断包内成员。这种区分也解释了为什么本报告同时介绍三 Skill 最终方案和四 Skill 历史路线。

在对外介绍时，建议按“对象—证据—边界”组织一句话：说明说的是哪个 Candidate 和 ZIP；给出它实际运行或离线检查的记录；再说明哪些事情没有验证。比如，完整说法是“冻结包绑定 exact v6，离线材料校验通过；一条 Dev 完整样本得到上述结果，但运行遵循审计失败，官方上传和隐藏 Test 评测未知”。这种表述比单独报最高数字更长，却能让听众准确判断结果代表什么。
