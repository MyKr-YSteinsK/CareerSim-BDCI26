# 02｜Agent 技术方案与系统架构

## 1. 真正要解决的问题

一个 48 个月的模拟并不只是挑选“看起来收益最大”的行动。Agent 必须把当前公开事实与行动后的变化接起来，同时控制以下几类工程问题：

- **长期状态漂移：**Health、Dignity、Network、Wealth、Skill、Output、Level 会随时间变化。旧观察不能代表当前状态。
- **上下文压缩：**模型上下文可能被压缩。如果恢复后没有重新读取当前局状态和关键规则，Agent 可能记错目标或套用过时计划。
- **目标变化：**一次正式绩效反馈、晋升或未晋升都会改变策略起点。保持长期目标不变，和盲目照抄上一阶段路线，是两回事。
- **生存与成长的权衡：**过度保守可能放弃仍可实现的成长；只看成长也可能忽略公开的重大生存警告。
- **陈旧或不可归因的信息：**动作之后发生了状态变化，并不总能证明变化由该动作造成。中间事件、额外动作或过期状态会污染比较。
- **动作是否真正执行：**模型的自然语言意图、工具调用、模拟器接受的动作和最后状态变化属于不同证据层次。
- **过拟合和职责冲突：**Dev 轨迹可能诱发对隐藏规则的猜测；多个规划者或审核者也可能对目标、状态和动作权限产生冲突。

这些问题不属于同一个层次。目标选择是否明智是策略问题；请求是否被模拟器接受是工具正确性问题；当前结论是否来自 fresh observe 是证据新鲜度问题；多个组件都能提交动作则是权限问题。若不先区分，分数下降、提前终止、工具错误和未加载 Skill 都可能被笼统地归为“Agent 策略不好”，从而导致错误修复。

最终方案把判断拆给三个 Skill（技能模块），同时让 Single Agent 保持唯一动作提交权。这样做的目标是让职责和证据关系容易核对；它并不证明设计在每一局里都能被模型正确执行。

## 2. 总体架构

冻结提交物是 Single Agent + 3 Skills。当前 main checkout 有历史 v8a 的第四个 Skill，但它不是 final-v6 ZIP 的身份来源。

    CareerSim
         ↑↓ MCP
    Single Agent（唯一动作提交者）
      ├── structured-state-board：公开事实与新鲜度
      ├── rolling-planning：唯一策略规划负责人
      └── risk-review：当前候选的重大风险门

Agent 读取 fresh observe（新鲜观察），整理状态，形成当前合法候选，再由 Risk Control（风险控制）检查候选的直接重大后果。Agent 根据检查结果提交至多一个动作。模拟器返回回执和新状态后，流程再从观察开始。

读者也要把这个冻结身份与当前仓库分开看。当前 main 保留历史 v8a 的第四 Skill；最终 ZIP 则绑定到更早的 exact-v6 source commit 和三个固定 Skill blob。当前源码更靠后，并不意味着它自动取代了用户冻结的包。

三个 Skill 是同一 Agent 决策过程中的职责说明，不是三个独立的玩家、三个投票席位或三个动作发送器。准确身份和 Skill 文件 Git 对象见[最终提交身份](../project/FINAL_SUBMISSION_IDENTITY.json)；最终方案的解释见[架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md)。

## 3. Agent Loop（智能体循环）

设计中的一个决策循环包含八步：

1. **observe：**从当前 game session 取得最新公开状态，确认月份、公开反馈、当前合法选择和来源。
2. **Board：**structured-state-board 提取变化、稳定事实和未知项，不复述整段历史，也不从相邻事件猜因果。
3. **Planning：**rolling-planning 设定一个有公开依据的 Primary Gap（当前主要缺口），判断进展状态、公开生存预算和剩余可实现窗口。
4. **候选生成：**Agent 按当前状态比较合法候选。Energy 与 Main 需要共同考虑，不能把旧状态下的选择顺序照搬到动作后。
5. **Risk gate：**risk-review 对已经形成的候选及其直接相关公开后果做有界审核。
6. **take_action：**Single Agent 选择并提交一个合法动作。Skill 本身不调用工具、不替 Agent 提交动作。
7. **fresh observe：**如果动作改变状态，取得新观察；拒绝、失败或不确定回执要按实际证据分别处理。
8. **刷新决策：**Board 用新观察更新事实；Planning 再决定下一项行动。前一项动作之前的扫描不作为下一项状态改变动作的依据。

fresh observe 是闭环的连接点：它让上一项动作后的环境状态重新成为下一项判断的输入。如果行动改变了状态却跳过重新观察，后续 Energy/Main 可能基于陈旧值连续提交。项目设计要求每次状态改变后重新观察；运行审计还必须逐次检查工具回执和观察配对，不能只看 Skill 文本里有这条规则。

举例来说，如果 Agent 提交 Energy 行动后 Health、Energy 或当季状态发生变化，原来候选列表里的主行动仍可能合法，但它所依据的资源和风险已经不同。下一步必须以新观察重新比较，而不是复用调用之前的计划。若工具明确拒绝请求且状态未变，可以记录拒绝并按当前状态重新决策；如果回执中断、超时或部分返回，就先观察并核对状态。没有核对之前，结果属于 UNKNOWN，不能靠重发同一请求来“确认”。

当回执拒绝请求时，系统不能把它当成成功动作继续规划；当调用超时或断连、结果不明时，也不能假设“肯定没执行”而盲目重发。正确解释需要把工具结果与随后可读到的游戏状态放在一起。这样既避免重复动作，也能让一次技术失败停留在它实际发生的边界内。

## 4. structured-state-board：先说明现在能确认什么

Board 只负责本局公开事实，不负责目标选择和风险结论。

| 项目 | 设计职责 | 常见失误 |
|---|---|---|
| 输入 | 同一 game session 的最新公开状态、月份、可见正式反馈、当前合法选项 | 混用不同局的数据或过期的摘要 |
| 输出 | 有来源和新鲜度的公开值、可比较变化、必要时的 UNKNOWN | 把推断写成环境事实 |
| 快照 | 新局、季度首次 Energy、观察到正式反馈/晋升、重大公开状态变化或上下文恢复时，建立有限状态快照 | 每次都抄整份状态，或因派生标签变化反复重建 |
| 近期效果 | 最多保留两条有清楚来源、且没有中间变化污染的 before/after | 把时间相邻当成动作因果 |
| 恢复 | 先确认同一 session，再取 fresh observe；确有必要时最多查看近期同局公开记录 | 用旧记忆覆盖新的环境状态 |

Health、Dignity、Network、Wealth、Level、Output 和 Skill 是可整理的公开字段。Board 标明“观察到什么”，Planning 才解释这些事实是否改变目标。缺字段、来源不清或前后不可比时，正确输出是 UNKNOWN，而不是用合理猜测填空。

Board 不负责建立跨局 durable Memory（持久记忆），也不读取数据库、隐藏字段或其他游戏会话。它是一个有边界的当前局事实板，不是策略模型。[最终方案审阅](../project/FINAL_SOLUTION_REVIEW.md) · [S06 closeout](../project/S06_CLOSEOUT.md)

一个典型的整理结果不是“我认为健康风险很高”，而是“同一局最近两次可比观察中 Health 下降，数据来自哪两个 public observe；是否存在中间事件；如果来源不完整，则标 UNKNOWN”。Board 保留的是可由下一位审阅者核对的事实输入，Planning 才决定这项变化是否构成当前生存约束。这个分离既减少把结论误记成事实，也避免 Board 为了方便而维护第二套策略状态。

因此，状态板更像带来源的工作便笺，而不是另一个仿真器。审阅时应能回答：这个数值何时观察、来自哪一局、是否为当期值、与哪个基线比较、中间是否有会改变解释的事件。字段缺失时保留空缺并不会降低记录质量；相反，它让后续策略解释知道哪些地方尚无依据。若把推断后的“风险升高”写进事实栏，之后的规划者就可能把它当成环境直接给出的警告，造成证据层级混淆。

## 5. rolling-planning：一个目标负责人

Planning（规划）是唯一的策略 owner。它在每次决策时根据新鲜公开事实回答四个问题：当前唯一主要缺口是什么、公开进展是否可见、现有生存约束是否收紧、剩余时间里哪些收益仍可实现。

- Primary Gap 可以是 Skill、Network、Output 或其他有公开反馈支撑的当前缺口；证据不足时标为 UNKNOWN。
- Progress 可描述为 ADVANCING、STALLED 或 UNKNOWN。只有同一目标、两个相邻且可比较的正式观察点都没有公开进展，才进入严格 STALLED；单次没有增长不够。
- Risk Budget（风险预算）是当前公开生存趋势形成的候选无关约束，可为 AVAILABLE、TIGHT 或 UNKNOWN。它不使用固定 Health 数字、隐藏计数或晋升阈值。
- Horizon（剩余窗口）帮助判断某条收益路径是否还有时间兑现，不使用固定月份硬切换策略。
- Energy 与 Main 联合比较；一项动作改变状态后，先重新观察，再决定下一项。

新局、当季首次 Energy、半年评审前最后行动窗口、实际观察到的反馈/晋升结果、严格停滞判断和上下文恢复，都是规划重新检查的触发点。相同窗口内多个触发可以合并，不能因为某个派生标签改变就不断递归打开完整复核。

观察到正式反馈或晋升后，旧进展比较应失效；规划需要从新事实建立基线。菜单上写着“会提升”只是候选说明，不能代替同局观察到的结果。规划的目标是适应公开证据，不是把某个历史动作固化成每季必选的赢家。

因此，规划可以在一个季度里先比较一个 Energy 选项和主行动的互补关系，但只要第一项实际改变了状态，第二项选择就要重新读取环境。半年正式反馈则是更明显的规划重置点：此时可以确认等级或绩效反馈变化，而不是从“过了六个月”推断一个没有看到的结果。这个方法把时间用于选择观察点，不把时间直接变成隐藏阈值。

Primary Gap 的价值在于让候选比较有共同问题，而不是把职业状态压成单一数字。例如公开反馈指出输出缺口时，可以比较仍有兑现窗口的交付或能力建设；若 Health 等公开状态持续恶化，生存约束可能收紧，候选就需要先满足继续参与的条件。报告没有规定在任何固定月份自动转向某个目标，因为现有公开材料不足以支持这样的硬编码。遇到多个同样重要但难以排序的缺口时，应记录取舍理由和未知，而不是假装系统找到了唯一正确的路线。

## 6. risk-review：检查具体候选，而不是接管目标

risk-review 只审核 Agent 已生成的当前合法候选，以及与该候选直接相关的新鲜公开事实。它不负责选 Primary Gap，不比较所有普通行动，不制定整体策略，也不提交动作。

结果可以是：

- **ALLOW：**没有发现要求改变当前候选的重大公开风险。
- **WARN：**存在值得说明的公开顾虑，但证据不足以要求替换候选；仍可提交。
- **RECONSIDER：**有明确重大后果和直接相关的合法替代方案，而当前候选没有处理该风险。此时只要求一次有界比较；候选改变后要重新审核。
- **UNKNOWN：**相关事实缺失、陈旧或来源不清。可以按正常流程补一次新观察；仍未知时保留未知，不循环猜测。

普通的小成本、日常关系摩擦或泛化的“项目/角色”词语不会自动触发否决。风险审核看的是候选在当前情境中会带来的公开重大后果，而不是风险词典是否命中。这样可以让安全约束影响真正相关的选项，同时不让 Risk 变成第二个 Planning。

四种结果也有不同后续动作：ALLOW 让既有候选继续走正常提交流程；WARN 需要保留顾虑，但不强迫更换选择；RECONSIDER 把比较限定在与该风险直接相关的替代候选；UNKNOWN 则要求补足一份必要的新鲜事实，或带着未知继续记录。它们不是对角色贴上的永久标签，也不是评估整个职业路线优劣的总分。审核输入过宽，Risk 就会越权规划；审核输入过窄，直接风险又可能被遗漏，因此复核范围必须跟候选和公开证据绑定。

例如，某个选项的普通时间成本不必单独盖过对当前公开目标有帮助的成长候选；但如果新的公开警告把 Health、合规、信任或可靠性后果明确绑定到该候选，Risk 可以要求有限复核。线索只是要求检查的信号，不等于风险结论，更不是某个事件标题的答案映射。最终是否换项仍由唯一的 Agent 作决定。

## 7. 为什么没有采用 Multi-Agent

职责拆分不等于增加 Agent。Board、Planning 和 Risk 是同一 Agent 决策流程里的功能边界；最终只允许 Single Agent 提交动作。

多 Agent 可能引入新的状态权威、动作权威、同步和工具隔离问题。现有证据没有建立一个必须用多个 Agent 才能解决的瓶颈，也没有完成 Team/Swarm 的部署或对照实验。因此它仍是 DEFERRED / NOT_TESTED：既没有被证明不可行，也不能声称它改善成绩。增加参与者本身不是改进证据。

单 Agent 选择也不是“多 Agent 一定不好”的结论。项目选择的是一种更容易确认权限归属的方案：所有功能模块读同一局公开证据，最终动作只有一个提交者。未来如果出现可重复的角色冲突或并行任务瓶颈，Team/Swarm 仍可重新评估，但需要先建立可隔离的角色、共享状态定义和唯一动作提交者，再决定是否做实验。

## 8. 为什么没有 durable Memory

当前方案的 Board 是当前 session 内的有限状态摘要；它会用新观察刷新事实，不把不同游戏混在一起。Planning 的目标与风险判断也以当前局公开输入为依据。这个边界可以降低跨局信息污染和过期事实冒充观察的风险。

后续对自动 MEMORY.md 锚点的可行性探查中，指定冻结运行路径没有把预期正文放进启动、更新和模拟压缩后的捕获；显式读取可用。因此记录的是那条自动锚点路径未达到部署要求，不是“所有记忆机制都无效”。其他记忆方案的策略收益、云端可用性和跨局隔离仍未验证。[实验复盘](../project/EXPERIMENT_RETROSPECTIVE.md)

这里的选择是有限状态，而不是“任何形式的记忆都不需要”。当前局最近两条有清晰来源的效果和最新正式反馈，仍可由 Board 在本局内保留；被明确拒绝的是没有确认隔离、生命周期和可部署性的跨局 durable Memory。长文本压缩摘要不是可靠数据库，也不能取代 fresh observe。

## 9. Context compression：压缩后的恢复属于正确性

模型上下文被压缩时，文字变短不代表必要事实和规则自动完整保留。恢复流程需要先确认仍是同一局，再取得 fresh observe，重新建立 Board 与 Planning 当前状态，并按最终合同重读相关 Skills。

恢复的目的不是重放全部对话，而是用最小的操作恢复当前决策所需事实：确认 session 身份、取得当前公开状态、按需读取同局近期记录、确认仍适用的 Skill 边界，再重建一个当前目标。如果这些信息无法恢复，标出未知比依赖压缩后的模糊印象更可靠。

exact v6 的唯一完整运行记录了两次 CurrentRoundCompressor 压缩。两次之后都没有重新读取三个 Skills，因此最终运行审计仍为 RUNTIME_ADHERENCE_FAIL。后来静态补充恢复约束，并不能把修订版的规则算到原 v6 包里，也不能反向证明模型会遵循恢复流程。上下文压缩与恢复应像工具调用顺序一样接受运行证据检查。[S06 closeout](../project/S06_CLOSEOUT.md) · [v6 运行记录](../project/runs/v6-run1-validation.md)

复核压缩恢复时，可以把检查拆成可观察的里程碑：压缩前是否已有可辨认的 session 身份；恢复后是否确实取得当前状态；所需 Skill 是否重新进入上下文；新一轮决策是否引用恢复后的公开事实。只读静态合同可以说明预期流程，但实际运行日志要另外显示这些步骤是否发生。若只有终局前后的零散文本，无法确认恢复顺序，就应将遵循状态记为未证或失败，而不是根据最终完成月份倒推全过程正确。

## 10. MCP 到实际动作：意图、请求、结果分层

一次实际动作至少要区分三个步骤：

1. 模型或 Agent 表达了准备采取什么行动。
2. Agent 通过 MCP 向 CareerSim 提交工具请求。
3. 模拟器接受或拒绝请求，并返回回执；成功后，新的 observe 显示状态是否发生变化。

第一步不是第二步，第二步也不能保证第三步成功。项目因而把 malformed 参数、技术失败、部分运行和自然终局分开记录。一个运行没有终局分数时，不能从前面一段轨迹推造最终分数；工具失败也不能改写成策略表现差。

## 11. 运行正确性与策略质量是两条轴

exact v6 的一次完整运行走满 48 个月，得到 75.29、52.70、A、L6；同时审计发现一次被模拟器拒绝的 Energy 多选参数、一个半年 H 标记遗漏、无新证据却反复重开的普通故事讨论，以及压缩后没有重读三个 Skill。202 次成功状态改变动作之后均有新观察，但这些通过项不足以抹去其他运行缺陷。

这说明“走完一局”和“严格遵循运行契约”是不同问题；“运行契约做对”和“策略因此提高分数”也不是同一命题。当前证据只支持一次完整样本及其具体审计结果，不支持稳定收益或因果结论。[冻结审计](../project/reviews/S10-23R_FINAL_SINGLE_SHOT_FREEZE.md) · [最终证据索引](../project/FINAL_EVIDENCE_REVIEW.md)

## 12. 历史 v8a 的第四个 Skill

历史 v8a 工程状态增加了 delivery-progress，用于追踪当前局的公开交付承诺、完成证据和生命周期状态。它的职责不是选目标、排序行动或提交动作。

这是一个不同时间点的工程 Candidate。最终冻结的 exact v6 ZIP 只有 structured-state-board、rolling-planning、risk-review 三个 Skill；当前仓库看到四个 Skill，不能据此改写已冻结 ZIP 的身份。v8a 的两次完整运行和边界见[运行审阅](../project/FINAL_EVIDENCE_REVIEW.md)与[架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md)。

## 13. 防止对 Dev 过拟合

正式策略只使用当前局参与者可见的状态、合法选项、公开反馈、手册和确认回执。历史局后分析可以帮助提出假设，却不能自动变成 Agent 可用规则。

因此最终方案不包含：

- 隐藏风险计数、晋升门槛或评测权重；
- 事件标题、编号到固定选项的答案表；
- 从 Dev 内部公式推导的分数最大化规则；
- 跨游戏复用的故事记忆或未证实的固定行动配方。

这些限制防止把局后观察冒充运行时可见信息，也避免把公开 Dev 的偶然路径写死到最终提交物中。[官方来源锁](../project/OFFICIAL_SOURCE_LOCK.md) · [S06 控制架构审查](../project/reviews/S06-16_FINAL_CONTROL_ARCHITECTURE_REVIEW.md)

## 14. 架构小结

| 层 | 解决的问题 | 组件 | 主要边界 |
|---|---|---|---|
| 环境 | 产生情境、执行合法动作、返回结果 | CareerSim / career-emulator | 负责真实状态变化 |
| 工具连接 | 传递请求和回执 | MCP / Runner | 请求发出不等于成功执行 |
| 事实整理 | 确认当前局已知内容 | structured-state-board | 不规划、不推断隐藏状态 |
| 策略规划 | 选择当前目标和候选路线 | rolling-planning | 唯一策略 owner，不提交动作 |
| 风险审核 | 检查候选的直接重大后果 | risk-review | 有界候选门，不取代规划 |
| 动作提交 | 最终选择并调用合法工具 | Single Agent | 全系统只有一个动作提交者 |

理解这套架构时，最重要的是把“职责设计”“工具实际执行”“局后分数”分开阅读，并始终核对它们是否来自同一个 Candidate、同一局和同一提交身份。
