# CareerSim｜Agent 技术方案与系统架构

## 架构摘要

最终方案采用 **Single Agent（单智能体）+ 三个 Skill（技能模块）**：状态模块整理公开事实，规划模块负责目标与候选排序，风险模块审核当前候选，单一 Agent 保留唯一动作提交权。持续生效的 Instruction（执行指令）约束观察、决策、工具调用与恢复顺序。

这套设计的核心是责任归属。它使复核者能区分“知道什么”“准备做什么”“为什么需要重考虑”和“谁实际执行”。它没有消除模型遵循问题；最终完整样本的运行契约审计仍失败，详细发现集中在 [最终方案报告](04-最终方案、候选选择与工程交付.md)。

## 1. 两张图理解方案

### 决策职责流

~~~text
Instruction：持续约束执行与证据边界
                  ↓
Single Agent：唯一动作提交者
                  ↓
Structured State Board：当前公开事实、来源、新鲜度
                  ↓
Rolling Planning：目标、进展、资源约束、候选排序
                  ↓
Risk Review：当前候选的重大风险 gate
                  ↓
take_action：提交一个合法选择
                  ↓
fresh observe：确认实际新状态
                  └────────→ 下一轮状态与规划
~~~

图中的箭头表示判断责任与数据依赖，**不是多 Agent 调用拓扑**。Skill 是模型使用的职责材料，不是三个有独立会话和动作权的执行节点；也没有因这张图而建立常驻多角色调度系统。

### 实际运行链

~~~text
Participant Solution：manifest、Instruction、Skills、设计材料
        ↓
Runner install：校验并部署对应材料、记录身份
        ↓
JiuwenSwarm / AgentServer：组织模型与工具交互
        ↓
MCP：暴露职业模拟的工具接口
        ↓
career-emulator：接受合法动作并改变环境状态
        ↓
回执与 fresh public observe → 下一次模型判断
~~~

图示是高层系统关系，不枚举每个内部方法。模型生成文本、框架发出工具调用、模拟器执行动作和观察到状态变化分别属于不同环节。系统运行细节与源码导航见 [Track B](../tutorial/track-b-system-runtime/01-比赛官方到底提供了什么.md)。

## 2. 三个 Skill 的责任划分

### Structured State Board：让事实有出处

长程对话会同时出现旧状态、计划、行动回执和当前观察。structured-state-board 的问题是：在这些信息里，下一次决策究竟可以把什么当作当前事实？

它整理当前 session 的公开状态、来源与 Freshness（新鲜度），保留有限、可归因的近期变化。新观察优先于旧摘要；未确认、冲突或来源不清的字段保留 UNKNOWN。时间上紧邻的变化不自动被解释为某个动作造成的结果。

Board 不制定目标，不建议一般动作，也不审核风险。若状态模块一边登记事实、一边给出策略推荐，规划者就可能在尚未比较候选时接受一个隐含结论。因此它的输出应是足以支撑判断的事实视图，而不是第二份计划。

**输入与输出概况：**输入为本局新鲜公开观察、确认回执与相关公开反馈；输出为当前可确认事实、来源、新鲜度和必要未知项。它的价值是减少过期或跨局信息混入决策，不能据此宣称提高了最终分数。

### Rolling Planning：保留唯一策略责任方

rolling-planning 负责将公开反馈、目标缺口、已观察进展、资源趋势和剩余机会窗口转成当前候选排序。它拥有 Primary Gap（当前主要目标缺口）、Progress（进展）、Risk Budget（公开趋势形成的风险预算）等规划判断。

Primary Gap 不是机械选择最低的数字；公开反馈和剩余实现窗口都会影响哪些问题应优先处理。Planning 也不推断隐藏晋升门槛、概率或收益公式。目标可以在有新证据时更新，但不应仅因模型重新措辞就无界改写。

Energy 与 Main 的安排需要共同考虑，仍不能用一份旧状态连续提交多个改变状态的行动。每次实际变化之后重新观察，规划才知道先前假设是否成立。动作选项描述的是可能性，观察结果才提供已经发生的证据。

**输入与输出概况：**输入为 Board 的当前事实、正式反馈和当前合法选项；输出为当前目标、有限比较后的候选及理由。它不绕过 Single Agent 提交动作，也不代替 Risk 对具体重大后果作最终门检查。

### Risk Review：审核候选，不接管规划

risk-review 接收已经生成的当前合法候选，检查与它直接相关的公开 Material Risk（重大风险）。风险不从泛化的事件标签或隐藏数值推导，而要有本局可见后果、警告或约束依据。

如果需要 RECONSIDER（重新考虑），它可以要求有边界的备选比较；选定新的候选后再检查。风险模块不拥有总体目标、一般动作排序或最终提交权。这样避免每个普通成本都引起第二轮完整规划，也避免安全偏好永久替代成长目标。

**输入与输出概况：**输入为当前候选、直接相关的公开证据与规划上下文；输出为通过、风险说明或有限重考虑要求。Risk 可以约束本次选择，不等于已经证明能提升生存率。最终样本中出现过符合设计的触发案例，其收益仍没有因果识别。[架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md)

### 权限总表

| 组件 | 拥有的责任 | 不拥有的权限 |
|---|---|---|
| Single Agent | 整合判断、选择并提交唯一动作 | 不把提交权分散到第二个 actor |
| Board | 当前公开事实、来源、新鲜度与有限效果记录 | 总体规划、动作排序、风险结论 |
| Planning | 目标、进展、公开资源趋势、窗口与候选排序 | 独立动作提交；替代候选风险审核 |
| Risk | 当前候选直接重大风险检查 | 总体战略、长期目标或第二套执行循环 |

“唯一 owner”表示需要明确谁对判断负责。模型可以在一次推理中运用多个 Skill，但这些职责不能因此互相覆盖。

## 3. Instruction 与 CTRL 的作用

Instruction 是持续执行契约，规定模型应该怎样使用 Skill、何时观察、怎样提交动作、如何处理恢复和证据边界。Skill 则承载其责任范围内的细化判断。两者配合时，通用执行约束不应被每个模块重复维护成相互冲突的版本。

CTRL 是动作前的审计标记，用于留下与控制判断有关的线索。它不是环境事实，也不是对正确性的自我认证。出现标记文字只说明模型输出了文字；判断它是否对应当前动作、是否同轮、是否重复，需要事件及会话证据。

最终 historical v6 使用的自由文本审计表面存在配对歧义。后续版本曾修改记录方式，但不能把后续合同或补丁描述成冻结包已经具备的修复。架构报告只说明标记角色，完整运行缺陷由 [04](04-最终方案、候选选择与工程交付.md) 集中维护。

详细指令与各版 Skill 条款见 [Track A](../tutorial/track-a-skill/01-从零理解Agent、Instruction与Skill.md)；历史原件的版本关系见 [Skill 版本索引](../skill-evolution/00-版本索引.md)。报告不将提示中的要求改写为运行保证。

## 4. 状态改变与新鲜观察

动作链至少要区分三个事实：模型决定了什么、工具接受并执行了什么、环境随后显示什么。take_action 的成功回执确认提交结果，不自动提供全部下一轮公开状态；fresh observe 才是重新整理状态的依据。

这个顺序也决定异常处置。如果工具拒绝参数且状态未改变，不能把它计成一次成功行动；若超时或连接中断导致结果未知，也不能靠重复发送恢复“看起来成功”。项目的治理要求先核对现有状态与证据，再在授权范围内决定后续动作。

最终完整样本中，成功状态改变后的新鲜观察纪律有明确支持。这是一项局部遵循证据，不能推出整个执行合同通过，也不能推出策略表现稳定。相同的总分与完成标志可以同时伴随别的执行缺陷。[最终方案审阅](../project/FINAL_SOLUTION_REVIEW.md)

这一机制可理解为把计划与世界状态分开：计划提出预期，回执说明动作处理，观察更新事实。只保留模型自己的长摘要，会失去核对它与环境是否一致的可靠依据。

## 5. 上下文压缩与恢复

Context Compression（上下文压缩）会改变模型下一轮能看到的材料。压缩摘要保存了部分内容，不等于完整保留当前状态、会话身份和所有 Skill 约束。恢复需要依据本局公开证据重新确认应使用的信息，而不是假设模型仍记得全部合同。

最终运行发现了压缩后的恢复缺陷，说明“存在恢复规则”和“执行了恢复规则”必须分开判断。它也不能被解释为已经建立 Durable Memory（持久记忆）：同局的压缩上下文与跨调用、跨安装的记忆机制具有不同边界。

后来的 Memory 可行性研究不属于最终架构；其具体自动 anchor 路径未通过部署门。负路线事实集中在 [03](03-研发演进、实验与失败复盘.md)，更完整的验证方法见 [Track D](../tutorial/track-d-project-method/01-为什么这个比赛不能靠反复改Prompt试分.md)。

## 6. 为什么保留 Single Agent

项目采用一个动作提交者，使当前状态、候选和实际提交保持明确责任链。三个 Skill 拆分判断内容，却不增加执行 authority（权限归属）。对于依赖当前 session 和新鲜观察的动作，这使审计问题可以围绕一条执行链展开。

这是已接受的架构选择。把它解释为控制协调复杂度、保持可审查性是合理工程说明，但本项目没有完成 Single Agent 与 Team/Swarm 的受控性能比较。**Team/Swarm = DEFERRED / NOT_TESTED**；官方允许研究该方向，不是比赛禁止多 Agent。

曾研究 advisory Reviewer（建议型审查者）的安全部署，但被测冻结提交路径没有建立机械只读边界，质量阶段没有运行。它没有成为本方案的第二个决策或动作角色。部署门停止不能转成“Reviewer 不如单 Agent”的性能结论。

因此，读者评估 Single Agent 时应看责任与证据是否匹配，而不是从角色数量推断更强或更弱。[架构决策](../project/ARCHITECTURE_DECISIONS.md)

## 7. 审计能力也是系统的一部分

长程 Agent 的工程对象不止 Instruction 和 Skill 文本。复核一次结果，还需要从行为身份到具体轨迹再到交付物建立可追溯联系：

| 对象 | 回答的问题 | 单独存在时的不足 |
|---|---|---|
| Candidate / source identity | 本次准备运行哪份行为材料？ | 不证明材料实际被应用 |
| game 与 drive session | 哪个环境会话、哪段驱动属于本次运行？ | 不证明每个事件都有效或公开可用 |
| events | 哪些工具调用、回执与状态变化发生了？ | 仍需字段解释与来源核对 |
| transcript | 模型怎样表达判断，哪些契约线索出现？ | 自由文本不等于认证后的动作配对 |
| score record | 某个会话记录了哪些结果字段？ | 可能过期，须与会话来源对齐 |
| adherence audit | 哪些执行要求通过、失败或无法认证？ | 不估计策略因果收益 |
| package manifest | 冻结交付包含哪些内容？ | 不证明官方已接受或运行 |

这条关系让项目可以发现错误归因，而不是在看到一个分数后才临时补来源。派生摘要用于阅读，原始证据用于必要复核；哈希提供身份校验，不能替代缺失内容。证据生命周期和本地保留方式见 [Track C](../tutorial/track-c-repository-tooling/01-仓库总览与核心工程文件.md)。

## 8. 当前工程状态与最终包

当前 main 的 configs 与 Skills 保留历史 v8a 四 Skill 工程状态，第四个模块 delivery-progress 负责有界的交付生命周期、证据状态与公开 recognition（确认）关系。它不拥有目标、策略排序、风险判断或动作提交权。[当前状态](../project/CURRENT_STATE.md)

最终包来自 historical exact-v6，仅含前述三个 Skill。delivery-progress 不是这个包的一部分；当前工程文件较新，也不自动成为提交源。完整来源、候选比较和包身份请看 [04](04-最终方案、候选选择与工程交付.md)。

这种并存不意味着两个身份互相覆盖。历史工程树服务复盘，最终工件服务交付；描述哪一个，都需要写清用途。不能把 v8a 的模块数量、后续修复和 v6 的成绩拼接成一个从未运行过的“最终增强版”。

## 9. 可评价的设计与未证收益

| 设计选择 | 可评价的工程意义 | 仍需独立证据的问题 |
|---|---|---|
| 新鲜公开状态作为决策起点 | 防止旧摘要越权覆盖当前事实 | 不同轨迹中能否长期可靠遵守 |
| 一个策略责任方 | 便于定位目标与排序来源 | 是否比其他架构带来更好表现 |
| candidate-first 风险门 | 将重大风险判断绑定到实际候选 | 风险判断的准确率及因果效果 |
| 一个动作提交者 | 权限、会话与执行责任明确 | 是否在云端运行中保持同样行为 |
| 恢复与审计契约 | 可以检查压缩、标记与执行断点 | 模型能否完整、稳定地遵循 |

这套方案有明确设计和真实运行支持，也有已知缺陷。评审可以检查它是否便于理解与复核；不能仅凭责任表认定其稳定优越。研发为何转向取证、为何未纳入更多扩展，见 [03](03-研发演进、实验与失败复盘.md)。
