# 04｜实验设计与证据评估

## 1. 实验要回答一个可改变决策的问题

CareerSim 对局耗时高、状态持续变化，而且工具链存在共享运行状态。一次实验开始前，先说明它要区分什么：是 Skill 能否安装和加载，是模型会不会在真实情境调用规则，还是某项策略是否改变了结果。问题不同，所需证据和成本也不同。若实验结果无论如何都不会改变架构、候选或下一步授权，就不应为了产生更多分数而启动昂贵运行。

人读复盘用“观察到什么—支持什么—不支持什么”呈现证据。一个完成的游戏可回答该局的终局和轨迹；它不能独立回答候选的稳定分布、单项机制的因果效果或隐藏 Test 的迁移表现。实验设计的首要工作是把结论范围预先写清楚，避免拿运行结束后的有利叙事替代原问题。

## 2. 验证不是一个总开关

可以把项目里的证据分成逐层递进的检查。前一层通过，只代表它自己的边界通过：

| 证据层 | 能回答的问题 | 不能替代什么 |
|---|---|---|
| 身份与材料 | Candidate、Skill、Runner、manifest 和包能否精确对应？ | 运行时是否安装、调用或遵循 Skill |
| 静态与离线合同 | 文件结构、固定枚举、允许成员和本地离线检查是否通过？ | CareerSim 是否接受一次真实动作 |
| 框架路径 | Skill 是否能安装、被发现并加载？ | 模型是否在相关情境中使用了它 |
| 真实情境运行 | 是否出现触发窗口、审核输出、动作请求和环境回执？ | 多局分布、因果收益或隐藏集效果 |
| 运行遵循审计 | observe、动作、标记、压缩恢复是否按合同执行？ | 策略是否提高最终成绩 |
| 重复或受控比较 | 轨迹是否显示可重复差异，或支持某一机制解释？ | 官方平台评分，除非官方评测实际发生 |

例如 S03-02 的 Skill 通过静态、安装、Runner 验证、发现和加载，但唯一 smoke 走了不匹配的通用工具路径，没有 CareerSim session，也没有 observe/take_action 链。它支持的是“若干材料与加载门通过”，不能被计作 Risk 策略的真实行为实验。这正是分层报告比单一 PASS/FAIL 更有用的原因。

## 3. 先锁定身份，再定义比较

可比较运行至少需要知道候选 source、Skill 字节、运行配置、Runner 与环境身份。构建 commit 和 runtime source commit 也应分别记录；ZIP manifest 证明包里有什么，不证明某段历史运行使用了完全相同的包。身份不清时，即使表格上列了多个分数，也无法确认差异来自候选还是运行材料。

比较设计还应预先约定结果字段。项目同时记录 quantitative score、competition partial score、存活月份、grade、Level、动作结果和运行契约遵循。完整时程、A 级和高分不是可互换指标；技术失败没有终局成绩，不能被补成低策略分。若问题是运行正确性，就用动作请求、回执和 fresh observe 的逐次审计回答；若问题是策略收益，就需要可比身份与能区分机制的实验条件。

一次明确的假设应说明候选机制、适用窗口、公开触发证据、合法对照选项和停止条件。例如“当前观察到的健康趋势是否改变某个成长候选的风险取舍”，比“加上 Risk Skill 会不会更强”可检验得多。前者可以通过触发案例和候选对照检查过程；后者把调用、策略选择、运行遵循和最终得分混成了一个问题。

## 4. 项目实际样本能说明什么

| 运行/身份 | 已记录结果 | 作为实验材料的边界 |
|---|---|---|
| S01 no-op | 26.95 / 18.86 / 19m / E / L3 | 证明有一条最小运行闭环；不是后续路线的受控对照。 |
| Candidate v1 两局 | 76.04 / 48m / A / L6；35.31 / 25m / D / L4 | 同一候选两条摘要轨迹差异明显；Tier-B 摘要且 raw 不可用，不估计分布。 |
| exact v6 S06-24 | 75.29 / 52.70 / 48m / A / L6 | 一个有效完整样本；运行审计为 RUNTIME_ADHERENCE_FAIL。 |
| v8a 两局 | 72.65 / 48m / A / L5；59.00 / 48m / C / L4 | 同一四 Skill 候选两条完整轨迹；不是 v6 复验或架构对照。 |
| v7q / v7m | v7q 在 M24 自然终局；v7m 在 M20 技术失败 | 自然终局与技术中断分别记录，后者没有终局分数。 |

这些材料适合支持工程判断，例如一个高峰值不足以说明稳定、运行中断不能算策略分、版本间结果不能直接归因。它们不足以支持“v6 比 v8a 高多少”或“某个 Skill 导致晋升”等因果结论。详细运行身份与保留状态见[最终证据审阅](../project/FINAL_EVIDENCE_REVIEW.md)，本表不替代运行台账。

## 5. 机制观察与机制因果不同

S06-24 中曾观察到若干设计机制在触发案例中的行为：公开 Health 趋势与风险预算变化、M13 候选触发 Risk 复核、Growth 选项出现可观察饱和后的调整，以及正式反馈后的 Planning 重置。这些记录可支持“机制在指定案例中有出现”，不能证明它们造成了 75.29 或延长了生存期。要从观察升级到因果解释，实验需提供可比较条件，并排除其他同时变化的因素。

即使某一局正确执行了 fresh observe，也只能说明该次动作后的状态刷新步骤可核验。若要估算长期遵循率，需要更多同身份运行和统一的审计口径；若要估算策略贡献，还需冻结其余变量并建立比较组。重复样本有助于观察波动，但若运行时身份、初始状态或执行环境不同，增加样本数仍不能自动解决可比性。

## 6. 高成本运行与资源读数

正式对局之前应先排除低成本即可发现的问题：包是否可解析、工具路线是否适用、Skill 是否进入运行时、输入和身份是否冻结。CareerSim 的安装、共享实例和状态写入可能影响其他会话，因此隔离不足时不能并行假设安全。live 运行必须有明确次数、成本和停止条件；技术失败或未知副作用先查状态，不盲目重发。

S06 closeout 还单独核算了 v6 的 token 读数：Runner gameplay aggregate 为输入 40,372,074、输出 247,309、合计 40,619,383，其中报告缓存 token 39,865,088；两次 CurrentRoundCompressor 合计 328,103 token，单独列账。实际账单成本为 UNKNOWN。缓存比例意味着总 token 不能被解释为全部未缓存输入；压缩 token 也不能与 Runner gameplay aggregate 混为一个调用。这个案例说明成本报告应保留口径和来源，而不是只引用一个大数字。

## 7. 先进路线的门槛设计

项目把 Reviewer、Memory、deterministic helper、Replay controller、策略挖掘和 Simulator policy search 分开检查。Reviewer 先要满足安全部署路径；自动 Memory 需要确实携带正文；helper 的工具层成功还需云端权限和模型调用验证；controller 要证明它修正了重要决策；策略挖掘需要处理选择与状态混杂；模拟器搜索则先过冻结基线可完成性门。

最终几条路线都没有提供可直接纳入冻结包的候选增量。准确做法是记录各自在哪道门停下，而不是把全部归类为“高级方法失败”。路线结果与非结论汇总见[实验复盘](../project/EXPERIMENT_RETROSPECTIVE.md)和[架构复盘](../project/ARCHITECTURE_RETROSPECTIVE.md)。

## 8. 一个可复核的实验模板

开展后续实验时，可先写下：

1. **问题：**结果可能改变哪个明确决定？
2. **身份：**锁定 Candidate、Skills、Runner、环境、父链和输入条件。
3. **比较：**一次主要改变一个机制，预先说明基线和替代解释。
4. **观测：**定义成绩、终局、动作正确性、fresh observe、策略遵循和成本的各自口径。
5. **停止：**写明运行次数、预算、技术失败、Unknown Side Effect 和证据不足时如何停止。
6. **留证：**保存去敏摘要与唯一必要 raw 来源，写清路径、hash、保留责任和解除条件。
7. **结论：**区分 FACT、支持范围、UNKNOWN 和下一步建议；不把技术通过写成策略收益。

S06 的后续实验方向曾被登记为 E1 重复 frozen-v6b 运行、E2 单机制消融、E3 结构化轨迹探索；这些是建议方向，不构成本报告的游戏授权或已执行结果。任何新运行仍须遵循当前 Main/Stage 的授权与 live gate。[S06 closeout](../project/S06_CLOSEOUT.md) · [LIVE_RUN_WORKFLOW](../project/LIVE_RUN_WORKFLOW.md)
