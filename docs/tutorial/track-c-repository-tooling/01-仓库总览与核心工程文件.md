## 先辨认目录与参与者

### 先分清三个“项目”

Repository（代码仓库）是 Git 管理的版本集合；Current Tree（当前文件树）是某个提交在检出目录呈现的文件；Local Workspace（本机工作区）还包含依赖、日志、临时输出和未进入 Git 的证据。资源管理器看到的是第三者，而别人克隆仓库主要拿到第一者在某个提交的当前树。于是，本机有一个目录，不代表别人克隆后也有；某目录被 ignore，不代表那里绝无 tracked 文件。

**事实：**S11-28 地图记录了当前主要对象。下图保持真实顶层名称；层名属于 **解释**，帮助理解职责，不是代码新增的目录。

```text
CareerSim repo
│
├─ Runtime layer（运行层）
│  ├─ career_sim_runner/     本仓库的安装、驱动、记录与报告代码
│  └─ pyproject.toml、uv.lock 依赖与锁定关系
├─ Candidate layer（候选方案层）
│  ├─ configs/               当前候选元数据与运行 manifest
│  └─ skills/                当前四份 Skill 文本及占位文件
├─ Tooling layer（工程工具层）
│  ├─ scripts/               打包、审计、研究、公开接口玩家
│  └─ tests/                 工具、文本、身份、解析与包装合同
├─ Experiment layer（实验层）
│  └─ experiments/           S07-50 系列输入快照和评估结果
├─ Evidence layer（证据层）
│  └─ artifacts/dev-runs/    选定并扫描的开发运行归档
├─ Documentation layer（文档层）
│  ├─ docs/                  权威状态、合同、报告、历史与教学
│  └─ submission_materials/  提交说明及设计文稿来源
└─ Local workspace layer（本机工作区层，通常 ignored）
   ├─ .local/               工作树、运行材料、上游副本、scratch
   ├─ .venv/                已安装 Python 与第三方依赖
   ├─ .career_sim_runner/   Runner 本机状态与输出
   └─ logs/、缓存等           身份和生命周期各不相同
```

官方模拟器和 JiuwenSwarm 是通过依赖安装的包，不等于 `career_sim_runner/` 本身。[Track B 官方提供什么](../track-b-system-runtime/01-比赛官方到底提供了什么.md)讲这些系统的归属；本章只把它们放回工程地图。

### 各目录是谁的工作台

| 对象 | 主要使用者与用途 | 是否参与一局正式运行 | 产生时点与保留理由 |
|---|---|---|---|
| [configs/](../../../configs/) | 候选维护者、包装脚本；声明身份与 Instruction | 通过打包、安装被使用；不能把源文件存在当成已加载 | 候选修改时产生；保留来源身份 |
| [skills/](../../../skills/) | 模型通过运行层读取；开发者编辑规则 | 被安装并实际读取时参与 | 策略开发资产；当前四 Skill 不是最终三 Skill ZIP |
| [career_sim_runner/](../../../career_sim_runner/) | 运行操作者；衔接提交、服务、动作与报告 | 参与正式 Runner 路线 | 工程运行核心，受冻结身份约束 |
| [scripts/](../../../scripts/) | 开发者、研究者、审计者 | 因脚本而异；事后提取器不参与动作 | 工程需求出现时产生；按职责及依赖决定保留 |
| [tests/](../../../tests/) | 开发者；自动检查明确断言 | 通常不被正式 gameplay 加载 | 保护合同和既往修复；不等于比赛必须提交 |
| [experiments/](../../../experiments/) | 研究者；保留输入/结果对照 | 历史快照不自动成为当前策略 | 实验时冻结，保留比较和复现来源 |
| [artifacts/](../../../artifacts/) | 审计者；选定运行包 | 是运行产物及派生材料，不是全部运行输入 | 运行后归档，受来源/hold约束 |
| [submission_materials/](../../../submission_materials/) | 最终构建器与人类评审 | 文稿不替模型选择行动 | 最终提交解释层的来源 |
| [docs/](../../) | Main、开发者、学习者 | 教程不参与比赛执行；合同影响工程行为 | 保存可审的状态、判断、方法和学习资料 |
| `.local/` | 本机工程任务和证据管理者 | runtime 子项可能有关；scratch一般无关 | 任务工作状态，默认不共享到Git |
| `.venv/` | Python 程序与工具 | 提供真实运行依赖 | 按依赖身份安装，可重建但不能随意扰动 |

目录在同一个 repo，**不等于它们都参与一次 Agent gameplay**。例如，S09 的 forensic（取证调查）脚本分析已经完成的公开轨迹；`docs/tutorial/` 帮助人理解工程；它们和正式 Runner 有关系，但不在每次模型动作的调用链上。

### 从一次运行看文件怎样合作

**教学示例：**设想一个获准的开发运行。工程人员先核对候选身份，将 manifest 与 Skill 包装成提交目录；Runner 安装并驱动运行；模拟器和模型产生事件、文本及结果；工程人员用审计脚本整理摘要，再把结果写入 Run Record（运行记录），由 Main 作出决策。

```text
configs + skills → 包装/安装 → Runner → Agent/MCP/模拟器
                                      ↓
                                本机运行输出
                                      ↓
                         audit / 选定的 evidence archive
                                      ↓
                       docs/project 中的记录与决策
                                      ↓
                          docs/tutorial 中的讲解
```

这幅图省略服务细节，没有执行任何步骤。**教学示例；本篇阅读不授权执行，当前 S11-41 也不授权运行或清理。**真正的安装与运行链在[Track B 第 06 章](../track-b-system-runtime/06-Runner、Tool调用与状态更新.md)。

如果只保留 Skill，别人不知道怎样安装、用什么依赖、哪份结果属于它。如果只保留日志，别人不知道输入身份及结论。如果只有结论而没有必要来源，遇到身份争议就无法再核对。工程仓库把这些关系连接起来，是为了使改变和判断可以被审阅。

### 当前树与本机状态的关系图

```text
Git 历史：保存被提交过的版本
        │ checkout 某个提交
        ▼
当前树中的 tracked 文件 ──────── 可形成下一次 Git diff
        │
        ├─ 安装依赖 → .venv/                  ignored
        ├─ 运行程序 → .career_sim_runner/     ignored
        ├─ 工程任务 → .local/scratch/         ignored
        └─ 运行证据 → .local/runtime/         ignored，可能受hold
                         │ 明确选定 + 扫描 + 归档
                         ▼
               artifacts/dev-runs/ 中部分tracked文件
```

Tracked（已跟踪）是一种 Git 状态；Canonical（权威）是一种事实职责；Held（受保留约束）是一种生命周期限制。它们是三个不同维度。一个本机 ignored 原件可以是唯一证据；一个 tracked 历史 review可以已被权威总结吸收；一个小 manifest可以很重要，却不能替代它记录的大原件。

`.gitignore` 也不会把已跟踪归档从历史或当前树自动撤掉。这个表面上的“例外”来自显式归档流程，不能推广成随意 force-add整个日志目录。忽略规则及字节规则在下面的根文件部分展开。

目录图说明材料放在哪里；根文件说明开发者和工具按什么规则使用它们。尤其要区分：编辑仓库的 Codex 与参加比赛的 Agent，虽然都叫 Agent，却有不同任务和权限。

### AGENTS.md：此处的 Agent 是工程人员

本项目同时有 Codex engineering agent（Codex工程 Agent）和 competition CareerSim Agent（比赛 Agent）。前者读代码、编辑文件、检查 diff、形成提交；后者在比赛运行时读 Instruction与Skills，通过工具采取行动。两者可能都使用语言模型，但工作对象、权限和证据完全不同。

`AGENTS.md` 对前者约定仓库身份、Windows路径、Git工作流、live授权、raw留存以及 Main review。它要求工程 Agent不要静默修改 frozen Runner、依赖或锁文件，不要把工作树当运行隔离，不要把一次成功工具结果扩大成游戏通过。

它不是后者的比赛 Instruction。比赛 Instruction的来源在 `configs/runtime_manifest.json`，最终冻结包又绑定历史exact-v6来源。将 `AGENTS.md` 放在仓库根目录，不能据此认定 JiuwenSwarm在对局时自动读取它。[Track A 第 01 章](../track-a-skill/01-从零理解Agent、Instruction与Skill.md)解释比赛文本角色；[运行合同](../../project/AGENT_RUNTIME_CONTRACT.md)说明 ownership（职责归属）。

**教学示例：**“只改教程，不调用Provider”约束工程 Agent；“选择前重新观察游戏状态”约束比赛 Agent的运行规则。前者通过文件范围与操作记录审阅，后者要通过真实session轨迹审计。检查前者的Git diff，不能证明后者遵循了决策规则。

没有根工程合同，任务容易在不同对话里默默扩大范围；但有合同也不意味着执行自然正确。合同提供共同基准，实际行为仍需可核验的交付物。

### README：从门口进入，不把门口当整栋楼

README适合让人快速知道项目现在处于什么阶段、最终选择是什么、去哪里读报告和教程。具体来源冻结在 `OFFICIAL_SOURCE_LOCK.md`，当前状态在 `CURRENT_STATE.md`，架构判断在 `ARCHITECTURE_DECISIONS.md`。这些文档分工使入口能保持简洁。

当README概述与更具体的权威来源出现冲突，应该核对身份和时间，不能只挑较顺眼的一句。历史run与当前候选并存时尤其如此：运行记录保存当时事实，状态文档表述现在的决定，两者不必有相同Candidate。

长期保留README的理由是导航价值。它不参与模型选择，但会影响别人是否能找到准确来源。若将所有历史日志和全部合同复制到README，更新负担会增加，读者反而更难发现关键状态。

### pyproject.toml：工程声明不是安装目录

TOML是一种结构化配置格式。当前项目声明名称 `CareerSim-BDCI26`，版本 `0.0.0`，Python范围 `>=3.11,<4`，依赖包括 `career-emulator[bdci]`、`jiuwenswarm`、`fastmcp`、`rich`、`pyyaml` 等。范围告诉工具哪些版本满足声明；它不等于本机当前实际版本。

**事实：**配置还有 test、format、dev依赖组；`pytest`的 `testpaths` 是 `tests`；Runner prompts通过 package-data声明随包包含。因此同一文件既为运行提供依赖声明，也为开发工具提供配置。`scripts/research/s10_22/test_boundary.py` 在研究目录，不能仅凭文件名就说默认pytest必然覆盖它。

代码依赖的外部包不全部复制进本仓库：项目代码在 `career_sim_runner/`，安装后的包在 `.venv`。长期保留pyproject使别人在没有原环境时知道应准备什么；它不能证明安装已经成功或该配置在官方平台运行通过。

依赖为什么包含很多看起来与游戏无关的库？直接依赖会再依赖网络、序列化、界面或工具包，形成 transitive dependency（传递依赖）。具体完整关系由锁文件及安装身份解释，不能按包名猜它一定参与每一步行动。安装机制详见[Track B 环境章](../track-b-system-runtime/02-从零搭好Python与依赖环境.md)。

### uv.lock：把“满足范围”落实成可比较的解析结果

`pyproject.toml`可以允许一个版本范围，`uv.lock`保存解析后的包、版本、来源、依赖和平台条件。若没有锁文件，隔一段时间重建环境可能解析到不同分发物；调查行为差异时，就多了一组不受控变量。

Lockfile（锁文件）并不打包解释器、已安装目录、服务状态或本机数据库。锁文件存在也不自动说明当前`.venv`没有漂移。因此要区分：声明范围、锁定结果、已安装身份、一次Run记录的身份。项目freeze（冻结）要求可比较配置，不允许为了“让工具跑起来”悄悄同步依赖并覆盖原环境。

**解释：**pyproject回答“工程需要哪些类别和范围”，lock回答“此次解析选定了哪些身份”，`.venv`回答“这台机器现在安装了什么”。三者合作提供复现基础，但复现还需要平台、Python版本和明确运行授权。

可重建环境的存在，是长期保留这两个小文件的理由；它不是当前删除大环境的授权。第[09章](08-本地工作区、环境与可重建状态.md)进一步解释。

### .gitignore：默认不共享什么

当前规则排除虚拟环境、`.local`、`.career_sim_runner`、常见cache、logs、数据库、本机输出和秘密文件类型。`.env`及其变体被排除，模板例外可以只保留无真实凭据的结构。这里不读取任何秘密值。

为什么不提交`.venv`？它包含大量可由依赖声明重建且与平台有关的文件。为什么不提交`.local`？它混合临时研究、独立checkout和可能敏感的运行材料。为什么不提交共享DB？它可能包含不属于本任务的session与内部状态，并非可公开的run证据。

Ignore只改变Git对未跟踪路径的默认处理，不是加密、访问控制或自动去敏。已跟踪文件仍会被跟踪；显式强制加入也能绕过默认排除。因此归档脚本必须先选定、切时间窗、扫描，再有限地stage（暂存）。不能因为 `artifacts/`被忽略，就认定其中七个tracked开发归档不存在。

常见误解有两个：一是“看不到git status就安全”，忽略只是减少提示；二是“需要证据就把整个日志目录提交”，证据合同要求范围、身份和secret scan（敏感值扫描），并禁止共享DB及无关session。相关规则见[证据章](07-artifacts、Raw-Evidence与证据链.md)。

### .gitattributes：此项目的实际规则很窄

**事实：**当前文件只有 `/artifacts/dev-runs/** -text` 规则。`-text`禁用该归档路径的Git文本转换，使manifest记录的hash能与提交中的字节对应。它不是全仓CRLF统一规则。

这是对S11-28地图泛化描述的源代码校正：源地图把属性文件概括成文本/换行处理，教程按真实规则解释它对证据字节的用途。同样，地图中把`skills/`五项概述成“四Skill加manifest”也需校正：第五项是`.gitkeep`，manifest实际在configs。地图是导航，当前文件才是事实依据。

Hash（哈希）是由内容算出的指纹。文本换行转换会改变字节，从而改变hash；但hash不会存储原始文件，也不会说明文件属于哪一局或有没有敏感内容。字节规则解决一致性中的一个小问题，不解决全部provenance（来源链）。

### 根目录之外：提交文稿的准确角色

`submission_materials/`当前三份tracked文件是README及两份设计文稿。它们为最终构建提供说明文字，不是完整冻结payload。最终ZIP还需要从冻结身份取manifest与三Skills。别把“文稿来源齐全”说成“可交付运行包已在此目录全部展开”。

自查：删去uv.lock但保留`.venv`，项目此刻可能仍能执行，为什么这不是可靠精简？因为现有环境掩盖了重建输入缺失；未来机器无法按同一锁定结果准备依赖。反过来，保留锁文件不等于可以当下删除唯一实验环境。保留决策必须同时看长期可复现性和当前依赖。
