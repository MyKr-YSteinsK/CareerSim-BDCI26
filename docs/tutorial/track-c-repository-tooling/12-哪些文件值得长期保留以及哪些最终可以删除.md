# 12｜哪些文件值得长期保留，以及哪些最终可以删除

[学习地图](00-学习地图.md) · [上一章](11-一次开发任务从Plan到Git是怎样落地的.md)

## 精简仓库先回答“失去什么”

Repository Reduction（仓库精简）不是把大小压到最低，而是让当前核心容易找到，同时保住必要事实、复现能力、教学知识和未决证据。Current Tree（当前树）承载正在使用及明确保留的资产；Git History（版本历史）保存已提交过的过去；Local State（本机状态）有些可以重建，有些根本不在Git里。

这章提供判断方法，没有删除、移动、归档或hold release。下列taxonomy（分类法）为 **INTERPRETATION｜解释**，用于教学和将来审查；不是Main批准的逐路径disposition（处置决定）。

## 一、九类保留/退役状态

| 类别 | 含义 | 本项目示例与前提 |
|---|---|---|
| KEEP_CORE | 当前运行/工程接口的必要来源 | Runner、依赖声明、当前使用的包装/审计工具 |
| KEEP_CANONICAL | 负责项目权威事实/决定 | CURRENT_STATE、OFFICIAL_SOURCE_LOCK、FINAL_EVIDENCE_REVIEW |
| KEEP_FOR_TEACHING | 承载独有长期学习价值 | Track A/B/C、代表版本GUIDE |
| KEEP_FOR_REPRODUCIBILITY | 使重要方法/结果可重算或身份可恢复 | 冻结builder、必要实验snapshot与方法代码 |
| KEEP_UNTIL_KNOWLEDGE_MIGRATED | 知识还未完整迁移，不急于删除 | 含唯一解释的旧review或调查脚本 |
| DELETE_AFTER_KNOWLEDGE_MIGRATED | 迁移后可进入明确删除审查 | 已被canonical/tutorial吸收、引用关闭的过程资产 |
| SAFE_DELETE_CANDIDATE | 已知可重建、无活动/证据依赖的低风险候选 | 确认纯生成且不被使用的cache；仍需具体授权 |
| HOLD_OR_PROVENANCE_BLOCKED | hold或来源依赖阻止删除 | held events/raw、唯一session payload、未知来源范围 |
| UNKNOWN_REVIEW_REQUIRED | 不能准确说明来源、使用者或释放条件 | v7o/v7v未知条件、未分类本机材料 |

标签可以描述主职责，也可以叠加限制。例如核心audit脚本是KEEP_CORE，某次audit输入却是HOLD_OR_PROVENANCE_BLOCKED；同名目录不能只贴一个标签就批量删除。

## 二、先画依赖，再决定去留

Dependency（依赖）意味着A要使用或解释B。代码import、脚本输入、test断言、Markdown链接、Run来源和review责任都可能是依赖。删除B时，A可以仍存在却不能工作或失去可审依据。

```text
运行代码 → 依赖/配置/Skills
包装器 → 冻结源 + 提交文稿 + 合同
test → 受测脚本 + fixture + 版本期待
研究结论 → 方法 + 输入身份 + 必要raw
tutorial → source链接 + 真实案例
Main决定 → canonical证据 + 尚未闭合的责任
```

**TEACHING EXAMPLE｜教学示例：**旧review不再被README链接，但一个research报告仍引用其中唯一Session解释。它不是“无人引用”的文件。反过来一个tutorial引用了旧脚本作为源码案例，未来若退役脚本，需要替换为可恢复的固定历史链接或迁移足够方法说明；否则教材会留下断链。

没有依赖检查，删除会把错误推迟到下次复验或阅读时才发现。有依赖检查也不自动提供授权：它只是形成可审阅的候选范围。

## 三、Git history与current tree为什么可以不同

Git history保留历史，**不等于当前main必须永远保留每份历史过程文件**。一个重要开发阶段可以在历史提交里完整恢复，同时当前树只留下更清晰的权威总结和少量代表性来源。

什么时候旧review可以退出？至少要核对独有知识已吸收到canonical docs/tutorial、引用已修复、runtime/repro/hold依赖已解除、历史对象确实可恢复，并由任务授权准确范围。删除可以移除当前文件而不重写已推送历史；恢复历史来源则需保留commit/path身份，不只记一个模糊文件名。

**FACT｜事实：**[FINAL_EVIDENCE_REVIEW](../../project/FINAL_EVIDENCE_REVIEW.md)记录S11-15已从当前树移除六份被吸收的S10过程gate review，同时research来源和历史结果仍可从Git恢复；该次清理没有改变台账hold。这是“知识迁移后减当前树”和“raw责任继续保留”并行的真实案例。

反例是从未commit的raw：Git只能恢复进入对象数据库的内容。`.local/runtime`下唯一捕获、DB row或服务log若没有受控副本，删除之后无法从Git生成。它的hash能核对找回的内容，不能找回本身。

## 四、六类常见对象的具体判断

### 1. Cache：低风险候选仍有前提

纯 `__pycache__`或pytest生成cache通常可以重新生成。将来若确认不是活动依赖、不含手写材料、没有证据引用，可作为SAFE_DELETE_CANDIDATE。收益主要是空间或目录清晰，不是“删除后系统更正确”。

没有cache，程序可能多做一次计算；没有源码，程序可能根本无法重建。先区分这两种损失。当前S11-29没有cache cleanup权限。

### 2. One-off forensic script：重要方法可能迁移，也可能仍需复验

S08/S09提取器当时保护准确来源、窗口和公开边界。它可以是KEEP_FOR_REPRODUCIBILITY；如果唯一知识尚未迁移，则KEEP_UNTIL_KNOWLEDGE_MIGRATED；迁移并关闭全部依赖后，才可能DELETE_AFTER_KNOWLEDGE_MIGRATED。

不能因为名称有S09、年份旧或任务完成就删。还要查tests是否import、report是否靠它重算、同一方法是否被下一脚本复用。必要时保留固定历史源码身份；方法文字摘要是否足以替代代码，应由复验要求决定。

### 3. Historical review：结论、来源和判断边界都要迁移

旧review可能保存“为什么没继续”“哪些阶段未运行”“哪份来源不可信”。只抽取分数而漏掉限制，不算知识迁移完成。若未来只留下“75.29高分”，却丢了单样本和RUNTIME_ADHERENCE_FAIL，精简就扭曲了事实。

review退役时，canonical来源应保留足够身份、理由与未知；引用要改到新权威文档或固定历史对象。不能先删再希望下一个任务补链接。

### 4. Canonical source：小文件也能承担最大责任

`CURRENT_STATE`管现在状态，`OFFICIAL_SOURCE_LOCK`管官方身份，`ARCHITECTURE_DECISIONS`管架构判断，final identity/manifest管冻结提交。它们通常KEEP_CANONICAL，部分还与运行/包装合同直接相关。

权威文档也不是不能重构，但换职责和路径需要迁移事实、引用与验收，不能当“重复Markdown”普通删除。本任务明确保护全部canonical路径。

### 5. Held raw evidence：先闭合责任，再另行授权

events、transcript、run log、session payload可能是HOLD_OR_PROVENANCE_BLOCKED。当前canonical台账20具名active/pending项为18 KEEP_ACTIVE、2 UNKNOWN_REVIEW_REQUIRED、0可释放。本次HOLD_RELEASE_COUNT=0。

有结论不代表所有归因结束；有archive不代表所有原件都覆盖；有hash不代表来源能恢复。Release需要Main/Stage接受和下游依赖闭合，删除还需要限定到具体来源的授权。未知范围只能先对账，不能把UNKNOWN理解成没有hold。

### 6. Tutorial asset：不参与比赛，仍有长期读者价值

Track A/B/C为人建立模型，是KEEP_FOR_TEACHING。它们可能保存已从过程文件迁移的知识，因此删除教程也可能重新造成知识缺口。未来缩减应检查内容替代、导航、源码链接和用户学习目标，而不是用runtime-critical=false直接删。

如果某章过时，先标清版本并修事实；如果整个知识迁移到新的教程，再审查旧章退役。教学资产维护也要有范围，不能顺手重写A/B来追求统一风格。

## 五、.venv与scratch分别怎么审查

`.venv`通常不tracked且能按依赖基础重建，仍可能支撑当前所有static任务及冻结runtime。它可以减少误提交，却不属于默认垃圾。若未来需要回收，先核对解释器/安装身份、没有活动任务、重建方案与具体授权；不能以大为唯一依据。

scratch通常是可重建派生物，但S11-23→S11-28→S11-29形成真实消费链。七份source pack尚在本任务被使用；完成教程也不自动证明未来Track D或Main不再需要它。保留到知识迁移和依赖确认，再由低成本机械任务精确处置。

工作树则另有未提交状态/父链/review依赖。只看磁盘目录存在，无法判断是否可以remove；不例行prune，不强删dirty。runtime更不能整体清空。

## 六、一个教学用退役审查流程

```text
准确对象与身份
     ↓
用途/调用者/引用/唯一知识
     ↓
是否运行核心、canonical、教学或复现资产？
     ├─ 是 → 保留或先定义替代与迁移
     └─ 否/迁移已完成
             ↓
      raw/hold/来源及下游依赖是否明确？
             ├─ 未知/未闭合 → blocked或review required
             └─ 闭合 → 核对可恢复性与确切删除范围
                              ↓
                        Main/任务明确授权
                              ↓
                  精确清理 + 引用核验 + 限制记录
```

**教学示例；当前 S11-29 不授权执行。**图只讲判断步骤，没有生成下一Plan或删除清单。具体授权必须来自当前任务，不能从教程拿到。

每一步为何必要？身份防删错对象；用途避免删活动组件；迁移防知识流失；来源/hold防丢独有证据；授权确保责任明确；后验检查发现断链和范围错误。只做secret scan也不替代这些判断，秘密安全与证据完整性是不同要求。

## 七、常见误判与修正问题

| 误判 | 更有用的提问 |
|---|---|
| “ignored，所以没用” | 为什么不共享？是否唯一raw或活动环境？ |
| “tracked，所以永远保留” | 当前职责是什么？历史是否足够、引用是否迁移？ |
| “COMPLETE，所以raw可删” | 哪个任务完成？release condition和依赖闭合了吗？ |
| “Git能恢复所有东西” | 这个确切文件是否commit过、哪份bytes？ |
| “一份摘要包含全部知识” | 是否保存了方法、身份、未知和未运行阶段？ |
| “大文件先清理最划算” | 空间收益对应什么不可恢复风险？ |
| “历史负结果没有价值” | 是否避免重复失败或说明真实部署边界？ |
| “tutorial不参与game，可删” | 是否承载用户长期学习与知识迁移？ |

## 八、完成Track C后的完整mental model

Mental Model（心智模型）不是一张要背下来的目录表，而是能沿问题找到对象和证明边界：运行问题看Runner/安装身份，候选问题看config/Skill/冻结来源，包装问题看builder/合同，解析问题看工具/fixture，结果问题看Run/Session/raw，协作问题看Plan/Git/TASK_RESULT，删除问题看用途/依赖/hold/授权。

同一个文件可以有多重角色，所以答案不是“py保留、log删除、md随意”。当前树、历史对象和本机状态共同支撑工程，但生命周期不同。最终精简应使core更清晰，让canonical判断可独立理解，让教学可读，让复验仍有必要来源，也让不再使用的过程资产有准确退役条件。

**TEACHING EXAMPLE｜教学示例：**未来有人想删除一个S09forensics脚本、一份旧review和一份held log。合理返回可能是三种：脚本仍被tests依赖，暂保留；review独有知识与引用已经迁移，可交明确授权审查；log的release条件未闭合，继续hold。把它们都称“旧资产”会丢掉真正决定资格的信息。

本教程到此完成Repository/Tooling关系教学。项目S11是否完成、哪些资产下一步清理、是否开启Track D，由Main/用户另行决定。返回[学习地图](00-学习地图.md)可用十二个问题自查，再按需要回到[Track A](../track-a-skill/00-学习地图.md)与[Track B](../track-b-system-runtime/00-学习地图.md)。
## 深入练习：怎样判断“知识已迁移”是否充分

**TEACHING EXAMPLE｜教学示例：**旧review包含一张分数表、失败根因假设和未执行阶段。新canonical只复制分数表，这并不等于独有知识迁移：后来人会不知道根因仍未证实、哪些步骤因gate停止，也可能把未运行的比较当负结果。迁移至少保留身份、结论、理由、范围及重要未知。

如果旧脚本还记录解析算法而新教材只说“做过分析”，方法也未充分迁移。是否需要保留代码取决于复验合同：有些统计可由清楚算法和固定输入再实现，有些复杂边缘处理最好保留准确源码。不能用教学写得流畅代替可复验性。

### 当前树退役与来源保全可以并行

某旧review退出当前树时，可在新的权威索引注明固定commit/path，使历史知识仍可追踪。某本机raw若不进Git，则要保留准确local来源和hold责任。两种保全方式不能混用：“Git里有旧报告”不保护报告依赖的未提交原件。

### 哪些发现应该交给下一次审查

一类是明显重复、已被吸收但仍有引用的过程文件；需要先修引用。第二类是一次性方法代码仍被tests导入；需要明确是否迁移tests及方法。第三类是未知来源范围；需要责任任务对账。第四类是可重建大环境或cache；需要确认活动任务和空间收益。

这些是判断类别，不是本任务生成的删除Plan，也不是准确路径的当前删除批准。S11-29只把原则教清楚，后续机械清理应拿到具体范围、保全前提和后验核验要求。

### 一个好的精简结果应让新人更容易判断

精简之后，新人应能找到运行入口、冻结身份、权威证据、教学导航和必要复现来源；不再误把历史实验current当现在候选；不再从文件大小推断垃圾；也能看见哪些hold尚未闭合。若清理后只剩源码而无法解释来源，空间变小了，工程可理解性反而变差。

同样，什么都不清理也不是天然可靠。无限累积的旧入口容易被误用，过时tests容易被当当前证书，重复合同容易出现不同解释。退役是维护的一部分，只是它需要准确事实和授权，不能靠作者直觉自动执行。
