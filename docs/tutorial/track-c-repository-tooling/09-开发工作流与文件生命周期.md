# 开发工作流与文件生命周期

[四条学习路线与术语](../00-从这里开始.md) · [本 Track 入口](01-仓库总览与核心工程文件.md)

## 一个任务怎样形成交付

### 工作流为什么反复出现这些词

软件改动的难点不只是把代码写出来，还要保证改的是批准的问题、基于正确版本、验证边界明确、别人能够审阅和接续。本项目用Main、Stage、Plan、Codex、Git和TASK_RESULT分配这些责任。

这些角色并不必须对应不同真人或不同服务。Main（项目主控）管理全局目标与接受决定；Stage（阶段）把一段目标组织成有边界的任务；Plan（任务计划）冻结执行合同；Codex工程Agent在仓库落实；Git保存可审阅的版本增量。它们也不属于比赛Agent的游戏决策链。

### 开发循环图

```text
Main：全局目标 / 授权 / 验收
   ↓
Stage：阶段问题、边界与任务顺序
   ↓
Plan：目标 + 来源 + 权限 + 受保护范围 + 验收
   ↓
Codex：核基线 → 读指定来源 → 做范围内implementation
   ↓
默认：root main串行       获准隔离：branch / worktree
   ↓                                  ↓
相关静态核验/测试 + diff + 来源与未知
   ↓
范围明确的Git交付 + TASK_RESULT
   ↓
Main review：接受 / 部分 / 冲突 / 新证据请求
   ↓
需要分支整合时merge/main；串行main则确认已有交付
   ↓
下一项被明确授权的Task（不会自动获得live或cleanup权限）
```

图示是项目[AGENTS](../../../AGENTS.md)与[Plan合同](../../project/CODEX_PLAN_CONTRACT.md)的职责整理，不把每项任务强制变成分支开发。当前默认root main串行；branch需要独立理由，worktree又需要单独理由与授权。S11-29按默认main工作，没创建新分支/工作树。

### Main为什么不直接承包全部coding

落实到文件操作：Main 给出全局接受标准，Codex 核当前源码和 diff，TASK_RESULT 把实际交付返回 review。角色可以由同一人或不同对话承担，不能混入比赛 Agent 的动作链。

这种分工怎样降低实验误判，集中读 [D09 治理设计](../track-d-project-method/09-Main、Stage、Plan与Codex为什么这样协作.md)；这里继续看任务交接时各对象如何进入 Git。

### Stage为什么要有边界

Stage 组织任务顺序，每个 Task 另列基线、写入集合、权限和验收。例如先准备 ignored source pack，再由下一 Task 写正式教程；“继续 S11”本身不增加 gameplay 或 cleanup 预算。核对实际 Task 合同后才编辑。阶段边界的理由见 [D09](../track-d-project-method/09-Main、Stage、Plan与Codex为什么这样协作.md)。

### Plan不是固定每行实现的脚本

[CODEX_PLAN_CONTRACT](../../project/CODEX_PLAN_CONTRACT.md)分三个层级：

| 层级 | 冻结/委托什么 | 执行者能怎样判断 |
|---|---|---|
| FROZEN（冻结要求） | 目标、范围、已确认事实、保护、权限、停止与验收 | 必须遵守；事实前提冲突应停受影响部分并回传 |
| RECOMMENDED（推荐） | 有证据的实现方向、可能文件、验证顺序 | 可按当前事实调整并解释理由，不能突破FROZEN |
| DELEGATED_TO_CODEX（委托执行调查） | 未知根因、位置或方案，带问题/证据/判断标准 | Evidence→Investigation→Decision→Implementation→Verification |

**教学示例：**Plan规定“修正唯一失效锚点，不改运行事实”，这是FROZEN；提示目标可能是某个中文slug（标题锚点）只是待验证建议。Codex应读真实标题并按现有Markdown规则确认，而不是机械复制Planner猜的字符串。

自主性作用于实现选择，不扩大scope（范围）。读到了一个旧test断言，不意味着本教程任务可顺便修tests；知道一个日志可以重算，也不意味着可以删除它。例如 S11-29 当时仅允许新增13篇教程，其他已跟踪文件的修改为0。

### Branch、Commit与Worktree怎样分工

Branch（分支）是一条提交线的名字/指针；Commit（提交）记录一个版本快照和父关系；Worktree（工作树）提供独立工作文件及index。工作树能支持并行编辑，分支能隔离提交增量，commit让别人比较“这次改了什么”。

```text
工作文件的编辑
     ↓ 选择本任务内容stage
暂存索引：下一次提交的准确集合
     ↓ commit
本地提交：可比较、可审阅的身份
     ↓ push
远程分支：其他参与者可取得的交付身份
     ↓ review / 必要时merge
接受的项目事实与主线状态
```

这只是操作关系。涉及 stage/commit/push/merge 的演示属于流程说明，不构成当前执行授权；实际 Git 写入遵守当前任务合同和仓库治理要求。

Git clean表示工作树没有相应未提交增量，不表示所有ignored日志已清理；push成功表示远端收到提交，不表示官方比赛上传；分支commit存在表示IN_FLIGHT_EVIDENCE，不自动成为MERGED_FACT或Main接受。

### 验证为什么跟任务类型走

文档修改检验链接、锚点、格式、来源和范围；包装修改检验身份与文件集合；解析修改检验实际归属错误；live运行才检查授权内的runtime门。项目Tier制度见AGENTS，不要求每个小任务都运行全部pytest或完整游戏。

**教学示例：**修一个Markdownfragment，如果跑游戏成功也不能证明导航正确；反过来链接全部通过也不能证明正式Agent遵循。正确验证要与失败方式一一对应。

失败还要分层：本地命令构造错且没有触发运行，是Tooling Error（工具错误）；真实动作启动后的失败按runtime合同处理；若无法确认动作是否发生，是Unknown Side Effect（副作用未知），不能当无害错误盲重试。命令退出码只是线索，语义操作才决定预算和停止。

### 真实walkthrough：S11-28的两种交付

本章选择source map推荐的S11-28，而非重新恢复S11-24历史。它结构清晰，且当前base提交可以直接核验：修一条旧导航缺陷，同时准备ignored source pack，随后S11-29消费该包写正式教学。

#### 问题

Track B正文被接受，但全仓Markdown检查发现一个更早存在的fragment失效：v7o运行记录仍链接英文 `#forensic_hold-ledger`，目标标题已经是 `FORENSIC_HOLD 台账`。此前任务不允许修改docs/project，所以返回Partial而没有越界。

#### Plan contract

S11-28冻结base `85217072f64d2463e57b224d9c7e85b078f747be`，允许唯一tracked文件的一处anchor target替换；run identity、score、session、hold、hash和历史结论都不能变。另允许把七份机械地图写到ignored `.local/scratch/s11-28-track-c-source-pack/`，不commit、不从README链接。

#### Codex execution

读取真实目标标题，确认GitHub-compatible slug，再把链接替换为 `#forensic_hold-台账`。同时在scratch准备repo/scripts/tests/experiments/local/HPL/workflow/chapter maps。两项工作分别满足“修缺陷”和“降低下一作者扫描成本”。

#### 可直接核验的Git evidence

**事实：**该历史修复提交 `1c6231de36c98e4cdae38bba95c070d8750bcf65` 的message为 `docs: repair final evidence hold anchor`，仅一个tracked文件一行替换。其[v7o记录](../../project/runs/v7o-run1-validation.md)现链接到[中文台账](../../project/FINAL_EVIDENCE_REVIEW.md#forensic_hold-台账)。提交diff没有改score或hold语义。

source pack未进入该commit，所以只看Git stat会看见一处修复，不会看见七份scratch的工作量。S11-29opening gate还要求七份文件存在并完整读取，补上本机handoff（交接）依赖。这说明Git交付和本机机械交接可以是不同对象，但两者都要记录身份与消费条件。

#### Review与next decision

用户S11-29任务将source pack准备视为已完成，并固定1c6231…为新基线。下一任务只写正式教学，不重做全仓机械盘点；当前来源若与map不一致，按源码纠正教学描述。这个例子展示“低成本机械准备→高质量解释”的任务分工，不推断任何未提供的Main聊天细节。

没有TASK_RESULT及opening gate，下一作者可能以为scratch已commit，或读取不到就重新考古；有合同后，缺包应返回Main，而不是绕过前置条件。这里七份包完整，所以教学可以继续。

### TASK_RESULT为什么不是随便总结

TASK_RESULT（任务执行结果）应能让Main回答：基于哪版做了什么、交付是哪次commit、验证哪些问题、没有验证什么、是否触发live、副作用/hold怎样、还缺什么决定。它是execution evidence（执行证据）的入口，不是个人感想。

| 字段 | Main需要它的原因 |
|---|---|
| Base/parent/HEAD | 防止旧基线或未合父链被当当前主线 |
| changed files / delivery identity | 核对是否只交付批准范围 |
| verification / limitations | 判断PASS的对象及缺口 |
| evidence paths / hold | 保持后续调查及保留责任 |
| live counts / failures / unknowns | 核对预算、重试和未知副作用 |
| decision / next recommendation | 明确返回review，不自动开始新任务 |
| execution metrics | 校准真实时间；无法读取model/effort则UNKNOWN |

结果里写“模型名称”要基于可靠执行记录，不把推荐模型当实际模型；同样，写“测试通过”要有实际执行输出，不能把历史review的数值当本次执行。

### 开发链与实验链怎样相交

开发交付的 commit 与实验检验的 Candidate/Run 可以相交，但分别验收。一次文档修改只需对应文档证据，不要求新实验；有运行证据也不能补足文件交付缺口。实验链的完整解释见 [D03](../track-d-project-method/03-实验方法与多层验证.md)。

### 保留与自查

Plan、TASK_RESULT和review的独有知识应迁移到canonical状态/合同/教学；Git保留历史提交，当前树不必永久堆积每份过程记录。但迁移前要检查引用、未决问题和来源依赖，后半部继续检查这些退役条件。

自查：S11-28提交只改一条链接，是否因此工作不完整？不能按diff大小判断。Plan要求的另一个交付是ignored机械source pack；其存在、完整性和下一任务消费是独立验收对象。反过来，写了很多scratch也不能掩盖tracked修复未完成。完成以合同为准，事实以证据为准。
### 深入练习：Main怎样审阅一个小而完整的交付

**教学示例：**合同只许新增 13 篇，额外 README 仍越界。核对 base、准确路径、diff、验证输出，再看对应 TASK_RESULT；便利性不能替范围批准。S11-28 的一行 Git 修复与七份 ignored source pack 则都在合同内，需要分别核验交付。

#### Review的三种结论如何不同

Accept、Partial、Conflict 分别报告目标已满足、尚有可交付部分与实质缺口、冻结前提冲突。S11-27 的受保护旧锚点由下一授权任务 S11-28 修复，例子已在 walkthrough 中展开；结果分类不是工作量评价。

#### 一个小TASK_RESULT该怎样写未知

把未知绑定到具体对象：无法读取的 model/effort、未执行的 runtime 验证或缺失的 raw 范围。push 是 Git 交付事实，Main 接受是 review 决定，不能互相代替。

#### 为什么交付身份比聊天中的“最新版”可靠

commit 与 base 固定可比较增量；ignored source pack 则靠准确路径及 opening gate 补足消费检查。下一 Task 据此接续，不依赖随时变化的“最新版”。后半部判断过程资产何时可以退役；治理理由另见 [D09](../track-d-project-method/09-Main、Stage、Plan与Codex为什么这样协作.md)。

Commit 保存这次可审阅的版本，TASK_RESULT 说明验证与未知。这些材料怎样进入 Git 已经清楚；接下来检查每项资产的消费者、复现需要和保留责任。任务完成本身不授权删除。

## 交付之后，材料怎样保留或退役

### 精简仓库先回答“失去什么”

Repository Reduction（仓库精简）不是把大小压到最低，而是让当前核心容易找到，同时保住必要事实、复现能力、教学知识和未决证据。Current Tree（当前树）承载正在使用及明确保留的资产；Git History（版本历史）保存已提交过的过去；Local State（本机状态）有些可以重建，有些根本不在Git里。

这章提供判断方法，没有删除、移动、归档或hold release。下列taxonomy（分类法）为 **解释**，用于教学和将来审查；不是Main批准的逐路径disposition（处置决定）。

### 九类保留/退役状态

| 类别 | 含义 | 本项目示例与前提 |
|---|---|---|
| KEEP_CORE | 当前运行/工程接口的必要来源 | Runner、依赖声明、当前使用的包装/审计工具 |
| KEEP_CANONICAL | 负责项目权威事实/决定 | CURRENT_STATE、OFFICIAL_SOURCE_LOCK、FINAL_EVIDENCE_REVIEW |
| KEEP_FOR_TEACHING | 承载独有长期学习价值 | Track A/B/C/D、代表版本GUIDE |
| KEEP_FOR_REPRODUCIBILITY | 使重要方法/结果可重算或身份可恢复 | 冻结builder、必要实验snapshot与方法代码 |
| KEEP_UNTIL_KNOWLEDGE_MIGRATED | 知识还未完整迁移，不急于删除 | 含唯一解释的旧review或调查脚本 |
| DELETE_AFTER_KNOWLEDGE_MIGRATED | 迁移后可进入明确删除审查 | 已被canonical/tutorial吸收、引用关闭的过程资产 |
| SAFE_DELETE_CANDIDATE | 已知可重建、无活动/证据依赖的低风险候选 | 确认纯生成且不被使用的cache；仍需具体授权 |
| HOLD_OR_PROVENANCE_BLOCKED | hold或来源依赖阻止删除 | held events/raw、唯一session payload、未知来源范围 |
| UNKNOWN_REVIEW_REQUIRED | 不能准确说明来源、使用者或释放条件 | v7o/v7v未知条件、未分类本机材料 |

标签可以描述主职责，也可以叠加限制。例如核心audit脚本是KEEP_CORE，某次audit输入却是HOLD_OR_PROVENANCE_BLOCKED；同名目录不能只贴一个标签就批量删除。

### 先画依赖，再决定去留

Dependency（依赖）意味着A要使用或解释B。代码import、脚本输入、test断言、Markdown链接、Run来源和review责任都可能是依赖。删除B时，A可以仍存在却不能工作或失去可审依据。

```text
运行代码 → 依赖/配置/Skills
包装器 → 冻结源 + 提交文稿 + 合同
test → 受测脚本 + fixture + 版本期待
研究结论 → 方法 + 输入身份 + 必要raw
tutorial → source链接 + 真实案例
Main决定 → canonical证据 + 尚未闭合的责任
```

**教学示例：**旧review不再被README链接，但一个research报告仍引用其中唯一Session解释。它不是“无人引用”的文件。反过来一个tutorial引用了旧脚本作为源码案例，未来若退役脚本，需要替换为可恢复的固定历史链接或迁移足够方法说明；否则教材会留下断链。

没有依赖检查，删除会把错误推迟到下次复验或阅读时才发现。有依赖检查也不自动提供授权：它只是形成可审阅的候选范围。

### Git history与current tree为什么可以不同

Git history保留历史，**不等于当前main必须永远保留每份历史过程文件**。一个重要开发阶段可以在历史提交里完整恢复，同时当前树只留下更清晰的权威总结和少量代表性来源。

什么时候旧review可以退出？至少要核对独有知识已吸收到canonical docs/tutorial、引用已修复、runtime/repro/hold依赖已解除、历史对象确实可恢复，并由任务授权准确范围。删除可以移除当前文件而不重写已推送历史；恢复历史来源则需保留commit/path身份，不只记一个模糊文件名。

**事实：**[FINAL_EVIDENCE_REVIEW](../../project/FINAL_EVIDENCE_REVIEW.md)记录S11-15已从当前树移除六份被吸收的S10过程gate review，同时research来源和历史结果仍可从Git恢复；该次清理没有改变台账hold。这是“知识迁移后减当前树”和“raw责任继续保留”并行的真实案例。

反例是从未commit的raw：Git只能恢复进入对象数据库的内容。`.local/runtime`下唯一捕获、DB row或服务log若没有受控副本，删除之后无法从Git生成。它的hash能核对找回的内容，不能找回本身。

### 六类常见对象的具体判断

#### Cache：低风险候选仍有前提

纯生成 cache 若可重建、无活动/证据依赖，可进入 SAFE_DELETE_CANDIDATE，仍需准确授权。它与源码的损失不同：前者重新计算，后者可能无法重建。机制读 [环境与缓存](07-本地工作区、环境与可重建状态.md#虚拟环境缓存与日志)；当前文档任务不清 cache。

#### One-off forensic script：重要方法可能迁移，也可能仍需复验

S08/S09 提取器可属 KEEP_FOR_REPRODUCIBILITY；独有方法未迁移就保留，知识、tests 导入、report 重算和后续脚本依赖全闭合后才进入退役审查。脚本的具体用途查 [C03](03-scripts为什么这么多以及分别做什么.md)。旧编号、任务完成和固定 Git 身份均不单独提供删除资格。

#### Historical review：结论、来源和判断边界都要迁移

迁移 review 要保留身份、判断理由、失败/未执行阶段与未知，修好引用后再退役。只复制“75.29”而丢掉单样本与 RUNTIME_ADHERENCE_FAIL，不是充分迁移；后人会错误外推。固定历史对象只能保存已提交内容。

#### Canonical source：小文件也能承担最大责任

`CURRENT_STATE`管现在状态，`OFFICIAL_SOURCE_LOCK`管官方身份，`ARCHITECTURE_DECISIONS`管架构判断，final identity/manifest管冻结提交。它们通常KEEP_CANONICAL，部分还与运行/包装合同直接相关。

权威文档也不是不能重构，但换职责和路径需要迁移事实、引用与验收，不能当“重复Markdown”普通删除。本任务明确保护全部canonical路径。

#### Held raw evidence：先闭合责任，再另行授权

### 一个教学用退役审查流程

```text
准确对象与身份
     ↓
用途/调用者/引用/唯一知识
     ↓
是否运行核心、canonical、教学或复现资产？
     ├─ 是 → 保留或先定义替代与迁移
     └─ 否/迁移已完成
             ↓
      raw/hold/来源及下游依赖是否明确？
             ├─ 未知/未闭合 → blocked或review required
             └─ 闭合 → 核对可恢复性与确切删除范围
                              ↓
                        Main/任务明确授权
                              ↓
                  精确清理 + 引用核验 + 限制记录
```

图只说明如何判断文件去留，不是删除清单或可执行指令。具体操作必须由当前任务合同授权，不能从教程中推导。

每一步为何必要？身份防删错对象；用途避免删活动组件；迁移防知识流失；来源/hold防丢独有证据；授权确保责任明确；后验检查发现断链和范围错误。只做secret scan也不替代这些判断，秘密安全与证据完整性是不同要求。

### 常见误判与修正问题

| 误判 | 更有用的提问 |
|---|---|
| “ignored，所以没用” | 为什么不共享？是否唯一raw或活动环境？ |
| “tracked，所以永远保留” | 当前职责是什么？历史是否足够、引用是否迁移？ |
| “COMPLETE，所以raw可删” | 哪个任务完成？release condition和依赖闭合了吗？ |
| “Git能恢复所有东西” | 这个确切文件是否commit过、哪份bytes？ |
| “一份摘要包含全部知识” | 是否保存了方法、身份、未知和未运行阶段？ |
| “大文件先清理最划算” | 空间收益对应什么不可恢复风险？ |
| “历史负结果没有价值” | 是否避免重复失败或说明真实部署边界？ |
| “tutorial不参与game，可删” | 是否承载用户长期学习与知识迁移？ |

### 深入练习：怎样判断“知识已迁移”是否充分

**TEACHING EXAMPLE｜教学示例**：旧 review 有分数、根因假设和未执行阶段，新文档只复制分数，仍缺判断边界。复杂 parser 若仍需复验，仅写“做过分析”也不足以替代准确源码。迁移充分性由独有知识与复验合同决定。

#### 当前树退役与来源保全可以并行

已提交 review 可以固定 commit/path 保全；未提交 raw 依赖本机来源与 hold。两种方式分别确认，“Git 有报告”不能保护它依赖的 ignored 原件。

#### 哪些发现应该交给下一次审查

后续候选可按重复但仍有引用、方法仍被导入、来源范围未知、可重建但仍在使用四类分流。它们是待审问题，不是当前删除清单；具体 Task 须提供范围、保全前提和后验核验。

#### 一个好的精简结果应让新人更容易判断

精简后仍应能找到 core、冻结身份、权威证据、教学和必要复现来源；旧入口及重复合同也应得到准确退役。空间减小和事实可理解性都要检查，不能以“全部保留”或“全部删掉”替代逐对象判断。
