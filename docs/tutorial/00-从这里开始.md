# 从这里开始：理解 CareerSim 的四条路线

CareerSim 是一个让 Agent（智能体）在模拟职业环境中作选择的项目。一局目标跨度为 48 个月，选择会影响资源、成长和后续机会。本项目采用一个 Agent 配合多个 Skill（技能模块）的路线：模型负责判断，工具负责把选择交给游戏；开发者还需要确认运行身份、验证规则是否被遵循，并保留可复核的结果。

LLM（大语言模型）根据输入文本生成输出；Runtime（运行时）是这些规则、模型和工具实际工作的环境与过程。写好一份规则文件，与在运行时用它完成行动，需要分别确认。

这套教程把这些问题分成四条路线。你可以先按自己的问题进入，无须顺序读完全部文件。

## 决策与执行中的名词

**Agent（智能体）** 是能结合模型、规则、观察与工具持续处理任务的系统。CareerSim 中，唯一比赛 Agent 决定选择并提交动作；三份 Skill 分别帮助整理事实、规划和审风险，不意味着有三个额外玩家。

**Instruction（运行指令）** 规定跨越整局的行为合同，例如先观察、生成候选后审查、动作后取得新状态。**Skill（技能模块）** 展开某项职责的方法。本项目的 `structured-state-board`、`rolling-planning`、`risk-review` 主要是供模型读取的规则文本，不能把一次文件读取当成一次正确应用。

**Tool（工具）** 是读取或改变外部环境的接口。模型写“选择休息”只是文本；请求 `take_action` 才是提交动作。**Tool calling（工具调用）** 是执行层把模型提出的工具名与参数变成请求的过程；请求仍可能被拒绝。`observe` 取得公开状态，fresh observe（新鲜观察）要求这份状态适用于当前会话和当前决策时刻。成功回执仅能证明它明确报告的结果，不自动包含下一步需要的完整状态。

**CareerSim** 是这里的赛题和模拟职业任务。实际游戏环境由 `career-emulator` 提供。**JiuwenSwarm** 是承载 Agent 运行的框架；项目采用 Single Agent（单智能体）路线，框架支持其他模式不能证明本项目测试过它们。

**AgentServer（Agent 服务）** 接收模型任务并将运行事件传回调用者。**MCP（Model Context Protocol，模型上下文协议）** 连接工具接口，使 Agent 能通过服务使用模拟器工具。MCP 不是替模型作决定的玩家，也不负责凭空生成正确策略。

**Runner（运行驱动器）** 指本仓库 `career_sim_runner/` 的准备、安装、任务驱动、记录与报告代码。它通过 WebSocket（双向消息连接）与服务通信；游戏动作通过 Agent 的 MCP 工具链执行。因而“Runner 发任务”“模型提出选择”“模拟器改变状态”是不同步骤。详细通信关系见 [B 的服务章](track-b-system-runtime/04-JiuwenSwarm、AgentServer与MCP分别是什么.md)。

## 身份、材料与一次实验

**Candidate（候选方案）** 是准备拿去验证的一套行为身份，可包含 Instruction、Skills、配置和运行相关选择。**Run（运行样本）** 是它的一次具体执行轨迹。**Experiment（实验）** 围绕一个问题组织有界验证，可以用多个 Run，也可以只做静态或可行性检查。v8a 的两局分别为 72.65 和 59.00，同一冻结行为身份并不会使每局轨迹相同。三个概念的完整例子见 [D 的身份章](track-d-project-method/02-Candidate、Run、Experiment到底有什么区别.md)。

**Submission（提交材料）** 是按输入合同组织的文件包，并不意味着已上传。**Manifest（清单）** 在这里用 JSON 描述名称、模式与指令等元数据。`manifest.json` 是供程序读取的材料入口；它不是比赛成绩证明。布局检查与安装位置的区别见 [B 的校验与安装](track-b-system-runtime/03-Submission校验与Skill安装.md)。

**Session（会话）** 表示某条持续交互的身份。模型驱动会话与游戏会话可以有不同 ID；报告必须绑定正确游戏，不能因为文件最新就认定分数属于它。**Score（分数）** 是特定来源、口径和样本的结果。quantitative、加权字段、生存月数及等级不能互相替填，也不能把本地分数写成官方隐藏测试成绩。

**Current checkout（当前检出）** 是你此刻打开的版本文件。**Frozen submission package（冻结提交包）** 绑定特定历史来源与文件字节；它可能不同于当前检出。本项目当前 v8a 四 Skill 工程状态与最终 exact-v6 三 Skill 包不同。最终包身份以[最终交付报告](../final-report/04-最终方案、候选选择与工程交付.md)和[权威身份文件](../project/FINAL_SUBMISSION_IDENTITY.json)为准，不能从最新 `skills/` 目录反推。

## 验证、证据与文件保留

**Static Validation（静态验证）** 检查布局、格式、代码或文本合同。**Runtime Validation（运行时验证）** 检查真实运行路径上安装、发现、加载、应用等是否发生。**Gameplay Validation（对局验证）** 关注游戏执行与结果。它们不是一个从文件到收益的自动保证；每个检查只支持自己检查的对象。

**Adherence（运行遵循）** 检查轨迹有没有按合同行动。例如完成 48 个月，不自动证明压缩后重读了 Skill。exact-v6 的一个完整样本同时记录为 `VALID_48M_COMPLETION` 和 `RUNTIME_ADHERENCE_FAIL`；完成与遵循是两个判断。验证阶梯在 [D 的方法篇](track-d-project-method/03-实验方法与多层验证.md)。

**Evidence（证据）** 是支持一个具体命题、能追溯来源的材料。**Artifact（工件）** 是开发或运行留下的产物；一个输出文件只有绑定问题和来源后，才知道它能否用于举证。**Raw Evidence（原始证据）** 如原始事件与运行文本，保留当时信息。**Derived Evidence（派生证据）** 如解析摘要或审计表，经过选取和处理，不能补造原件没有的内容。

**Forensics（取证分析）** 根据保留记录重建发生的事件、排除错误归因。例如 v7i 曾输出来自旧 v7g 会话的成绩报告，文件存在不能证明新局有该成绩。案例与结果分类见 [D 的取证与负证据](track-d-project-method/06-Forensics、失败实验与负证据.md)。**Provenance（来源链）** 把材料关联到版本、Run、Session、时间窗与处理过程；内容 hash（哈希）能检查字节指纹，却不能替代来源文件。

**Hold / FORENSIC_HOLD（取证保留）** 是在调查、复核或依赖尚未闭合时暂时阻止清理的责任状态。摘要完成或文件已有 hash 都不会自动解除它。当前权威台账有 20 个具名 active/pending 项：18 `KEEP_ACTIVE`、2 `UNKNOWN_REVIEW_REQUIRED`、0 可释放；不确定的 aggregate 与 v6 raw 状态另有说明。准确范围及解除条件查[证据台账](../project/FINAL_EVIDENCE_REVIEW.md#forensic_hold-台账)和 [C 的证据生命周期](track-c-repository-tooling/06-artifacts、Raw-Evidence与证据链.md)。

**Worktree（工作树）** 让同一个 Git 仓库有多个独立检出目录与暂存索引，共享版本对象；它可隔开代码编辑。两个工作树仍可能连接同一个服务、数据库或已安装 Skill，因此工作树不能单独证明 CareerSim 运行隔离。**Canonical（权威来源）** 表示某个文档承担特定事实的正式归属，如状态、身份或证据结论；它与 Git 是否跟踪、文件大小无关。本机未提交 raw 仍可能是唯一证据，教程只是讲解层。

## 怎样区分讲解与事实

教程用 **FACT / 事实** 表示来源直接支持的内容，用 **INTERPRETATION / 解释** 表示对设计关系的理解。**HYPOTHESIS / 假设** 需要验证，**TEACHING EXAMPLE / 教学示例** 是构造场景，不冒充历史运行；**UNKNOWN** 表示当前证据不足。自然语言中也会直接说明这些边界，不必把每个段落都读成审计标签。

目前最终方案已冻结，但官方上传为 `NOT PERFORMED / NOT PROVEN`，平台分数和 hidden-test transfer（隐藏测试迁移）为 `UNKNOWN`；S11 仍为 `ACTIVE`。阅读教程不会授权安装、服务启动、调用模型、对局或清理。文中可能产生副作用的命令均作教学说明；当前文档重构任务不执行这些操作。
