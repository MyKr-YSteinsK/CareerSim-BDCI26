## 从证据组织一个有界实验

一个实验的价值，不只在于最后有没有高分，还在于它是否消除了一个重要的不确定性。CareerSim 的研发逐渐形成了“先有证据，再提出有边界的假设”的顺序。

先读 [D02 的 Candidate / Run / Experiment](02-Candidate、Run、Experiment到底有什么区别.md)。先看下面的证据循环和两个案例，后半部逐层检查验证结论；替代路线的完整边界在[路线研究](07-Reviewer、Memory、Helper、Controller与Simulator路线.md)。

### 循环中每一步在做什么

**Evidence（证据）** 是可核对的观测或来源；**Hypothesis（假设）** 是对问题和潜在改进的待验证判断；**Experiment（实验）** 用明确方法检验判断；**Decision（决策）** 决定采用、继续、修改、停止或返回审查；**Implementation（实现）** 把已授权的决策落实成代码或合同。

**事实：** 项目用证据、假设、实验和决策组织架构变化，Plan 要冻结范围、权限、所需证据与验收边界；实现细节不明确时交由执行者调查。[实验复盘](../../project/EXPERIMENT_RETROSPECTIVE.md) · [Plan 合同](../../project/CODEX_PLAN_CONTRACT.md)

~~~text
Evidence → Hypothesis → Experiment → Decision → Implementation
    ↑                                              │
    └────────────── New Evidence（新证据）───────────┘

Decision 可以是 ADOPT / CONTINUE / STOP / RETURN_FOR_REVIEW
STOP 不要求先创建一个新的正式 Candidate。
~~~

**解释：** 这不是要求每个任务按五个标题机械排版。它要求在顺序上分清：问题依据是什么、哪些还是假设、检查实际上做了什么，以及实现获得了多大授权。

### 正向 walkthrough：v6 审计如何转化为 v6b 修复

#### Evidence：完成与遵循出现分离

**事实：** v6 完整运行有 203 次 action attempts（动作尝试），202 次成功状态改变，1 次参数格式拒绝。成功动作之后都有新观察。另一方面，运行漏掉必要标记，普通 Story（情节决策）在没有新证据时重新 deliberation（权衡），存在 Energy 多选参数问题，CTRL（控制标记）与动作无法可靠一一绑定。[v6 运行记录](../../project/runs/v6-run1-validation.md)

两次压缩 epoch（时期）之后没有重读 Skill 也是记录事实。原报告用 S06-25 的 recovery definition（恢复定义）评估该缺口；该定义与原冻结合同之间的时间关系需要保留，不能把后续更明确的恢复条款倒写成最初已完全定义的合同。

#### Hypothesis：先解决可执行的合同缺口

**HYPOTHESIS｜假设：** 如果把动作格式、决策关闭和动作绑定标记写得更明确，能够降低这些类型的协议偏离。该假设只涉及执行正确性；它没有预先承诺改善游戏策略或终局分数。

这个范围有两个好处。首先，问题来自实际轨迹，不是凭“再加一点规则可能有用”展开。其次，修复效果可以用格式和合同检查验证到一部分，无需先假定新局一定表现更好。

#### Experiment / Implementation：建立 v6b 静态版本

**事实：** S06 closeout 记录 v6b 的静态修复包括 action-linked CTRL、DECISION_CLOSED、Energy 单个整数逐次提交，以及 compression 后的 Skill 恢复重读。它没有重设计策略，也没有新的 runtime validation（运行时验证）。[S06 收口](../../project/S06_CLOSEOUT.md)

因此，这个案例的“正向”含义是：问题得到可追踪的合同修复，并通过当时静态范围的检查。它不表示这套修复已经证明模型全程遵循，更不表示它赢过原 v6。

#### Decision：接受有限结果

**事实：** Main 对 S06 的接受是 PASS_WITH_KNOWN_RUNTIME_LIMITATION。原 v6 样本的成绩和运行缺陷保持原身份；v6b 的静态状态不继承 v6 的 75.29。[S06 收口](../../project/S06_CLOSEOUT.md)

**解释：** 这避免了常见“修完 bug 就把旧高分当成新版验证”的归因错误。新的内容需要新的证据，但新证据可以按授权分阶段获得，不需要无界扩大验证。

#### New Evidence：还有什么未证明

**UNKNOWN｜当前证据不足：** v6b 在真实长程运行中的遵循率、稳定性和分数效应。这些缺口应该留在结果中，而不是被“静态修复完成”抹去。

这个 walkthrough 教的是如何把失败转成精确工程工作：事实定位问题，假设限定修复，静态验证回答可回答的部分，Main 接受时保留运行限制。

### 负向 walkthrough：Simulator 在比较宏策略之前停止

#### Evidence 与问题

**事实：** 历史策略挖掘没有形成足够安全的新策略信号。S10-22 转向 prospective（前瞻式）public-only（仅公开信息）Dev 模拟，研究能否用可复现的确定性控制来比较宏策略。[策略挖掘](../../project/research/S10-21_REVIEW_WINDOW_STRATEGY_MINING.md) · [Simulator 研究](../../project/research/S10-22_SIMULATOR_POLICY_SEARCH.md)

#### Hypothesis 与必要前提

**HYPOTHESIS｜假设：** 若底层 Story nuisance policy（作为比较基础的情节控制策略）具有足够胜任能力，那么固定种子与公开输入可能帮助比较更上层的策略配置。

这里存在 prerequisite（前提）：基础控制不能频繁提前终止，以致宏策略还没有施展窗口。这个前提不成立时，比较得到的主要是基础语义控制缺陷。

#### 冻结 Experiment

**事实：** 研究预先冻结 12 个宏配置、Story 规则、种子和停止标准。基线门禁要求至少 8/16 次完整完成；实际仅 B0 基线进入 16-seed 检查。policy（策略）输入不包含最终 score、隐藏计数或未来结果，score 留在 evaluator（评估端）。[Simulator 研究](../../project/research/S10-22_SIMULATOR_POLICY_SEARCH.md)

把门禁写在结果之前，是为了不在看到低分后临时降低合格标准。公开信息边界同时防止模型或脚本用局后答案拟合策略。

#### 实际 Evidence

**事实：** 16 次基线运行只有 2/16 自然完成 48 个月。速度足够，但冻结语义基线未达到胜任门禁；全部低分/早终局留在记录，没有反复改 Story 规则直到门禁通过。

#### Decision = STOP

**事实：** 决策是 SIMULATOR_POLICY_SEARCH_NOT_FEASIBLE。macro screening（宏配置筛选）、confirmation（确认）和 planned holdout（计划留出验证）都未执行；128-seed holdout 仍未使用，没有选出宏策略赢家。[Simulator 研究](../../project/research/S10-22_SIMULATOR_POLICY_SEARCH.md)

**解释：** STOP 是高质量结果，因为它阻止把未经有效比较的宏策略写进正式 Candidate。失败的是当前比较实现的可行性，不是所有宏策略被证明无优势。

### 为什么这两个案例属于同一种方法

| 环节 | v6 → v6b | Simulator |
|---|---|---|
| 起点 | 运行协议缺口 | 历史挖掘信号不足 |
| 待验证判断 | 明确合同能解决一部分缺口 | 胜任基础控制能支持宏比较 |
| 实际证据 | 静态修复与合同检查 | 16 次冻结基线检查 |
| 决策 | 接受有限修复，运行限制保留 | 前提失败，停止后续比较 |
| 没有证明 | 全程遵循、分数收益 | 宏策略优劣、hidden transfer |

正向案例不应夸大，负向案例不应贬低。它们分别把决策推进到证据允许的位置。

### 怎样设计一份有用的实验合同

**解释：** 在开始前，至少说清问题、现有证据、假设、对象身份、允许干预、观察窗口、判定规则和停止条件。对长程 Agent，还应列明技术失败与 unknown side effect（副作用不明）的处理。

不是检查越多越好。比如当前任务只是文档，运行模型无法帮助证明链接正确；如果要研究安全只读 Reviewer，则机械权限边界是前提，决策质量测试应放在前提之后。

**教学示例：** “多加 Reviewer”可以改写为三个问题：它是否能被正式路径注册？是否机械排除动作修改权？在这些前提通过后，独立建议是否修正错误？每个问题有不同证据，不应让第三个问题的吸引力跳过前两个。

### 第三个接缝：Reviewer 为什么先查可部署性

**事实**：[Reviewer 研究](../../project/research/S10-19R1_SUBAGENT_FEASIBILITY.md) 先检查冻结路径的注册与权限，机械只读隔离未成立，质量阶段未运行。它在这里说明 experiment dependency（实验依赖）：后续收益检查依赖先前安全门禁，不能因好建议的吸引力跳过部署前提。

完整测试范围、`REVIEWER_NOT_SAFELY_DEPLOYABLE` 和非结论集中在 [D07](07-Reviewer、Memory、Helper、Controller与Simulator路线.md)。上面的 Simulator walkthrough 则展示同一依赖设计怎样产生 STOP 和未运行阶段。

### 把假设写成可反驳的句子

**解释：** “方案更聪明”缺乏可检查对象。“压缩后，模型在下一次动作前取得新观察并重新读取三个来源 Skill”给出了事件与顺序，能查到发生或未发生。

假设也应包含适用范围。“当前 frozen path 能部署机械只读 Reviewer”在一个路径上可以被否定；“Reviewer 永远没用”范围过大，当前实验没有能力回答。

**教学示例：** 从 v6 的证据提出“显式 action-linked marker 会改善可配对性”，适合先检查语法、事件身份与 parser 接口。从同一证据直接提出“这会增加终局成绩”，跨过了多个未验证接缝。后一判断可以保留为更远的假设，不能作为当前修复成功条件。

### 实验中的失败判定不能靠临时愿望

**解释：** 开始前应明确哪些结果否定前提、哪些使结果无法定论。例如，基础控制自然早终局可以否定预先设定的胜任门禁；输出 pipe（管道）编码损坏可能只说明装置坏了。二者若混算，门禁就不再回答原问题。

**事实：** Simulator 先修复 ASCII transport（传输编码）与冷/热初始化差异，再保留政策冻结和 adapter refreeze（适配层再冻结）；最终 16 次有效基线检查没有技术失败，但完成率门禁仍失败。[Simulator 研究](../../project/research/S10-22_SIMULATOR_POLICY_SEARCH.md)

区分 transport repair（传输修复）与 policy change（策略修改），才能使门禁仍回答原冻结假设。路线最终落点集中在 [D07](07-Reviewer、Memory、Helper、Controller与Simulator路线.md)。

### 实验结束时怎样写结论

结论应包含实际通过的层次、结果适用范围、未运行的条件阶段和剩余未知。“零调用”可以是本任务计数，但不能写成某工具实测零延迟、零成本；没有测量的能力应写 NOT_MEASURED（未测量）。

**解释：** 最终实现是决策的后果，不能替代决策依据。一份漂亮代码、一份完整报告或一个高分，都只有回到明确问题之后，才知道其研究价值。

v6b 的静态修复与 Simulator 的停止决定都有价值，但价值落在不同验证层。要准确陈述结果，还需要把“材料存在”到“隐藏测试迁移”之间的每个命题分开。

## 实验结果通过了哪一层验证

“验证通过”必须带对象。文件校验通过，是文件满足结构合同；运行完成，是某次执行走到终局；行为遵循通过，是检查窗口里的动作与合同相符。它们之间需要证据连接。

本章用 Validation Ladder（验证阶梯）组织这些判断。**解释：** 这是一种教学分组，不是仓库新增的官方评级标准，也不是必须严格按时间顺序发生的流程。例如，分数已经出现时，adherence 审计仍可能失败。

### 十一层：每一层保留自己的问题

~~~text
file exists（文件存在）
  ↓ schema / static valid（结构与静态有效）
  ↓ installed（已安装）
  ↓ discovered / loaded（已发现 / 加载）
  ↓ runtime applied（运行中实际应用）
  ↓ gameplay completed（对局完成）
  ↓ behavior adhered（行为遵循）
  ↓ observed score（观测分数）
  ↓ repeatability / stability（重复性 / 稳定性）
  ↓ causal improvement（因果改进）
  ↓ hidden-test transfer（隐藏测试迁移）

箭头表示需要进一步证据；不表示上层 PASS 自动推出下层 PASS。
~~~

#### File exists：存在

看到一个 SKILL.md，只能确认路径上有文件。它可能内容错误、未安装，或者属于历史教学快照。

**事实：** 七个历史代表版本有可恢复原件；版本索引同时明确区分 exact configuration（精确配置）是否有 runtime evidence（运行证据）。v5、根 v7、v7c 的对应条目没有精确归属的完整运行证据。[版本索引](../../skill-evolution/00-版本索引.md)

#### Static valid：静态有效

Static Validation（静态验证）检查结构、路径、合同或特定代码逻辑。它可能发现 manifest（清单）遗漏、输入格式不合法、输出要求互相冲突。它不观察长程模型是否按要求执行。

**事实：** v6b 修复了执行合同并完成静态检查，但没有新 runtime validation。不能给它继承原 v6 的运行成绩。[S06 收口](../../project/S06_CLOSEOUT.md)

**教学示例：** “验证器确认 Energy 参数应是整数”与“模型实际每次都发整数”是两个命题。静态 PASS 可以阻止错误配置进入下一阶段，不能取代第二个命题的轨迹检查。

#### Installed：已安装

Installation（安装）让目标运行位置具备所需内容。必须检查目标内容，而不仅是安装命令返回成功。目标目录身份与源目录身份也应对应。

**事实：** Runtime Contract（运行合同）把源身份、安装、发现与应用分开管理；工作树代码隔离不自动证明 shared runtime（共享运行时）隔离。[运行合同](../../project/AGENT_RUNTIME_CONTRACT.md)

这一层不能证明服务加载了最新内容，也不能证明后续没有被别的任务覆盖。安装副作用是独立授权动作；本轮教材没有执行安装。

#### Discovered / Loaded：已发现与已加载

Discovery（发现）表示运行系统能够识别入口或工具；Loaded（加载）表示组件被读入相应上下文或运行结构。文件在目录里不等于框架注册了它。

**事实：** Reviewer 研究发现 verification factory（验证智能体构造函数）存在，但冻结 agent adapter（智能体适配层）没有把该 reviewer 注册为可部署路径。构造能力的代码存在不能代替注册证据。[Reviewer 可行性](../../project/research/S10-19R1_SUBAGENT_FEASIBILITY.md)

Skill 初始读取也只定位某个时间点。之后压缩、恢复或执行绕过，仍需另查。

#### Runtime applied：运行中应用

Applied（已应用）需要行为证据：组件的输入、输出或动作约束在实际窗口中发挥作用。不能只看 Instruction 声明“必须使用”。

**事实：** v6 运行记录保留了一个 Risk RECONSIDER（重新考虑）触发案例；S06 closeout 接受局部机制证据，但不把它当成整局收益的因果证明。[v6 记录](../../project/runs/v6-run1-validation.md) · [S06 收口](../../project/S06_CLOSEOUT.md)

一次触发证明该案例发生，不能证明每个风险窗口都触发，更不能证明选择优于未触发方案。应用程度应按窗口和检查标准描述。

#### Gameplay completed：对局完成

Completion（完成）检查自然终局、有效成绩与 scored survival months（成绩记录的存活月数）。显示月份不应直接当成完成月数。

**事实：** v6 最后行政状态可显示 M49，但成绩口径是 survival 48m。v7m 停在 fresh M20，仍存活，没有自然终局或终局分数。[v6 记录](../../project/runs/v6-run1-validation.md) · [v7m 取证](../../project/reviews/S07-47_V7M_M20_PARTIAL_RUN_FORENSIC_REVIEW.md)

不要把“最后看到 M20”改写成“完成 20 个月”，也不要为部分运行填入预估 final score。

#### Behavior adhered：行为遵循

Adherence 审查模型和执行链是否真的满足合同。它通常同时需要工具序列与语义证据：有没有 observe、风险判断是否基于新事实、标记是否对应动作、压缩后是否恢复。

**事实：** S08-09 确认 take_action 回执只有 success/error，不能替代 public observation（公开观察）；该被审计局存在 18 个缺失 observe 的动作边界，属于真实执行违规。[运行合同取证](../../project/reviews/S08-09_RUNTIME_CONTRACT_ADHERENCE_FORENSICS.md)

语法标记通过也不能自动证明语义遵循。marker（标记）可能齐全，而 Board 内容仍旧、Delivery 判断仍没有实际交付证据。

#### Observed score：观测分数

Score（分数）首先需要 Provenance（来源链）：当前 Run、session、Candidate 和有效 receipt（回执）的绑定。否则只是某个文件里的数字。

**事实：** v7i 首次故障输出了旧 v7g session 的分数，该数字被排除出 fresh-run（新运行）归因；后来 replacement（替代运行）另有 Main raw re-audit（原始材料复审）。[stale-score 取证](../../project/reviews/S07-39_PROVIDER_CONNECTIVITY_FORENSICS.md) · [替代运行](../../project/runs/v7i-run1-replacement-validation.md)

即使绑定正确，分数仍只描述该轨迹。quantitative 与 competition_partial 是不同字段，不能互换、相加或把后者写成官方 hidden score。

#### Repeatability / Stability：重复性与稳定性

Repeatability（重复性）关心相同身份和规定条件下能否重复观察；Stability（稳定性）关心结果在多种相关轨迹中是否可靠。

**事实：** v8a 有两个完整样本，72.65 与 59.00；exact-v6 只有一个被接受的完整样本。项目不据此宣称稳定 75+。[最终证据审查](../../project/FINAL_EVIDENCE_REVIEW.md)

同种子重复得到同轨迹可以检查某个模拟路径的复现，却不等于新种子稳定。重复安装可以检查部署过程，却不等于策略稳定。这些“重复”对象要写清楚。

#### Causal improvement：因果改进

Causal Improvement（因果改进）要求能够把改动与结果区别于其他解释。样本数量、干预控制、比较条件和运行身份都影响这种判断。

**事实：** 历史 strategy mining 存在机会、Level、tenure（任职时长）、资源与前序轨迹混杂，结论 STRATEGY_SIGNAL_WEAK。[挖掘报告](../../project/research/S10-21_REVIEW_WINDOW_STRATEGY_MINING.md)

不能用“多用 Network 的局晋升多”直接推出普遍多用 Network。该动作可能只是更好机会或资源条件的伴随现象。

#### Hidden-test transfer：隐藏测试迁移

Transfer（迁移）需要未被研发反复利用的新环境证据。Local Dev（本地开发集）结果并不自动回答 official hidden Test 的问题。

**事实：** 官方上传未执行/未获证明，platform score（平台成绩）与 hidden-test transfer 都是 UNKNOWN。[官方来源锁](../../project/OFFICIAL_SOURCE_LOCK.md) · [最终方案审阅](../../project/FINAL_SOLUTION_REVIEW.md)

遵守公开信息边界、保留负结果、限制试分，有助于降低误判，但仍不是迁移已成功的证据。

### 怎样审查一句“4 passed”

**教学示例：** 设想一个执行结果写“4 passed”。在看数字之前，应问四个检查各自输入什么、assert（断言）什么，以及调用了哪些实际组件。

如果四个检查覆盖非法参数、路径解析、标记解析和清单成员，它们证明的是这些合同在测试输入上成立。它们没有观察模型在 48 个月里保持事实新鲜度，也没有观察隐藏评测。

如果检查使用 fixture（受控装置）代替 shared service，结果仍可能非常有价值：它能准确验证某个 guard（守卫条件）或 callback。但结果必须带“fixture”边界，不能换成“真实服务的所有行为都已通过”。

**事实：** Reviewer 的离线检查使用提取的实际函数与 inert sentinel（不触发真实动作的哨兵对象）；Helper / Memory 使用隔离实际工具或回调。报告都保留了 shared registry 或模型行为尚未测量的边界。[Reviewer](../../project/research/S10-19R1_SUBAGENT_FEASIBILITY.md) · [Helper](../../project/research/S10-19R3_NATIVE_CONTROL_SURFACE_AUDIT.md) · [Memory](../../project/research/S10-19R2_MEMORY_FEASIBILITY.md)

**解释：** 测试数量不是证据强度的快捷指标。一个精确击中故障机制的检查，可能比许多不相关检查更有价值；一个完整游戏也不一定覆盖压缩恢复或特定风险触发。

### 验证窗口与覆盖率必须有分母

**解释：** “风险门全部通过”需要说明全部是什么：全部动作、所有触发窗口，还是所有可解析标记？“没有违规”还要区分确实检查没有问题，和材料缺失导致无法检查。

同样，marker coverage（标记覆盖）至少需要定义唯一动作、去重、绑定和缺失策略。若一个工具调用同时出现在 event 与 delta 里，把它当两次会改变分母。

**事实：** v7m 取证按 kind/tool_call_id 去重；v6 的 CTRL 形似文本无法认证动作绑定；v8a 两个样本 parser 对邻接格式的接受不同。[v7m 取证](../../project/reviews/S07-47_V7M_M20_PARTIAL_RUN_FORENSIC_REVIEW.md) · [v6 记录](../../project/runs/v6-run1-validation.md) · [v8a 样本一](../../project/runs/v8a-full-horizon-sample1.md)

这些案例提醒我们：覆盖率首先是某个测量定义的结果。定义正确并且来源充足时，它才能回答实际遵循问题。

### 两个轴，避免“完成就全通过”

| 运行结果轴 | 合同轴 | 合法表述 |
|---|---|---|
| v6 有效 48m 完成 | adherence FAIL | 保留真实分数，同时保留执行缺陷 |
| v7m 技术部分局 | 局部序列可以审计 | 保留 84 次成功动作证据，不造终局成绩 |
| 静态 Candidate | 尚无实际应用证据 | 只标静态验证状态 |

**解释：** 一个成熟报告应该允许这些组合存在。强迫所有信息压成一个 PASS/FAIL，会让“成绩差”“调用断开”和“规则没执行”失去各自意义。

需要理解实际安装、MCP 和 Runner 细节，阅读 [Track B 运行链](../track-b-system-runtime/07-工程排障与完整运行链复现.md)。本章用于解释这些检查为何不能互相代替。
