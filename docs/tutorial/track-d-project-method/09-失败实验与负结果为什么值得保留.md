# 09｜失败实验与负结果为什么值得保留

**Negative Result（负结果）** 是研究没有支持预期判断时留下的结果。它可以缩小搜索范围、阻止不安全部署、揭示比较方法的问题。前提是准确描述“哪件事没有得到支持”。

**INTERPRETATION｜解释：** “失败”若没有对象，会把未测量、技术故障、低分和可行性门禁混为一谈。下一位开发者可能因此重复无信息工作，或者错误关闭有价值方向。

先读 [D08](08-Forensics为什么成为项目的重要部分.md) 学会重建事实。本章集中区分结果类型；每条替代路线的测试深度与部署结论查 [D10](10-Reviewer、Memory、Helper、Controller与Simulator路线.md)。

## 六种标签有不同含义

| 类型 | 实际判断 | 真实项目例子 | 不能推出 |
|---|---|---|---|
| Unsupported improvement（未支持改进） | 没有足够证据确认收益 | 后期加固未形成稳定 75+ 突破 | 所有改动无价值 |
| Technical failure（技术失败） | 执行链在可比较结果前中断 | v7m M20 部分局 | 该 Candidate 会自然死亡 |
| Feasibility failure（可行性失败） | 后续研究必要前提不成立 | Simulator 基础胜任门禁失败 | 宏策略比较已失败 |
| Weak signal（弱信号） | 有观察，但不足以支持部署 | Controller / strategy mining | 方法逻辑完全无用 |
| Inconclusive（无法定论） | 不能区分关键解释 | v7m 连接根因 | 猜测的根因已成立 |
| Not tested（未测试） | 尚未执行相应研究 | Team / Swarm | 已测试而失败 |

**FACT｜事实：** 表中路线与结论分别见 [实验复盘](../../project/EXPERIMENT_RETROSPECTIVE.md)、[v7m 取证](../../project/reviews/S07-47_V7M_M20_PARTIAL_RUN_FORENSIC_REVIEW.md)、[Simulator](../../project/research/S10-22_SIMULATOR_POLICY_SEARCH.md)、[Controller](../../project/research/S10-20_PROMOTION_WINDOW_CONTROLLER.md)。

这些是教学分类，不是一个所有项目通用、按优劣排列的结果等级。

## 为什么 Provider 错误不是策略失败

**FACT｜事实：** v7i 的历史 Provider 异常发生在有效 HTTP 响应之前，且输出存在旧成绩风险。没有新局轨迹与正确分数绑定，不能用该报告评价策略。[Provider 取证](../../project/reviews/S07-39_PROVIDER_CONNECTIVITY_FORENSICS.md)

**INTERPRETATION｜解释：** 这类失败首先告诉你“本次运行没提供合格策略样本”。它仍然提供部署可靠性与归因风险信息。把它记成零分会制造一个未发生的游戏 outcome（结果）；把它静默删掉又会隐藏工程不可靠性。

MCP（模型上下文协议）注册失败也需要相同思路。注册/发现门禁失败时，尚未观察正式 Agent 的动作策略；不能说风险 Skill 已被游戏证明无效。项目早期加载与应用需要分开举证的合同，正是为了避免这种跳跃。[运行合同](../../project/AGENT_RUNTIME_CONTRACT.md)

## Schema rejection：拒绝发生在什么边界

**FACT｜事实**：[v6 运行记录](../../project/runs/v6-run1-validation.md) 中一次 Energy 格式拒绝发生在状态改变前，另外 202 次成功动作有新观察。这里归为执行缺陷，不记成成功动作，也不直接评价某个 Skill 的策略收益。

参数形状与回执细节查 [B03](../track-b-system-runtime/03-Submission、Manifest与Skill校验.md) / [B07](../track-b-system-runtime/07-从模型决定到Tool调用再到新状态.md)。同一低分可能涉及多种原因，分类要绑定实际发生的边界。

## 自然低分不能自动变成技术失败

**FACT｜事实：** v7q 记录 26.80 /18.76/24m/E/L1，属于自然 M24 终局；它与 v7m 没有最终成绩的技术部分局不同。[运行历史](../../project/RUN_HISTORY.md) · [最终证据审查](../../project/FINAL_EVIDENCE_REVIEW.md)

**INTERPRETATION｜解释：** 如果只接受高分为“有效”，低分都被改成“异常”，选择偏差会被流程制度化。自然低分可以提示策略风险，但不能单凭终局结果定位某一句规则为根因。

## Weak signal 为什么仍有价值

**FACT｜事实**：[Controller 报告](../../project/research/S10-20_PROMOTION_WINDOW_CONTROLLER.md) 的工具状态持续性工作，24 个 replay cases 中仅一个 state-level correction、8 个 UNKNOWN，信号不足，未创建 v15。

**INTERPRETATION｜解释**：保存“状态机制可用、决策信号弱”比一个笼统 FAIL 更有定位价值；下次问题应针对语义缺口。完整协议与停止边界集中在 [D10](10-Reviewer、Memory、Helper、Controller与Simulator路线.md)。

## No deployment 不等于 idea worthless

**FACT｜事实**：Helper 的 `DETERMINISTIC_HELPER_CHALLENGER_SUPPORTED` 仅支持 isolated tool-level，尚无正式 Candidate 部署；Reviewer/Memory 在各自冻结前提停止。三者不能都改写成“想法无价值”。[Helper](../../project/research/S10-19R3_NATIVE_CONTROL_SURFACE_AUDIT.md) · [Reviewer](../../project/research/S10-19R1_SUBAGENT_FEASIBILITY.md) · [Memory](../../project/research/S10-19R2_MEMORY_FEASIBILITY.md)

本章分类区分“有限支持但未部署”和“当前路径前提失败”；各路线详见 [D10](10-Reviewer、Memory、Helper、Controller与Simulator路线.md)。

## 失败记录应保存什么

记录问题、身份、实际门禁、证据、决策和非结论，条件阶段未执行则明确留下。Reviewer Phase B/C 与 Simulator holdout 未运行，不能记成收益失败。技术失败要可见，也不能与自然终局强行合算均分；保存知识不解除 raw/hold。

## 为什么“没测量”不能记成零

**FACT｜事实**：[Reviewer](../../project/research/S10-19R1_SUBAGENT_FEASIBILITY.md) 未进入建议阶段，latency/token/成功率为 NOT_MEASURED；零 invocations 是调用次数，不是实测耗时零。

**INTERPRETATION｜解释**：0 次、无分、分数 0 是计数、缺失、数值三个对象；没有 usage 不等于零成本。门禁阻断不能提供能力成功率。

## 负结果怎样影响下一次授权

重开要指出新的 material evidence（实质证据）及它改变的前提：安全部署、语义排序或连接机制。**TEACHING EXAMPLE**：新的机械隔离 reviewer loader 需要独立验证，不能从旧 frozen-path 结果认定它必然成功或失败。单纯“再试可能成功”不回答旧门禁。

## 怎样读一个负结果

先找 decision token（决策标记），再看测试对象与前提。接着检查实际执行阶段、未测量能力和 stop rule（停止规则）。最后问：未来若重新打开路线，需要哪个新的 material evidence（实质证据）？

**TEACHING EXAMPLE｜教学示例：** 对 Memory，要同时保留指定自动锚点未过门禁与 explicit read 成功。完整原因和范围查 D10；结果标签不能省略测试对象。

项目保存失败，是为了让决策可复核。保存失败知识与永远保留全部过程文件仍是两件事；后续精简需遵循 [Track C 保留原则](../track-c-repository-tooling/12-哪些文件值得长期保留以及哪些最终可以删除.md)，本轮不执行清理。
