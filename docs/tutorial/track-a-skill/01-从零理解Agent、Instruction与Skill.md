# 01｜从零理解 Agent、Instruction 与 Skill

[学习地图](00-学习地图.md) · [下一章：Instruction](02-exact-v6-Instruction逐句拆解.md)

本章先搭一个能使用的 mental model（心智模型）。**FACT** 指本项目历史原文与[最终方案审阅](../../project/FINAL_SOLUTION_REVIEW.md)支持的合同；**INTERPRETATION** 指理解组件的方法；所有构造场景另标 **TEACHING EXAMPLE**。不用先懂代码，也不要把示意图当成系统实现图。

## 1. 先把“会说话的模型”与“能完成任务的 Agent”分开

LLM（大语言模型）根据输入的文本 Context（上下文）生成下一段输出。它能描述计划、提出选项、解释理由，但单凭一段回答，并不能证明外部游戏已经变化。对 CareerSim 来说，写出“我选择休息”与通过合法动作工具完成一次选择是两件事。

**INTERPRETATION**：可以把 Agent 理解为模型、Instruction、Context、Skills、Tools 和执行循环等组件的组合。模型产生判断；上下文容纳当前规则与已见信息；指令规定总体合同；模块提供专项方法；工具读取或改变外部环境；循环把结果带回下一次判断。这里的加号是概念关系，不是某段 Python 类的精确实现。

```text
公开环境 → Observation → Context → 模型应用 Instruction / Skill
          → 候选与审查 → Agent 调用 Tool → 外部结果 → 新 Observation
```

**FACT**：[exact-v6 Instruction](../../skill-evolution/04-v6-auditable-control-loop/instruction.md)规定 Single Agent（单一智能体）是唯一 `take_action` 提交者。三个 Skill 不创建第二提交者。多个职责可以由同一个 Agent 依次完成；“规划”“风险审查”这些角色词，不代表后台另有三个模型轮流操作游戏。

**TEACHING EXAMPLE｜教学示例，不是历史 Run 原始记录。** 模型在文字里说“已休息，健康应当上升”，但尚未提交动作。此时外部健康仍不能按预测更新；它只是一个想法。即使动作成功，也须 fresh observe 后才能知道当下公开状态。**反例**是把这段文字直接记录成“Health 已增加”，然后基于虚构值继续行动。

## 2. Context 是工作材料，不是永远可靠的记忆

Context（上下文）包括模型当前能读取的规则、公开观察、最近结果和工作摘要。长任务持续数十个月，会带来很多故事、季度选择和反馈；旧材料可能不再适用，上下文也可能被压缩或部分丢失。记得曾经看过某个数值，不能证明那个数值现在仍有效。

**FACT**：v6 要求只用本局新鲜公开事实；恢复时先取得新观察，再重读三个 Skill、重建 Board/Planning。Board 的规则允许必要时查看少量同局公开日志，但不把完整对话、数据库或别局材料变成记忆系统。

**INTERPRETATION**：新鲜度有两个问题：信息是否属于当前游戏，信息是否仍代表当前决策时刻。session（游戏会话）身份错误，哪怕数字刚刚生成也不适用；身份相同但中间已经行动，旧观察也不够。判断“我知道什么”时，应同时附来源和时间，而不是只留下结论。

**TEACHING EXAMPLE｜教学示例，不是历史 Run 原始记录。** M12 前一次观察说角色尚未晋升，之后正式反馈说明已经升职。旧“当前职级”和旧进展比较不能继续覆盖新反馈。正确做法是保留新公开结果，再重建当前基线；错误做法是只更新 Level 数字，却继续用旧职级的停滞结论指导下一季度。

真实运行中，两次压缩后未重读三个 Skill，属于[运行验证](../../project/runs/v6-run1-validation.md)确认的遵循问题。我们没有把“压缩必然丢掉某条具体规则”作为事实；可确认的是发生了恢复触发，而规定的重读没有发生。

## 3. Instruction 为什么存在

Instruction 是 persistent behavioral contract（持续行为合同）：用短而显著的文字，规定整段任务里反复适用的身份、证据、顺序、恢复与动作边界。它与临时 user prompt（用户提示）的主要区别在用途：临时提示往往描述眼前要解决的问题，Instruction 规定每次解决问题时都应守的合同。具体加载与优先级属于系统话题，本章只讲这里可见的行为内容。

**FACT**：v6 的五行 Instruction 同时要求 48 月公开决策、唯一动作提交、启动与恢复读取、候选先于 Risk、紧邻 CTRL、动作后新观察、季度和半年复核。它没有把三份 Skill 全部贴进去，也没有把每个故事的答案写进去。

**INTERPRETATION**：它需要短，是为了在长流程中容易定位关键边界；需要显著，是为了在候选生成和工具调用前得到注意；需要跨月稳定，是因为“本局公开证据”“唯一提交”“变状态后再观察”不会随一则故事改变。短并不等于越少越好，删掉必要的顺序或恢复条件同样会让合同含糊。

为什么不放入所有细节？比如 STALLED（停滞）的可比条件、公开生存趋势的语义、Risk 各状态的区分都需要展开。若把这些细节混入一条长指令，每次读主流程时就要穿过大量分支，也难看清谁拥有判断。分工是把主合同留在 Instruction，把详细判断放到 owner（职责归属者）的 Skill。

**反例**：为避免遗漏，指令写“凡有负面词就停下；Planning 也审风险；Risk 也改目标；每步重读全部历史”。这些句子不只是变长，还造成权限重叠和循环，未必能在当前候选上闭合决策。

**FACT｜证据边界**：Instruction 的长度与质量并不直接对应分数；本项目没有证明某个短文本长度能保证遵循或收益。

## 4. Skill 在这里究竟是什么

**FACT**：本比赛配置中的三个 Skill 以历史 `SKILL.md` 表达结构化职责和规则。它们说明使用时机、可用信息、应该提供的判断或摘要、不能做的事，以及不确定时怎样回退。名称和 description（用途描述）帮助辨认职责，文件正文承载具体合同。

Skill（技能模块）在这里不是另一个 Agent，也不要求作为 Python function（函数）自动运行。函数通常由程序按确定输入执行实现；这些 Skill 主要给同一个 Agent 读取和应用的规则。看到“每次决策必须应用”是行为要求，不足以证明每次决策都已经执行了某个确定性代码函数。

**INTERPRETATION**：把 Skill 想成有边界的专业工作说明书较合适。它可以教你怎样判断“这个候选是否忽略重大公开风险”，却不能仅凭文字保证模型按三条件判断，也不能保证输出标记真实。要证明遵循，需要看运行行为；要证明收益，还要看适当的比较证据。

**TEACHING EXAMPLE｜教学示例，不是历史 Run 原始记录。** Risk 说明“重大风险明确、存在直接合法缓解项、候选没处理时才 RECONSIDER”。模型却只因选项看起来不礼貌就要求重比。Skill 已存在且被读到，仍然可能被错误应用。纠正方式是回到当前公开后果与三个条件，不是仅再贴一次 Skill 名称。

## 5. Instruction 与 Skill 怎么分工

| 维度 | Instruction | Skill |
|---|---|---|
| 主要问题 | 整个 Agent 每次按什么合同工作 | 某项职责怎样判断与组织信息 |
| v6 的例子 | 观察→Board→Planning→候选→Risk→CTRL→动作 | Board 如何处理混杂效果，Planning 如何判 STALLED |
| 频率表达 | 启动、每步顺序、恢复与提交边界 | quick scan 与 full checkpoint 的具体条件 |
| 输出责任 | Agent 生成动作前 CTRL 并紧邻提交 | 模块提供事实、战略建议或候选风险结果 |
| 不能代替的证据 | 文字存在不能证明每回合遵守 | 文件读取不能证明应用正确，更不证明收益 |
| 修改时的风险 | 主流程与所属模块定义不一致 | 抢其他模块的目标、预算、标记或提交权 |

**INTERPRETATION**：拆开不是为了追求文件多。好的边界允许你问“这个判断出了问题，应该回哪份规则查？”事实不新鲜先查 Board 与观察顺序；目标比较错误查 Planning；候选具体风险错判查 Risk；标记与动作脱节查 Instruction 的执行合同。问题定位比模块数量有用。

## 6. 为什么要拆成事实、规划、风险三类职责

**FACT**：Board 不拥有 Gap、Progress、Risk Budget 或风险结论；Planning 是唯一战略 owner；Risk 只审已生成候选；三个模块都不提交。

**INTERPRETATION**：这是三种不同提问。

| 职责 | 应回答的问题 | 不该顺便回答的问题 |
|---|---|---|
| Board | 当前观察证实了什么，来源是否新鲜，变化能否比较？ | 最好选什么、是不是停滞、风险是否可接受 |
| Planning | 一个主要目标是什么，路径怎样服务目标与剩余窗口？ | 在候选尚未生成时提前作候选风险判决 |
| Risk | 此候选是否忽略了明确重大风险，需不需要一次相关重比？ | 下一年全部目标、固定季度动作配方 |
| Agent 执行职责 | 当前决定是否满足合同，怎样合法提交并取得新状态？ | 用文字声称外部动作已经成功 |

一个事实可以进入不同判断：公开健康持续下降是 Board 的输入；它是否收紧可接受的生存预算是 Planning 的判断；某个候选是否直接加重该约束是 Risk 的判断。分层不是让各模块互不知情，而是让它们对同一事实各自承担明确的问题。

## 7. Skill 与 Tool 的区别

Tool（工具）用于读取或执行外部环境；Skill 在这里规定怎样组织信息和判断。`observe` 是取得公开观察的工具动作，`take_action` 是提交合法选择的工具动作。三个 Skill 的正文都说不调用它们：需要新观察时，回到正常 Agent 循环，由唯一执行者调用。

**INTERPRETATION**：可以说 Skill 是“做决定的方法”，Tool 是“读环境或让决定落地的接口”。但这只是本教材的入门区分，不是所有系统的普遍实现定义。一个普通函数、一个工具和一个规则文档可能在别的系统中组合出现；本项目讲的是这三份历史规则的实际权限。

工具安装、服务、注册和调度实现属于 Track B｜System / Runtime，将在后续章节解释。这里不需要先知道任何接口实现，就可以检查“模块是否越权”“动作后是否再观察”。

## 8. 一个最小决策例子

**TEACHING EXAMPLE｜教学示例，不是历史 Run 原始记录。** 当前同局公开观察显示健康持续下降并有负荷警告，review（绩效反馈）临近。菜单存在候选 A：推进已有成果但增加当前负荷；候选 B：降低负荷并保留部分进展。我们不假定分数、隐藏阈值或哪个动作永远最好。

1. Board 记录下降、警告、当前窗口与两个合法选项；不知道具体损失就写 UNKNOWN。
2. Planning 维护一个基于公开反馈的 Gap，同时判断当前生存预算是否收紧，比较 A/B 的可见目标贡献与时间。
3. 先生成候选。假如选择 A，Risk 再问重大风险是否明确、A 是否未处理、B 是否直接相关合法缓解项。
4. 若三条件满足，重比 B 一次；若换 B，B 也重新过 gate。Agent 决定最终候选并生成 CTRL。
5. Agent 提交一次动作；成功回执后新 observe，再让 Board 整理新事实。

**反例**：Board 直接选 B；Risk 为整年安排固定恢复；Agent 输出 CTRL 却停在文字里；动作后直接用旧健康值继续选。四种错法分别是事实层越权、风险层越权、执行未闭合、状态过期。

真实 v6 M13 报告确认比较并选了较低负荷替代、再 gate；其 Gap 与精确 CTRL 字段未完整给出。[第六章](06-三Skill协同与一次Action闭环.md)会把真实事实和教学推演分开，不能用上面的假设菜单补成历史记录。

## 9. 自测与参考分析

题一：“三个 Skill 都被读过，所以它们都已持续正确执行。”错在哪里？题二：“同一 Agent 做 Planning 和 Risk，所以可以在生成候选前就填 Risk 结果。”为什么不成立？题三：“动作成功回执已到，就能用预期效果做下一项 Energy。”还缺什么？

参考分析：读取、功能应用、遵循与收益是不同证据层；Risk 必须有具体候选与新鲜公开后果；回执只确认其明确报告的结果，下一次决策仍需新观察。你如果能说出每个缺口，而不是只回答“遵守规则”，就已建立可用的组件模型。
