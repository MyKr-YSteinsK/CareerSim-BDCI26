# 09｜为什么我们做了那么多工程验证与排障

## 1. 按故障所在层阅读

这章不是任务编号流水账，而是十一类真实工程问题。每类回答同样五个问题，让读者学会从症状定位到最小证据。

**FACT｜事实**来自已完成的源码和历史记录；**INTERPRETATION｜解释**用于说明这些结果为什么只支持某一层结论。本轮没有重新注册工具、启动服务、调用模型、查 DB 或复玩。

## 2. 环境身份层：同名组件未必同一实现

**来源**：[ENVIRONMENT](../../project/ENVIRONMENT.md)、[OFFICIAL_SOURCE_LOCK](../../project/OFFICIAL_SOURCE_LOCK.md)、[pyproject.toml](../../../pyproject.toml)。

- **症状**：只说“装了 Python、JiuwenSwarm 和 CareerSim”，无法解释两次运行是否使用同一实现；S01 建环境时 Runner 源码尚未落地，历史使用 `--no-install-project`，与当前 checkout 条件不同。
- **实际故障层**：可比较的环境/源码身份缺失会使结论归因失效。记录确认 Windows 11、Python 3.12.13、uv 0.11.16，以及三个冻结 package 版本；Runner 基线是 `f61c738c72e51b77298cc1c14c7c6ebf4b6c527d`。
- **为什么不是另一层问题**：名称一致不等于版本一致；环境身份没有绑定时，不能先归因 Skill 策略。冻结也不等于组件没有缺陷。
- **如何验证**：历史用实际解释器/包身份、lock 与冻结来源交叉核对；本教程对照这些记录与当前冻结源码，不运行包更新或重新安装。
- **最后证明什么**：建立可追溯的比较前提；没有证明性能、全部依赖健康或未来新版本兼容。

**INTERPRETATION｜解释**：冻结是为了让“谁变了”可回答。遇到缺陷仍需记录真实问题，不能静默修改 frozen Runner 后继续把旧结果称为同一基线。

## 3. Skill 证据层：五个动词是五个命题

**来源**：H1；安装与校验源码见[第 03](03-Submission、Manifest与Skill校验.md)、[第 04 章](04-Skill是怎样真正安装进JiuwenSwarm的.md)。

- **症状**：材料校验成功，但“Skill 是否真的生效”仍没有证据。S02 设计了只加追踪标记、不改变选择策略的 `career-action-trace` 最小 Skill。
- **实际故障层**：从文件到模型执行之间的发现、加载和应用证据缺口。
- **为什么不是另一层问题**：格式正确只说明材料可接受；同分或低分不能直接说明 Skill 没加载，反之高分也不证明加载。
- **如何验证**：历史先确认格式与环境；源/暂存/运行副本 hash 一致、注册 enabled、IDENTITY 名称与 active install 匹配；再从实际 `skill_tool` 事件确认正文读入，从行动 note 确认追踪标记。
- **最后证明什么**：当时这条 Skill 使用链成立。180 秒有界运行到 M15 后超时，退出 1、无最终分；没有证明策略收益或长周期遵循。

| 命题 | 问题 | H1 中的证据性质 |
|---|---|---|
| VALIDATED（通过校验） | 材料符合校验合同吗？ | layout/frontmatter/environment 检查 |
| INSTALLED（完成安装） | 实际运行目录收到目标文件吗？ | 路径、内容 hash 与安装记录 |
| DISCOVERED（被发现） | runtime 将它列为可用 Skill 吗？ | 注册状态与历史运行层扫描机制记录 |
| LOADED（正文被加载） | 本次任务真的读到了正文吗？ | 一个真实 `skill_tool` 加载事件 |
| APPLIED（被应用） | 后续动作出现其要求的行为吗？ | 标记与正确行动/回执关联 |

H1 记录 58 个带标记的 `take_action` 调用，包括 57 个 canonical route（规范路由）和一个被拒绝的 malformed alias（错误别名）。57 个游戏动作条目中 56 个带标记，初始化条目不带。计数单位不同，不能写成“58 个成功游戏动作”。

历史 H1 描述 InstalledSkillUseRail/SkillTool 的发现加载机制；本轮没有独立探查当前 JiuwenSwarm 内部实现，所以这些细节限于该历史来源。

## 4. MCP 注册层：文件名正确，子进程仍可能启动不了

**来源**：H2、H3；[setup.py](../../../career_sim_runner/setup.py)。

- **症状**：Skill 已写好，AgentServer 注册 career-emulator 失败，裸 executable 出现 WinError 2。
- **实际故障层**：MCP 子进程 executable resolution（可执行文件解析）/PATH 与实例 command 配置。
- **为什么不是另一层问题**：同一环境的绝对 executable 在两个受控 cwd 条件中均完成 initialize/list_tools，说明不是 Skill 内容，也没有证据归因游戏规则或 provider。历史服务完整 PATH 未保留，不能把后来的 PATH 值冒充当时直接证据。
- **如何验证**：H2 进行了三种不同、有界的启动条件比较；裸名失败，绝对路径两组均返回五工具。H3 只修实例 command 字段，再从真实服务注册日志确认同一集合。
- **最后证明什么**：绝对路径消除了当时注册阻断；根因记 HIGH_CONFIDENCE。修复的是运行配置，冻结 `setup` 仍可能把它写回裸名。

H3 一次服务生命周期里出现两处注册记录，并不等于开了两个游戏。五工具集合见[第 05 章](05-JiuwenSwarm、AgentServer与MCP分别是什么.md)。那次没有 game/chat，却有一条预热模型响应，证明启动服务本身也要记 provider 副作用。

## 5. Runner 启动层：调用者 PATH 比嵌套脚本 PATH 更关键

**来源**：[v7n 首次验证](../../project/runs/v7n-run1-validation.md)、[v7n 替代验证](../../project/runs/v7n-run1-replacement-validation.md)、[RUN_HISTORY](../../project/RUN_HISTORY.md) 的 S07-51/51R。

- **症状**：服务已经 ready，但 Runner 在 `resolve_instance_ws_url()` 的裸 `jiuwenswarm-start --list` 处 WinError 2，尚未连 WS，也没有 `new_game`。
- **实际故障层**：Runner 调用进程 PATH 没有让裸命令可解析，不是 AgentServer 游戏通信失败。
- **为什么不是另一层问题**：报错发生在创建 CLI 子进程时；模型和游戏尚未进入执行。旧 output 指针必须排除，不能拿旧分当新尝试结果。
- **如何验证**：后续另获授权的 S07-51R 在调用进程自身 PATH 前置根 `.venv/Scripts`，核对 `shutil.which`，并实际执行一次裸 `--list`，退出 0。一次更早的嵌套 harness 在创建 CLI 前失败，被分类为无副作用 tooling error。
- **最后证明什么**：CLI 查找层修正，替代局有 23 个成功行动/23 个观察，达到 M6 存活；最终却因 `max_continuations` 退出 1，没有自然终局或分数。PATH 通过没有证明 gameplay 完整通过。

同一技术故障不靠无限重试换成功；首次与替代尝试属于分别授权窗口，本章不授予新窗口。

## 6. 共享 runtime 层：worktree 与 active install 都不是隔离证明

**来源**：H4；[install.py](../../../career_sim_runner/install.py)、[第 04 章](04-Skill是怎样真正安装进JiuwenSwarm的.md)。

- **症状**：S03-09 当前 worktree 的 active install 记录不存在，共享 registry 却有两个旧 Skill enabled；待装材料合法，仍不能说当前任务已经安装。
- **实际故障层**：Git checkout 本地元数据与用户目录共享 JiuwenSwarm workspace 的归属不同，安装还会清理会话、记忆、旧 Skills 等状态。
- **为什么不是另一层问题**：两个 enabled 条目可能来自旧任务，不证明当前 Candidate 被加载；worktree 文件分离也不隔离用户实例、DB、服务或 provider。
- **如何验证**：历史比较本地 active install、共享注册表和待安装材料；检查安装前 hold 保全副本。预检中出现 stdout 无 `fileno` 与后续 UTF-8 解码问题，工具列表未完整落盘，五工具状态记 UNKNOWN；门禁未通过，因此 install/service/game 均为 0。
- **最后证明什么**：存在真实的共享状态污染/覆盖风险，任务正确停在安装前；没有证明材料运行失败，也没有因为“可能能用”越过 hold 或预检。

源码的 `active_install.json` 记录来源和名称，不是共享 workspace 的实时 hash 证明。自定义 skills 目录也不自动迁移其它共享数据或注册路径；并行安装需要独立隔离证据。

## 7. 参数合同层：模型选项文本不等于合法 schema

**来源**：[v6 验证](../../project/runs/v6-run1-validation.md)、[RUN_HISTORY](../../project/RUN_HISTORY.md)。

- **症状**：一次 Energy 请求提交 `choice=6,7,3`，接口拒绝；模型意图不能直接成为合法动作。
- **实际故障层**：工具参数/枚举合同与模型输出之间不一致。
- **为什么不是另一层问题**：有明确拒绝回执，而且拒绝发生在状态变更前；这不是游戏随机后果、服务不可达或 provider 未响应。
- **如何验证**：历史将 203 次 `take_action` 尝试与结果关联，202 成功且随后 fresh observe，1 次 malformed 请求未改变状态；不把失败尝试计入成功动作。
- **最后证明什么**：该局 48 月完成但 runtime adherence 仍失败。一次被纠正的参数错误不能因最终得分较好就从审计中消失。

**INTERPRETATION｜解释**：自然语言要求、模型实际参数和游戏校验是三层。Skill 写“先验证”不等于 MCP 服务器有一段确定性代码替它验证所有 note 标记。

## 8. Provider 层：连接失败不能用改策略来解释

**来源**：H5，S03-10 当时失败窗口的后续取证。

- **症状**：历史游戏窗口出现 17 个请求开始、16 个 APIConnectionError、没有已完成响应；连接在 TLS/HTTP 响应前的阶段失败。
- **实际故障层**：上游模型连接链路；具体 peer/root cause（对端/根因）仍 UNKNOWN。
- **为什么不是另一层问题**：没有模型完成响应，无法由此评价模型决策策略；也没有 HTTP 证据把错误定为鉴权失败、限流或模型名错误。
- **如何验证**：当时在独立有界授权下做两个 provider-only 检查，一个非流式、一个流式，均完成，共 74 tokens；同时保留历史失败窗口。本轮只阅读历史 RESULT，不复制私有 endpoint/config。
- **最后证明什么**：检查时连接能够成功；没有证明历史故障的唯一原因或未来稳定性，没有新 gameplay 验证。

独立 connectivity（连通性）通过与目标 Run 通过必须分别记账。不能用后来成功的响应擦掉此前的连接失败，也不能把 reported cost 默认 0 当实际账单。

## 9. Session / score 层：最新 DB 行不等于目标局

**来源**：[v4 取证](../../project/runs/v4-run1-health-forensic.md)、[v7i 验证](../../project/runs/v7i-run1-replacement-validation.md)、[score.py](../../../career_sim_runner/score.py)。

- **症状**：v4 正常终局、Runner 退出 0，报告却 `ending_score={}`；v7i 的报告 game ID 为空，但 final observe 有合法完整结果。
- **实际故障层**：评分来源、DB 路径与 session provenance。v4 共享实例使用旧工作区 DB，根 Runner 查询根目录默认 DB。
- **为什么不是另一层问题**：v4 已知 M6 健康失败、量化 25.84 / partial 18.09；空报告不等于游戏没有结算。退出 0 也不等于 48 月。v7i 的报告缺字段不否定正确 final observe。
- **如何验证**：v4 当时按精确 game ID 对有效 DB 做只读取证；v7i 绑定 fresh game、事件、文本和 final observe，确认 64.0 / 44.8、48 月。当前任务没有查 DB。
- **最后证明什么**：分别恢复了正确的局部结果与字段缺陷；没有授权任意使用最新 DB fallback 修补过去，v6 报告覆盖原因也仍 UNKNOWN。

旧 DB 快照后来已不含 v4 那行，缺失原因未知且早于退役；现有 hash 不能恢复缺失 payload。不要把退役动作写成无证据的删除根因。

## 10. 上下文与遵循层：加载一次不证明整个长游戏都记得

**来源**：[v6 验证](../../project/runs/v6-run1-validation.md)、[v7i 验证](../../project/runs/v7i-run1-replacement-validation.md)、[RUN_HISTORY](../../project/RUN_HISTORY.md)。

- **症状**：Skill 开始时被读取，但长游戏出现 Context compression（上下文压缩）后，没有方案要求的 Skill 重读；v7i 累计日志曾被混读为 23 次本局压缩。
- **实际故障层**：运行遵循与日志时间窗归属。v6 有两次压缩后未重读三 Skill；v7i 本局是两次，之后有 fresh observe，却未重读四 Skill。
- **为什么不是另一层问题**：观察更新与策略恢复是两个动作；final score 或初始 LOADED 证据不覆盖压缩后的行为。累计框架日志也不是当前 Run 专用日志。
- **如何验证**：按 run-window、时区、请求和恢复点绑定压缩记录与后续读文件事件；不从所有累计记录做本局计数。
- **最后证明什么**：这些局存在已确认的 recovery-path 缺陷；不能说 IDENTITY 注释承诺持久注入就证明每份 Skill 正文始终在上下文，也不能把分数差异认定为压缩造成。

具体恢复要求和策略文本见 [Track A](../track-a-skill/07-真实案例、反例与失败模式.md)，本章只教证据怎样绑定。

## 11. Forensics 层：审计器也需要被审计

**来源**：[S08-09 取证](../../project/reviews/S08-09_RUNTIME_CONTRACT_ADHERENCE_FORENSICS.md)。

- **症状**：旧 summary 将 Delivery 标记判为 `0/207 valid`；模型全部输出 `R=PASS X=0`，但合同禁止 X=0 提交。
- **实际故障层**：前者是解析器对合法换行的 false negative；后者是合同编码/执行预检缺口，不是同一种故障。
- **为什么不是另一层问题**：Locked MCP 没有 note-marker gate，不会自动因 X=0 阻断。修汇总解析器也不会改变已经发生的模型行为。
- **如何验证**：离线逐项关联原事件；窄修 parser 接受既有同一行或一次换行格式，得到 174 valid、33 checkpoint 枚举错误、0 missing。同时确认全部 207 成功回执只有 success/error，18 个后置观察缺失，没有等价状态回执。
- **最后证明什么**：审计修复有依据，运行合同缺陷仍需单独决策；历史 evidence 未改、hold ACTIVE、无新游戏。Delivery 生命周期语义仍 INCONCLUSIVE。

**INTERPRETATION｜解释**：一个 parser PASS 是格式事实，不是语义 PASS；而 parser FAIL 也必须检查是否工具误读。项目审计脚本是证据助手，不是裁判替身。

## 12. 取证保留与退役层：删目录之前先断依赖

**来源**：[LOCAL_WORKSPACE_RETIREMENT](../../project/LOCAL_WORKSPACE_RETIREMENT.md)。

- **症状**：旧 S03 目录长期遗留，有真实 DB/log 归属和下游证据引用，不能因“旧 worktree”标签直接删掉。
- **实际故障层**：运行路径依赖与唯一证据生命周期。旧目标是普通目录，并非仍注册的 Git worktree。
- **为什么不是另一层问题**：Git 历史能恢复 tracked 文档，却不能自动恢复 ignored DB 和未归档日志；hash 也不等于 raw 内容保全。
- **如何验证**：S11-11 导出 20 个精确 session payload，共 244,154 bytes，核对引用、hash 与敏感信息扫描，并将有效 DB/log 路由改为根目录；没有迁移敏感配置。自动递归删除被审批策略拒绝后未绕过。S11-12 用户人工删除，随后确认目标不存在、迁移证据仍在。
- **最后证明什么**：旧目录已退役、有效路径依赖已解除、必要证据迁移。新的本地 hold 仍 ACTIVE，既有 S09/S10 hold 未解除；不是全项目证据可删的许可。

这里说明的是已完成历史动作，本轮既不删目录，也不复查 DB 内容。所有清理必须区分“可重建副本”“派生摘要”“唯一 raw 来源”。

## 13. 一张定位表

| 看见的症状 | 先定位的层 | 不应直接尝试 |
|---|---|---|
| 裸命令 WinError 2 | 调用进程的 executable/PATH | 重写策略、反复开局 |
| WS 可连却没有工具 | MCP 注册与有效 config | 宣称所有 runtime 通过 |
| enabled 有 Skill，任务却没记录安装 | 共享 workspace 与本地元数据 | 依据旧注册表宣布当前成功 |
| schema rejection | 参数/枚举合同与回执 | 统计为成功游戏动作 |
| provider 无完成响应 | 上游连接及请求窗 | 从失败评分判断策略 |
| score 空或 game ID 不明 | session/DB/output 归属 | 随便取最新 DB 行 |
| final score 好但要求未执行 | runtime adherence | 用成绩覆盖遵循缺陷 |
| 汇总与原事件不一致 | 审计器格式/关联逻辑 | 改写原始证据 |

大量任务是在逐层证明运行链成立。每一步都应说清它证明到哪里；没有证据的部分保留 UNKNOWN，而不是扩大探针、重跑预算或偷偷修改冻结实现。
