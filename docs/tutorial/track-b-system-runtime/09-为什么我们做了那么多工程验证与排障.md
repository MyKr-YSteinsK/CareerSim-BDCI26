## 2. 环境身份层：同名组件未必同一实现

**来源**：[ENVIRONMENT](../../project/ENVIRONMENT.md)、[OFFICIAL_SOURCE_LOCK](../../project/OFFICIAL_SOURCE_LOCK.md)、[pyproject.toml](../../../pyproject.toml)。

**FACT｜事实**：历史身份记录确认 Windows 11、Python 3.12.13、uv 0.11.16 与三个冻结 package 版本；Runner 基线为 `f61c738c72e51b77298cc1c14c7c6ebf4b6c527d`。S01 的 `--no-install-project` 有当时 Runner 尚未落地的前提。

**INTERPRETATION｜解释**：组件同名不能建立可比较身份。先按 [B02](02-从零搭好Python与依赖环境.md) 核对已有版本记录，再判断变化发生在哪层；不要以“重装最新版”替代归因。冻结身份也不保证全部依赖无缺陷。

## 3. Skill 证据层：五个动词是五个命题

**来源**：H1；安装与校验源码见[第 03](03-Submission、Manifest与Skill校验.md)、[第 04 章](04-Skill是怎样真正安装进JiuwenSwarm的.md)。

**FACT｜案例**：H1 用不改变选择策略的 `career-action-trace` 检查 Skill 使用链。先核 layout/安装副本 hash、enabled、IDENTITY 与 active install，再在本次 `skill_tool` 事件中确认正文加载，并关联动作 note 的追踪标记。材料合法、同分或高分均不能替代这些事件。

180 秒有界窗口到 M15 后超时、退出 1、无最终分；它证明当时使用链，不证明策略收益或全长遵循。下面五层分别保留证据对象。

| 命题 | 问题 | H1 中的证据性质 |
|---|---|---|
| VALIDATED（通过校验） | 材料符合校验合同吗？ | layout/frontmatter/environment 检查 |
| INSTALLED（完成安装） | 实际运行目录收到目标文件吗？ | 路径、内容 hash 与安装记录 |
| DISCOVERED（被发现） | runtime 将它列为可用 Skill 吗？ | 注册状态与历史运行层扫描机制记录 |
| LOADED（正文被加载） | 本次任务真的读到了正文吗？ | 一个真实 `skill_tool` 加载事件 |
| APPLIED（被应用） | 后续动作出现其要求的行为吗？ | 标记与正确行动/回执关联 |

H1 记录 58 个带标记的 `take_action` 调用，包括 57 个 canonical route（规范路由）和一个被拒绝的 malformed alias（错误别名）。57 个游戏动作条目中 56 个带标记，初始化条目不带。计数单位不同，不能写成“58 个成功游戏动作”。

历史 H1 描述 InstalledSkillUseRail/SkillTool 的发现加载机制；本轮没有独立探查当前 JiuwenSwarm 内部实现，所以这些细节限于该历史来源。

## 4. MCP 注册层：文件名正确，子进程仍可能启动不了

**来源**：H2、H3；[setup.py](../../../career_sim_runner/setup.py)。

**FACT｜症状与比较**：裸 executable 报 WinError 2；同环境绝对 executable 在两个受控 cwd 条件均 initialize/list_tools 成功，返回五工具。H3 只改实例 command，再从实际服务注册日志确认集合。

**INTERPRETATION｜定位**：证据支持 executable/PATH 配置阻断，根因记 HIGH_CONFIDENCE；不支持归因 Skill、游戏规则或 provider。历史服务完整 PATH 未保留，不能拿后来值补成直接证据；冻结 setup 仍可能写回裸名。

H3 一次生命周期的两处注册不等于两局；没有 game/chat，但有一条预热模型响应。服务启动有 provider 副作用，五工具机制见 [B05](05-JiuwenSwarm、AgentServer与MCP分别是什么.md)。

## 5. Runner 启动层：调用者 PATH 比嵌套脚本 PATH 更关键

**来源**：[首次验证](../../project/runs/v7n-run1-validation.md)、[替代验证](../../project/runs/v7n-run1-replacement-validation.md)、[RUN_HISTORY](../../project/RUN_HISTORY.md) S07-51/51R。

**FACT｜症状与核验**：服务 ready，但 Runner 创建裸 `jiuwenswarm-start --list` 时 WinError 2，尚无 WS/new_game。另获授权的 S07-51R 在调用进程 PATH 前置根 Scripts，核 `shutil.which` 与一次裸 CLI 退出 0；此前嵌套 harness 的无副作用失败另记 tooling error。

**结论边界**：CLI 修正后替代局有 23 成功动作/23 观察、M6 存活，仍因 `max_continuations` 退出 1，无终局分数。PATH PASS 不升级成完整 gameplay PASS；两次窗口分别授权，本章无新重试预算。

## 6. 共享 runtime 层：worktree 与 active install 都不是隔离证明

**来源**：H4；[install.py](../../../career_sim_runner/install.py)。

**FACT｜事实**：S03-09 的 worktree 无 active install 记录，共享 registry 却有两个旧 Skill enabled；预检又因输出/解码错误未完整保存工具列表，五工具状态为 UNKNOWN。门禁未过，install/service/game 均为 0，不能写成 Candidate 运行失败。

排查入口是 [B04 的共享安装副作用](04-Skill是怎样真正安装进JiuwenSwarm的.md) 与 [C08 的代码/运行隔离边界](../track-c-repository-tooling/08-local目录从worktree到runtime完整解释.md)。`active_install.json` 是来源记录，不能单独证明共享 workspace 当前内容；自定义 skills 路径也不隔离 DB、会话和服务。

## 7. 参数合同层：模型选项文本不等于合法 schema

**FACT｜事实**：[v6 验证](../../project/runs/v6-run1-validation.md) 与 [RUN_HISTORY](../../project/RUN_HISTORY.md) 记录 Energy 的 `choice=6,7,3` 被拒绝且未改变状态：203 次尝试中 202 次成功并有 fresh observe。完整 48 月与运行遵循失败同时成立。

先按 [B03 参数合同](03-Submission、Manifest与Skill校验.md) 和 [B07 回执闭环](07-从模型决定到Tool调用再到新状态.md) 区分请求、拒绝、成功；结果分类见 [D09](../track-d-project-method/09-失败实验与负结果为什么值得保留.md)。模型意图或 note 中的 PASS 不能代替接口验证，也不能把该明确拒绝推广成所有超时都无副作用。

## 8. Provider 层：连接失败不能用改策略来解释

**FACT｜事实**：H5 对 S03-10 失败窗口记录 17 个请求开始、16 个 APIConnectionError、无完成响应，失败在 TLS/HTTP 响应前；具体对端/根因为 UNKNOWN。后来另获授权的两个 provider-only 检查均完成，共 74 tokens，只证明那两个窗口连通。

没有 HTTP 证据就不能改写为鉴权、限流或模型名错误；没有模型完成响应，也不能评价策略。保留失败窗口与后来成功的独立归属，方法见 [D08](../track-d-project-method/08-Forensics为什么成为项目的重要部分.md)。本章不提供私有连接配置或重试授权；缺账单时不把 cost 记为实际零。

## 9. Session / score 层：最新 DB 行不等于目标局

**来源**：[v4 取证](../../project/runs/v4-run1-health-forensic.md)、[v7i 验证](../../project/runs/v7i-run1-replacement-validation.md)、[score.py](../../../career_sim_runner/score.py)。

**FACT｜症状与来源**：v4 退出 0 但 `ending_score={}`；实际共享实例用旧工作区 DB，根 Runner 查询根默认 DB。当时按精确 game ID 只读取证恢复 `25.84 / 18.09` 的 M6 健康失败，既非无结算，也非完整 48 月。

v7i replacement 的报告 game ID 空，独立 fresh game/events/transcript/final observe 却支持 `64.0 / 44.8 / 48m`。核目标来源可区分字段缺陷与真正错局，不能默认“最新 DB 行”正确。生产路径查 [B08](08-日志、Session、Score与证据是怎么产生的.md)，正反对照方法查 [D08](../track-d-project-method/08-Forensics为什么成为项目的重要部分.md)。

**UNKNOWN**：v6 报告覆盖原因；旧 DB 快照缺少 v4 payload 的原因。后者缺失早于退役，hash 不能恢复内容，也不能把它归因用户删除。当前没有 DB 查询。

## 10. 上下文与遵循层：加载一次不证明整个长游戏都记得

**FACT｜事实**：[v6](../../project/runs/v6-run1-validation.md) 的两次压缩后未重读三 Skill；[v7i](../../project/runs/v7i-run1-replacement-validation.md) 的累计 23 条压缩记录，按本局窗口归属后是两次，之后虽有 fresh observe 却未重读四 Skill。[RUN_HISTORY](../../project/RUN_HISTORY.md) 保留这些限制。

恢复合同查 [A02](../track-a-skill/02-exact-v6-Instruction逐句拆解.md)，时间窗和替代解释查 [D08](../track-d-project-method/08-Forensics为什么成为项目的重要部分.md)。初始 LOADED 与观察更新不覆盖恢复遵循，也不能由此证明分数差异由压缩造成。

## 11. Forensics 层：审计器也需要被审计

**FACT｜事实**：[S08-09 取证](../../project/reviews/S08-09_RUNTIME_CONTRACT_ADHERENCE_FORENSICS.md) 将误判的 `0/207 valid` 修正为 174 valid、33 checkpoint 枚举错误、0 missing；合法换行触发了旧 parser 的 false negative。另一个独立问题是全部 `R=PASS X=0`，而合同禁止 X=0 提交，Locked MCP 不会替 note 执行该门禁。

解析修复不改变既有行为：207 个成功回执只含 success/error，18 个后置观察缺失；Delivery 生命周期语义仍 INCONCLUSIVE，hold ACTIVE。方法归 [D08](../track-d-project-method/08-Forensics为什么成为项目的重要部分.md)：分别检查 parser 的读取规则与模型的合同执行，不能以其中一个 PASS 覆盖另一个缺陷。

## 12. 取证保留与退役层：删目录之前先断依赖

**FACT｜事实**：[旧工作区退役](../../project/LOCAL_WORKSPACE_RETIREMENT.md) 的目标是普通目录，并非仍注册 worktree。S11-11 导出 20 个精确 session payload、244,154 bytes，完成引用/hash/敏感信息核对和有效 DB/log 路由调整；自动删除被拒绝后未绕过，S11-12 由用户人工删除。迁移来源仍受 hold，既有 S09/S10 hold 未解除。

目录消失不能推出证据可删；Git 也不会自动恢复 ignored DB/log。生命周期查 [C07](../track-c-repository-tooling/07-artifacts、Raw-Evidence与证据链.md)，退役条件查 [C12](../track-c-repository-tooling/12-哪些文件值得长期保留以及哪些最终可以删除.md)。这里索引历史结果，本轮不复查 DB 或清理。

## 13. 一张定位表

| 看见的症状 | 先定位的层 | 不应直接尝试 |
|---|---|---|
| 裸命令 WinError 2 | 调用进程的 executable/PATH | 重写策略、反复开局 |
| WS 可连却没有工具 | MCP 注册与有效 config | 宣称所有 runtime 通过 |
| enabled 有 Skill，任务却没记录安装 | 共享 workspace 与本地元数据 | 依据旧注册表宣布当前成功 |
| schema rejection | 参数/枚举合同与回执 | 统计为成功游戏动作 |
| provider 无完成响应 | 上游连接及请求窗 | 从失败评分判断策略 |
| score 空或 game ID 不明 | session/DB/output 归属 | 随便取最新 DB 行 |
| final score 好但要求未执行 | runtime adherence | 用成绩覆盖遵循缺陷 |
| 汇总与原事件不一致 | 审计器格式/关联逻辑 | 改写原始证据 |

大量任务是在逐层证明运行链成立。每一步都应说清它证明到哪里；没有证据的部分保留 UNKNOWN，而不是扩大探针、重跑预算或偷偷修改冻结实现。
