# 10｜从零复现一条完整运行链

[学习地图](00-学习地图.md) · [上一章](09-为什么我们做了那么多工程验证与排障.md)

## 阅读前提：这是一条概念复现路线

Reproduction（复现）是让组件身份、运行链和证据归属再次可比较，不是保证模型逐字输出同一内容或得到同一分数。本章把前九章串起来；不是一个可以在当前阶段执行的脚本。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 本章没有执行 setup、环境 CLI validate、install、服务启动、MCP、provider、DB 查询或 gameplay。命令只说明历史接口；未来执行必须另有明确 Task 授权、次数/成本预算和停止条件。

命令中的变量是未来任务必须事先确定的真实输入，不是本轮设置值；本文不提供密钥、私有 provider 配置或能绕过现有冻结边界的材料。所有未知现场状态均为 UNKNOWN。

## Step 0｜先明确“要复现什么”

阅读 [OFFICIAL_SOURCE_LOCK](../../project/OFFICIAL_SOURCE_LOCK.md)、[ENVIRONMENT](../../project/ENVIRONMENT.md)、[CURRENT_STATE](../../project/CURRENT_STATE.md) 和未来任务的 run gate（运行门禁），先回答：

1. 复现哪个 Candidate、哪个 source commit，使用哪些 Skill/Instruction？
2. 是本地 Dev（开发环境）观察，还是有另行授权的官方提交？两者合同不同。
3. 谁独占 `career_emu`，哪些 raw evidence（原始证据）仍在 FORENSIC_HOLD？
4. 是否授权环境准备、安装/reload、服务/MCP、provider、一次新局或同局继续？各有多少预算？
5. 哪种技术失败/未知结果必须停止，结束后怎样归档必要证据？

**FACT｜事实**：当前最终冻结材料的 exact-v6 身份与工作中的 current Candidate 不是自动同一对象。不能因为当前目录方便就用 v8 替代指定 v6，也不能为教学重新构建 frozen ZIP。身份以 canonical（权威）记录和任务指定材料为准。

这一步的产物是一个明确的运行合同和身份清单，不是服务进程。比赛 gameplay 当前已关闭，本教程完成也不重新开放。

## Step 1｜找到正确的 Python 环境

先理解[第 02 章](02-从零搭好Python与依赖环境.md)：Interpreter（解释器）执行代码，`.venv` 为项目提供依赖，`uv.lock` 固定解析结果；三者不同。

本仓库静态/离线处理使用根 `D:/CS/CareerSim/.venv/Scripts/python.exe`。历史环境记录是 Python 3.12.13、uv 0.11.16，`jiuwenswarm==0.2.4b3`、`career-emulator==1.0.1`、`career-emulator-bdci26==1.0.0`，冻结 Runner SHA 为 `f61c738c72e51b77298cc1c14c7c6ebf4b6c527d`。

未来任务首先复用未漂移的稳定身份记录，再核对直接影响运行的差异。已有环境不能为了“从零”演示而重装或隐式同步；历史 `--no-install-project` 有当时 Runner 尚未落地的前提。依赖/Source Lock 漂移要返回决策，不能悄悄升级。

只在子进程里设置 PATH 也不足以证明调用者能创建裸 CLI。需要按获准 preflight（预检）确认真正调用进程及根 Scripts。环境变量只说明用途，不展示任何 `.env` 内容。

## Step 2｜准备身份明确的 solution

参阅[第 03 章](03-Submission、Manifest与Skill校验.md)，区分官方完整提交材料要求与 Runner 最低材料合同。最小输入至少有 `manifest.json` 和 `skills/<name>/SKILL.md`；正式最终包还要按其提交合同含 README/design 等材料，不能把最小可安装 bundle 称为完整提交。

未来命令变量 `$solution` 必须指向已核验的真实方案根目录；目录不是 `docs/skill-evolution` 教材，也不是任意拷贝来的 Skill 子目录。记录来源 commit、材料 hash、manifest 与 Skill 集合，确保匹配指定 Candidate。

**INTERPRETATION｜解释**：材料准备解决“拿了谁的文件”，不是“这些文件已进入模型”。策略含义与版本差异转到 [Track A](../track-a-skill/00-学习地图.md) 阅读。

## Step 3｜先检查材料，认识完整 validate 的运行前提

可以从已保存的材料校验报告与源文件，核对 layout（目录合同）、manifest 字段、Skill frontmatter（文件头元数据）。低层 `validate_submission_contract()` 不等于完整 manifest/frontmatter 检查，详见第 03 章。

完整 CLI `validate` 还检查运行环境，并可能初始化实例、覆盖环境、写 DB 父目录探针和连接 WS。若服务尚未启动，其 backend 检查可能失败。因此本步骤先定义材料要求；完整环境 CLI 的位置要等 Step 4 获准启动并就绪后，不是闭着眼在服务之前执行并期待全项 PASS。

预期证据是材料 PASS 与必要运行前提各自的结果。既有稳定 PASS 在身份未变时复用；不为收集更多报告无限追加门禁。失败须明确是哪一层，不得用“整体 false”掩盖具体来源。

## Step 4｜配置与启动 JiuwenSwarm / MCP

未来执行先按[第 05 章](05-JiuwenSwarm、AgentServer与MCP分别是什么.md)核对有效 instance config：MCP executable、cwd、DB/log 路由、provider 依赖与共享实例独占窗口。不能把 `setup` 当只显示配置；它可能覆盖修好的绝对 executable 以及有效路径。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 下面是已建立流程的服务启动接口，可能触发 provider 预热。

```powershell
& 'D:/CS/CareerSim/.venv/Scripts/jiuwenswarm-start.exe' --name career_emu all
```

成功要靠 readiness（就绪）证据、实例状态与真实必要接口确认，不靠固定等待秒数。历史 S03-06 证明了五个 CareerSim 工具；这份历史列表不替代未来窗口的有效注册证据。不能把 `backend-reachable` 通过或 executable 文件存在，当成所有 MCP 工具与模型链路都通过。

如未来合同允许完整 CLI 环境校验，且调用进程能解析裸 `jiuwenswarm-start --list`，其接口形状如下。这里没有提供 `$solution` 的实际值，也没有执行它。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 此命令包含环境写入/连接行为，不是纯材料静态校验。

```powershell
& 'D:/CS/CareerSim/.venv/Scripts/python.exe' -m career_sim_runner validate --submission $solution
```

正式任务还须接受必要 Hard Gates（硬门禁）；源码只检查文件/连接的能力不能替代预期运行接口证据。注册失败、连接结果不明或 hold 保全失败时，按合同停止，不能转而猜一个新工具表。

## Step 5｜安装并驱动一局

[第 04 章](04-Skill是怎样真正安装进JiuwenSwarm的.md)已说明 installation（安装）的清理副作用。未来操作者必须先保全仍需保留的源文件，确认不会覆盖唯一证据；拷贝到工作树不是 runtime 隔离。

`play --submission` 本身包含完整材料校验、install 和 reload，因此不能机械地先独立 install，再按“每一步都运行”重复 install。另一路径是独立 install 后不带 submission 的 play，但这要求核实 active install 的真实归属与服务配置加载，不能只相信旧记录。

以下展示首种历史入口；`$authorizedTimeout` 为未来合同给出的有限秒数，必须事先确定，默认 7200 秒不是额外预算授权。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 该命令会安装/reload，并可能调用 provider、MCP、`new_game` 与 `take_action`。

```powershell
& 'D:/CS/CareerSim/.venv/Scripts/python.exe' -m career_sim_runner play --submission $solution --timeout-s $authorizedTimeout
```

它通过已经启动的服务驱动任务，不负责启动该服务。该入口默认创建新 drive，游戏新建由模型之后调用工具完成。记录 actual install、drive ID、game ID、output 目录及开始时间，不以“某文件存在”补出没有发生的操作。

超时/断连/partial/unknown outcome（结果未知）之后不能盲重发：先在既有授权内读取状态或必要日志；仍不能确认就停止留证。手动 `--continue` 不等同于新游戏预算，也不保证恢复同一游戏；同时传 submission 还会重装/清理。是否继续必须来自具体任务授权。

## Step 6｜观察 model/tool loop

看[第 06](06-Runner如何启动并驱动一局CareerSim.md)、[第 07 章](07-从模型决定到Tool调用再到新状态.md)：

- 初始提示发出后，确认一个新游戏 ID 与合法初始观察。
- 找到本次 Skill 发现/正文加载的证据，不只看注册名称。
- 将行动请求与回执关联，区分成功、拒绝与未知结果。
- 核对该行动后的 fresh observe，以及正确游戏/事件/时间顺序。
- 将自动继续请求、模型任务结束、游戏终局和全局 timeout 分开。
- 发生压缩时，按该 Candidate 的恢复合同审计；开始时加载不能证明之后始终遵循。

这些是对已有观察的判读，不是本章要求进行新探针。Runner 采集到的普通文字不能替代结构化终局；月份、存活、完成身份均应来自正确目标局的状态。

## Step 7｜检查 score 的来源与归属

正常报告路径是 `drive → build_score_report → write_score_report`，见[第 08 章](08-日志、Session、Score与证据是怎么产生的.md)。先查同一 output 的证据绑定，而不是立刻再运行 `score`。

如果报告无分或 session 不明，保留原报告与其 hash，并说明缺失。官方 CLI `score` 会使用最新 DB session fallback，可能覆盖原文件；DB fallback 还会调用游戏引擎 observe。它不是一个总能安全修复归属的按钮，因此这里不安排“再 score 一次”作为默认补救。

未来复核要由任务明确允许读取哪个已存在来源、是否允许 DB/引擎调用。无法恢复则 UNKNOWN，不以其它游戏、模型猜测或新增重跑替代。

分别记录 local quantitative score（本地量化分）、competition partial score（比赛部分分）、存活月份与终局性质。不要把本地 report 说成 official hidden score（官方隐藏成绩），也不要把早期自然终局的退出 0 说成完整 48 月。

## Step 8｜离线 audit 与必要证据归档

项目的 [LIVE_RUN_WORKFLOW](../../project/LIVE_RUN_WORKFLOW.md) 提供共同离线证据管线。输入须显式绑定：目标 events、transcript、原始 score（若存在）、真实或声明重建的 runner-result、可用的安全 llm-log、起止时间和时区。

这套项目管线不是官方 Runner 原生能力。审计产物要说明 input hashes、身份一致性、终局、行动/观察、usage、压缩、Skill 重读、格式/语义边界与 limitations（限制）。缺失 llm-log 不填“压缩零次”，缺失账单不填“成本为零”，不确定晋升/机制结论保留 UNKNOWN。

归档只选明确允许的去敏 run-scoped（限定该局范围）材料，先 secret scan；共享 DB、凭据、无关会话和未扫描的累计日志不能提交。Raw 仍有复核依赖则保留 hold，派生 summary 生成不会自动解除它。具体脚本/仓库目录全量说明留给 Track C。

## Step 9｜停止服务，处理获准清理

未来任务结束或停止边界要记录实际 graceful stop（优雅停止）结果、manager 状态、目标进程退出和必要端口释放。停止行为自身也须在该 Task 生命周期授权中，不能靠杀全机进程“保证干净”。本轮没有启动服务，因此没有执行 stop。

清理前核对目标的解析后绝对路径、身份、证据来源与 hold。只删指定可删资产，不把 retired（退役）和 hold released（保留解除）当同一状态。已完成的 S03 旧目录退役见[记录](../../project/LOCAL_WORKSPACE_RETIREMENT.md)：用户人工删除目录后，迁移来源与 hold 仍保留。

本章不会给出一个递归删除命令作为学习练习，也不会以教程完成宣布 Stage 完成。

## Step 10｜怎样定义“这条运行链复现成功”

| 判断维度 | 最少要说明什么 | 仍不能扩大为 |
|---|---|---|
| Identity correctness（身份正确） | Candidate/source/config/环境与实际安装匹配 | 只看 Git HEAD 就证明 runtime 正确 |
| Runtime connectivity（运行链连通） | 服务/必要 MCP/provider 的窗口内证据 | 一个 WS 可连就全链 PASS |
| Game completion / termination（完成/终止） | 正确 game 的公开终局、月份与结束性质 | 模型说 DONE、退出 0 就满 48 月 |
| Score extraction（评分提取） | 来源与目标 game 一致，原报告/替代证据限制明确 | local score 等于 hidden Test |
| Evidence integrity（证据完整性） | 明确输入、时间窗、bytes/hash、缺失项、敏感信息处理 | hash 替代源文件或自动解除 hold |
| Behavior / adherence（行为/遵循） | Skill 加载、应用、恢复与动作闭环按合同审计 | 标记计数或好成绩就全部语义通过 |

允许某些维度通过、另一些失败或 UNKNOWN。复现报告应该给出这种真实分层结果，而不是一个掩盖故障的总 PASS。

## 最后的读者练习

**TEACHING EXAMPLE｜教学示例，不是历史 Run 原始记录。** 某方案完整 48 月，分数可归属，但压缩后未按合同重读 Skill。你能说“完整对局与评分链已确认，恢复遵循失败”；不能说“系统全通过”，也不能自动再开一局或改冻结 Runner。

至此，Track B 的路线是：知道组件由谁提供，理解材料怎样进入 runtime，跟踪模型请求怎样变成游戏动作，再让评分与证据回到正确身份。策略细节回到 [Track A](../track-a-skill/00-学习地图.md)；全仓工具、测试与资产组织留给后续 Track C。
