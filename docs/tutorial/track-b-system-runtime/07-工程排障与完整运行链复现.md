### Skill 证据层：五个动词是五个命题

**来源**：H1；安装与校验源码见[第 03](03-Submission校验与Skill安装.md)、[第 04 章](04-JiuwenSwarm、AgentServer与MCP分别是什么.md)。

**FACT｜案例**：H1 用不改变选择策略的 `career-action-trace` 检查 Skill 使用链。先核 layout/安装副本 hash、enabled、IDENTITY 与 active install，再在本次 `skill_tool` 事件中确认正文加载，并关联动作 note 的追踪标记。材料合法、同分或高分均不能替代这些事件。

180 秒有界窗口到 M15 后超时、退出 1、无最终分；它证明当时使用链，不证明策略收益或全长遵循。下面五层分别保留证据对象。

| 命题 | 问题 | H1 中的证据性质 |
|---|---|---|
| VALIDATED（通过校验） | 材料符合校验合同吗？ | layout/frontmatter/environment 检查 |
| INSTALLED（完成安装） | 实际运行目录收到目标文件吗？ | 路径、内容 hash 与安装记录 |
| DISCOVERED（被发现） | runtime 将它列为可用 Skill 吗？ | 注册状态与历史运行层扫描机制记录 |
| LOADED（正文被加载） | 本次任务真的读到了正文吗？ | 一个真实 `skill_tool` 加载事件 |
| APPLIED（被应用） | 后续动作出现其要求的行为吗？ | 标记与正确行动/回执关联 |

H1 记录 58 个带标记的 `take_action` 调用，包括 57 个 canonical route（规范路由）和一个被拒绝的 malformed alias（错误别名）。57 个游戏动作条目中 56 个带标记，初始化条目不带。计数单位不同，不能写成“58 个成功游戏动作”。

历史 H1 描述 InstalledSkillUseRail/SkillTool 的发现加载机制；本轮没有独立探查当前 JiuwenSwarm 内部实现，所以这些细节限于该历史来源。

### MCP 注册层：文件名正确，子进程仍可能启动不了

**来源**：H2、H3；[setup.py](../../../career_sim_runner/setup.py)。

**FACT｜症状与比较**：裸 executable 报 WinError 2；同环境绝对 executable 在两个受控 cwd 条件均 initialize/list_tools 成功，返回五工具。H3 只改实例 command，再从实际服务注册日志确认集合。

**INTERPRETATION｜定位**：证据支持 executable/PATH 配置阻断，根因记 HIGH_CONFIDENCE；不支持归因 Skill、游戏规则或 provider。历史服务完整 PATH 未保留，不能拿后来值补成直接证据；冻结 setup 仍可能写回裸名。

H3 一次生命周期的两处注册不等于两局；没有 game/chat，但有一条预热模型响应。服务启动有 provider 副作用，五工具机制见 [B04](04-JiuwenSwarm、AgentServer与MCP分别是什么.md)。

### Runner 启动层：调用者 PATH 比嵌套脚本 PATH 更关键

**来源**：[首次验证](../../project/runs/v7n-run1-validation.md)、[替代验证](../../project/runs/v7n-run1-replacement-validation.md)、[RUN_HISTORY](../../project/RUN_HISTORY.md) S07-51/51R。

**FACT｜症状与核验**：服务 ready，但 Runner 创建裸 `jiuwenswarm-start --list` 时 WinError 2，尚无 WS/new_game。另获授权的 S07-51R 在调用进程 PATH 前置根 Scripts，核 `shutil.which` 与一次裸 CLI 退出 0；此前嵌套 harness 的无副作用失败另记 tooling error。

**结论边界**：CLI 修正后替代局有 23 成功动作/23 观察、M6 存活，仍因 `max_continuations` 退出 1，无终局分数。PATH PASS 不升级成完整 gameplay PASS；两次窗口分别授权，本章无新重试预算。

### 共享 runtime 层：worktree 与 active install 都不是隔离证明

**来源**：H4；[install.py](../../../career_sim_runner/install.py)。

**事实**：S03-09 的 worktree 无 active install 记录，共享 registry 却有两个旧 Skill enabled；预检又因输出/解码错误未完整保存工具列表，五工具状态为 UNKNOWN。门禁未过，install/service/game 均为 0，不能写成 Candidate 运行失败。

排查入口是 [Skill 安装 的共享安装副作用](03-Submission校验与Skill安装.md#检查之后材料怎样进入框架) 与 [C07 的代码/运行隔离边界](../track-c-repository-tooling/07-本地工作区、环境与可重建状态.md)。`active_install.json` 是来源记录，不能单独证明共享 workspace 当前内容；自定义 skills 路径也不隔离 DB、会话和服务。

### 参数合同层：模型选项文本不等于合法 schema

**事实**：[v6 验证](../../project/runs/v6-run1-validation.md) 与 [RUN_HISTORY](../../project/RUN_HISTORY.md) 记录 Energy 的 `choice=6,7,3` 被拒绝且未改变状态：203 次尝试中 202 次成功并有 fresh observe。完整 48 月与运行遵循失败同时成立。

先按 [B03 参数合同](03-Submission校验与Skill安装.md) 和 [请求与回执 回执闭环](05-Runner、Tool调用与状态更新.md#一次选择怎样成为外部动作) 区分请求、拒绝、成功；结果分类见 [负结果分类](../track-d-project-method/06-Forensics、失败实验与负证据.md#给结果分类并保留停止理由)。模型意图或 note 中的 PASS 不能代替接口验证，也不能把该明确拒绝推广成所有超时都无副作用。

### Provider 层：连接失败不能用改策略来解释

**事实**：H5 对 S03-10 失败窗口记录 17 个请求开始、16 个 APIConnectionError、无完成响应，失败在 TLS/HTTP 响应前；具体对端/根因为 UNKNOWN。后来另获授权的两个 provider-only 检查均完成，共 74 tokens，只证明那两个窗口连通。

没有 HTTP 证据就不能改写为鉴权、限流或模型名错误；没有模型完成响应，也不能评价策略。保留失败窗口与后来成功的独立归属，方法见 [D06](../track-d-project-method/06-Forensics、失败实验与负证据.md)。本章不提供私有连接配置或重试授权；缺账单时不把 cost 记为实际零。

### Session / score 层：最新 DB 行不等于目标局

**来源**：[v4 取证](../../project/runs/v4-run1-health-forensic.md)、[v7i 验证](../../project/runs/v7i-run1-replacement-validation.md)、[score.py](../../../career_sim_runner/score.py)。

**FACT｜症状与来源**：v4 退出 0 但 `ending_score={}`；实际共享实例用旧工作区 DB，根 Runner 查询根默认 DB。当时按精确 game ID 只读取证恢复 `25.84 / 18.09` 的 M6 健康失败，既非无结算，也非完整 48 月。

v7i replacement 的报告 game ID 空，独立 fresh game/events/transcript/final observe 却支持 `64.0 / 44.8 / 48m`。核目标来源可区分字段缺陷与真正错局，不能默认“最新 DB 行”正确。生产路径查 [B06](06-日志、Session、Score与证据是怎么产生的.md)，正反对照方法查 [D06](../track-d-project-method/06-Forensics、失败实验与负证据.md)。

**UNKNOWN**：v6 报告覆盖原因；旧 DB 快照缺少 v4 payload 的原因。后者缺失早于退役，hash 不能恢复内容，也不能把它归因用户删除。当前没有 DB 查询。

### 上下文与遵循层：加载一次不证明整个长游戏都记得

**事实**：[v6](../../project/runs/v6-run1-validation.md) 的两次压缩后未重读三 Skill；[v7i](../../project/runs/v7i-run1-replacement-validation.md) 的累计 23 条压缩记录，按本局窗口归属后是两次，之后虽有 fresh observe 却未重读四 Skill。[RUN_HISTORY](../../project/RUN_HISTORY.md) 保留这些限制。

恢复合同查 [A02](../track-a-skill/02-exact-v6-Instruction逐句拆解.md)，时间窗和替代解释查 [D06](../track-d-project-method/06-Forensics、失败实验与负证据.md)。初始 LOADED 与观察更新不覆盖恢复遵循，也不能由此证明分数差异由压缩造成。

### Forensics 层：审计器也需要被审计

**事实**：[S08-09 取证](../../project/reviews/S08-09_RUNTIME_CONTRACT_ADHERENCE_FORENSICS.md) 将误判的 `0/207 valid` 修正为 174 valid、33 checkpoint 枚举错误、0 missing；合法换行触发了旧 parser 的 false negative。另一个独立问题是全部 `R=PASS X=0`，而合同禁止 X=0 提交，Locked MCP 不会替 note 执行该门禁。

解析修复不改变既有行为：207 个成功回执只含 success/error，18 个后置观察缺失；Delivery 生命周期语义仍 INCONCLUSIVE，hold ACTIVE。方法归 [D06](../track-d-project-method/06-Forensics、失败实验与负证据.md)：分别检查 parser 的读取规则与模型的合同执行，不能以其中一个 PASS 覆盖另一个缺陷。

### 取证保留与退役层：删目录之前先断依赖

**事实**：[旧工作区退役](../../project/LOCAL_WORKSPACE_RETIREMENT.md) 的目标是普通目录，并非仍注册 worktree。S11-11 导出 20 个精确 session payload、244,154 bytes，完成引用/hash/敏感信息核对和有效 DB/log 路由调整；自动删除被拒绝后未绕过，S11-12 由用户人工删除。迁移来源仍受 hold，既有 S09/S10 hold 未解除。

目录消失不能推出证据可删；Git 也不会自动恢复 ignored DB/log。生命周期查 [C06](../track-c-repository-tooling/06-artifacts、Raw-Evidence与证据链.md)，退役条件查 [文件生命周期](../track-c-repository-tooling/09-开发工作流与文件生命周期.md#交付之后材料怎样保留或退役)。这里索引历史结果，本轮不复查 DB 或清理。

### 一张定位表

| 看见的症状 | 先定位的层 | 不应直接尝试 |
|---|---|---|
| 裸命令 WinError 2 | 调用进程的 executable/PATH | 重写策略、反复开局 |
| WS 可连却没有工具 | MCP 注册与有效 config | 宣称所有 runtime 通过 |
| enabled 有 Skill，任务却没记录安装 | 共享 workspace 与本地元数据 | 依据旧注册表宣布当前成功 |
| schema rejection | 参数/枚举合同与回执 | 统计为成功游戏动作 |
| provider 无完成响应 | 上游连接及请求窗 | 从失败评分判断策略 |
| score 空或 game ID 不明 | session/DB/output 归属 | 随便取最新 DB 行 |
| final score 好但要求未执行 | runtime adherence | 用成绩覆盖遵循缺陷 |
| 汇总与原事件不一致 | 审计器格式/关联逻辑 | 改写原始证据 |

大量任务是在逐层证明运行链成立。每一步都应说清它证明到哪里；没有证据的部分保留 UNKNOWN，而不是扩大探针、重跑预算或偷偷修改冻结实现。

故障索引回答“卡在何处”，复现路线回答“按什么顺序核对前提”。后面的检查点引用前面的机制，不需要每次从头读完所有事故。

## 沿完整运行链检查复现条件

### 阅读前提：这是一条概念复现路线

Reproduction（复现）是让组件身份、运行链和证据归属再次可比较，不是保证模型逐字输出同一内容或得到同一分数。本章供读完 B01–B08 后逐点核对，不需要先通读 B09；故障时再查该参考页。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 本章没有执行 setup、环境 CLI validate、install、服务启动、MCP、provider、DB 查询或 gameplay。命令只说明历史接口；未来执行必须另有明确 Task 授权、次数/成本预算和停止条件。

命令中的变量是未来任务必须事先确定的真实输入，不是本轮设置值；本文不提供密钥、私有 provider 配置或能绕过现有冻结边界的材料。所有未知现场状态均为 UNKNOWN。

### Step 0｜先明确“要复现什么”

阅读 [OFFICIAL_SOURCE_LOCK](../../project/OFFICIAL_SOURCE_LOCK.md)、[ENVIRONMENT](../../project/ENVIRONMENT.md)、[CURRENT_STATE](../../project/CURRENT_STATE.md) 和未来任务的 run gate（运行门禁），先回答：

1. 复现哪个 Candidate、哪个 source commit，使用哪些 Skill/Instruction？
2. 是本地 Dev（开发环境）观察，还是有另行授权的官方提交？两者合同不同。
3. 谁独占 `career_emu`，哪些 raw evidence（原始证据）仍在 FORENSIC_HOLD？
4. 是否授权环境准备、安装/reload、服务/MCP、provider、一次新局或同局继续？各有多少预算？
5. 哪种技术失败/未知结果必须停止，结束后怎样归档必要证据？

**事实**：当前最终冻结材料的 exact-v6 身份与工作中的 current Candidate 不是自动同一对象。不能因为当前目录方便就用 v8 替代指定 v6，也不能为教学重新构建 frozen ZIP。身份以 canonical（权威）记录和任务指定材料为准。

这一步的产物是一个明确的运行合同和身份清单，不是服务进程。比赛 gameplay 当前已关闭，本教程完成也不重新开放。

### Step 1｜找到正确的 Python 环境

**前提**：使用身份已确认的根环境，参考 [B02](02-从零搭好Python与依赖环境.md)。本仓库静态/离线解释器为 `D:/CS/CareerSim/.venv/Scripts/python.exe`；历史 Python 3.12.13、uv 0.11.16 与冻结依赖以 [ENVIRONMENT](../../project/ENVIRONMENT.md) 为准。

**预期证据**：解释器、依赖/lock、Runner 来源与合同匹配；需要裸 CLI 时，调用进程自身能解析根 Scripts 中的命令。不能只核对嵌套子进程 PATH。

**停止点**：依赖或 Source Lock 漂移返回决策；不为“从零”演示重装、隐式同步或套用 S01 的历史 `--no-install-project`。

### Step 2｜准备身份明确的 solution

**前提**：按 [B03](03-Submission校验与Skill安装.md) 准备指定方案，区别最小可安装 bundle 与正式提交包。`$solution` 是未来合同核验的真实方案根目录，不是教材快照。

**预期证据**：source commit、材料 hash、manifest 与 Skill 集合匹配指定 Candidate。它证明文件身份；进入模型的证据要等后续运行检查，策略含义查 [Track A](../track-a-skill/01-从零理解Agent、Instruction与Skill.md)。

**停止点**：来源不明、材料不全或 Candidate 不符，先返回；不以当前 checkout 替换冻结材料。

### Step 3｜先检查材料，认识完整 validate 的运行前提

**前提**：先复用身份未变的材料校验，核对 layout、manifest、Skill frontmatter；[B03](03-Submission校验与Skill安装.md) 列出各校验器实际负责范围。

**预期证据**：材料 PASS 与环境前提分别记录。完整 CLI `validate` 会涉及实例/环境写入、DB 父目录探针及 WS 连接，应放在 Step 4 获准就绪后，不能视为纯文件检查。

**停止点**：指出失败的具体层；不以一个总 false 混淆材料和服务，也不为搜集报告无限追加门禁。

### Step 4｜配置与启动 JiuwenSwarm / MCP

未来执行先按[第 04 章](04-JiuwenSwarm、AgentServer与MCP分别是什么.md)核对有效 instance config：MCP executable、cwd、DB/log 路由、provider 依赖与共享实例独占窗口。不能把 `setup` 当只显示配置；它可能覆盖修好的绝对 executable 以及有效路径。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 下面是已建立流程的服务启动接口，可能触发 provider 预热。

```powershell
& 'D:/CS/CareerSim/.venv/Scripts/jiuwenswarm-start.exe' --name career_emu all
```

**预期证据**：readiness、有效注册与必要接口；历史五工具记录不能代替未来窗口。若合同允许完整环境 validate，调用进程应能解析裸 `jiuwenswarm-start --list`，再使用下方接口。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 此命令包含环境写入/连接行为，不是纯材料静态校验。

```powershell
& 'D:/CS/CareerSim/.venv/Scripts/python.exe' -m career_sim_runner validate --submission $solution
```

**停止点**：注册/连接不明或 hold 保全失败，按合同停止；文件存在、backend reachable 不能替代全链证明。

### Step 5｜安装并驱动一局

**前提**：[Skill 安装](03-Submission校验与Skill安装.md#检查之后材料怎样进入框架) 的覆盖/清理保全与共享窗口通过。`play --submission` 自带材料校验、install/reload，不要重复独立安装；不带 submission 的 play 则另核 active install 身份和加载配置。worktree 不隔离 runtime。

`$authorizedTimeout` 是未来合同明确的有限秒数；默认 7200 不是预算授权。

> **历史复现说明；当前 S11 未授权执行。Current S11 live operations = NOT AUTHORIZED。** 该命令会安装/reload，并可能调用 provider、MCP、`new_game` 与 `take_action`。

```powershell
& 'D:/CS/CareerSim/.venv/Scripts/python.exe' -m career_sim_runner play --submission $solution --timeout-s $authorizedTimeout
```

它通过已经启动的服务驱动任务，不负责启动该服务。该入口默认创建新 drive，游戏新建由模型之后调用工具完成。记录 actual install、drive ID、game ID、output 目录及开始时间，不以“某文件存在”补出没有发生的操作。

超时/断连/partial/unknown outcome（结果未知）之后不能盲重发：先在既有授权内读取状态或必要日志；仍不能确认就停止留证。手动 `--continue` 不等同于新游戏预算，也不保证恢复同一游戏；同时传 submission 还会重装/清理。是否继续必须来自具体任务授权。

### Step 6｜观察 model/tool loop

看[第 05](05-Runner、Tool调用与状态更新.md)、[第 07 章](07-工程排障与完整运行链复现.md)：

- 初始提示发出后，确认一个新游戏 ID 与合法初始观察。
- 找到本次 Skill 发现/正文加载的证据，不只看注册名称。
- 将行动请求与回执关联，区分成功、拒绝与未知结果。
- 核对该行动后的 fresh observe，以及正确游戏/事件/时间顺序。
- 将自动继续请求、模型任务结束、游戏终局和全局 timeout 分开。
- 发生压缩时，按该 Candidate 的恢复合同审计；开始时加载不能证明之后始终遵循。

这些是对已有观察的判读，不是本章要求进行新探针。Runner 采集到的普通文字不能替代结构化终局；月份、存活、完成身份均应来自正确目标局的状态。

### Step 7｜检查 score 的来源与归属

**预期证据**：同 output 的目标 session 与终局绑定，量化分、partial、月份、终局性质分别记录。生成路径查 [B06](06-日志、Session、Score与证据是怎么产生的.md)；退出 0 不自动证明完整 48 月，本地分不代替 hidden Test。

**停止点**：无分或归属不明先保留原报告/hash，记 UNKNOWN。CLI score 的 latest DB fallback、引擎 observe 与文件覆盖有副作用，不能默认“再 score 一次”；读取哪个来源或调用 DB/引擎必须另有明确授权，不以新局补过去。

### Step 8｜离线 audit 与必要证据归档

**前提**：按 [LIVE_RUN_WORKFLOW](../../project/LIVE_RUN_WORKFLOW.md) 绑定目标 events/transcript/原始 score、真实或明确重建的 runner-result、安全 llm-log 切片、起止时间和时区。

**预期证据**：input hashes、身份、终局、行动/观察、usage、压缩及重读的分层结果。缺日志或账单记 UNKNOWN；不能填“压缩零次”“成本零”。生成机制查 [B06](06-日志、Session、Score与证据是怎么产生的.md)，脚本输入输出查 [C03](../track-c-repository-tooling/03-scripts为什么这么多以及分别做什么.md)。

**停止点**：仅归档显式允许且经过 secret scan 的 run-scoped 材料；不提交共享 DB、凭据、无关累计会话。归属冲突按 [D06](../track-d-project-method/06-Forensics、失败实验与负证据.md) 处理，raw 有依赖则保持 hold。

### Step 9｜停止服务，处理获准清理

**前提**：结束/停止行为也必须在未来 Task 的服务生命周期授权内。本轮未启动服务，也没有 stop。

**预期证据**：实际 graceful stop、manager 状态、目标进程退出及必要端口释放；获准清理还要有精确解析路径、来源与 hold 状态。

**停止点**：不杀全机进程，不以教程完成解除 hold。[S03 退役记录](../../project/LOCAL_WORKSPACE_RETIREMENT.md) 显示目录退役后迁移来源仍保留；具体条件查 [文件生命周期](../track-c-repository-tooling/09-开发工作流与文件生命周期.md#交付之后材料怎样保留或退役)。本章不提供递归删除练习。

### Step 10｜怎样定义“这条运行链复现成功”

| 判断维度 | 最少要说明什么 | 仍不能扩大为 |
|---|---|---|
| Identity correctness（身份正确） | Candidate/source/config/环境与实际安装匹配 | 只看 Git HEAD 就证明 runtime 正确 |
| Runtime connectivity（运行链连通） | 服务/必要 MCP/provider 的窗口内证据 | 一个 WS 可连就全链 PASS |
| Game completion / termination（完成/终止） | 正确 game 的公开终局、月份与结束性质 | 模型说 DONE、退出 0 就满 48 月 |
| Score extraction（评分提取） | 来源与目标 game 一致，原报告/替代证据限制明确 | local score 等于 hidden Test |
| Evidence integrity（证据完整性） | 明确输入、时间窗、bytes/hash、缺失项、敏感信息处理 | hash 替代源文件或自动解除 hold |
| Behavior / adherence（行为/遵循） | Skill 加载、应用、恢复与动作闭环按合同审计 | 标记计数或好成绩就全部语义通过 |

允许某些维度通过、另一些失败或 UNKNOWN。复现报告应该给出这种真实分层结果，而不是一个掩盖故障的总 PASS。

### 最后的读者练习

**教学示例（非历史运行记录）：** 某方案完整 48 月，分数可归属，但压缩后未按合同重读 Skill。你能说“完整对局与评分链已确认，恢复遵循失败”；不能说“系统全通过”，也不能自动再开一局或改冻结 Runner。

至此，Track B 的路线是：知道组件由谁提供，理解材料怎样进入 runtime，跟踪模型请求怎样变成游戏动作，再让评分与证据回到正确身份。策略细节回到 [Track A](../track-a-skill/01-从零理解Agent、Instruction与Skill.md)；工具与资产组织查 [Track C](../track-c-repository-tooling/01-仓库总览与核心工程文件.md)，证据判断查 [Track D](../track-d-project-method/01-为什么这个比赛不能靠反复改Prompt试分.md)。
