# CareerSim｜研发演进、实验与失败复盘

## 研发结论

项目的研发主线从建立官方基线，逐步转向 Skill 的实际参与、长程决策职责、运行遵循和证据归因，再进入替代架构研究与最终冻结。版本增加没有自动形成稳定高分；后期也没有把每条研究路线都并入最终方案。

能确认的进展是：问题更具体、身份更明确、运行与策略结果分开评估、停止决定保留了来源。稳定分布、单个机制的因果贡献和隐藏测试迁移仍未证明。最终候选数值及选择理由由 [04](04-最终方案、候选选择与工程交付.md) 集中维护。

## 1. 研发采用什么判断链

~~~text
Evidence（证据）：实际发生了什么，来源是否可靠？
        ↓
Hypothesis（假设）：哪个机制可能解释问题？
        ↓
Experiment（实验）：在冻结边界内验证什么？
        ↓
Decision（决策）：接受、限制、继续或停止？
        ↓
Implementation（实现）：只落实获得支持且获授权的改动
        ↓
新的运行或静态证据 → 下一轮判断
~~~

这条链要求把“发现问题”与“决定改动”隔开。一个低分可能来自策略、轨迹、执行或技术故障；一个高分也可能伴随违反运行合同的行为。先给问题和证据分类，才能知道下一步应该修工具、修改策略，还是保留未知并停止。

Candidate 是被冻结的行为方案；Run 是它在某条具体轨迹上的一次执行；Experiment 是为回答问题开展的有界验证。单次分数不构成完整决策，相同 Candidate 的两次结果也不自动成为受控试验。完整方法教学见 [Track D](../tutorial/track-d-project-method/00-学习地图.md)。

## 2. 七个主要研发转折

以下按问题组织阶段，不复述几十个 Task。S02、S05 的独立完整 Stage 定义在当前权威来源中未恢复；这里仅描述已确认的具体工作，不填造阶段目标或验收结果。

### 第一阶段：把官方基线真正跑起来

最初问题是“所使用的环境、Runner、模型与工具链能否完成一条真实轨迹”。S01 的最小 no-op 基线提供了真实运行起点，结果为提前终局。它证明了相应运行闭环发生过，没有证明基线策略有效，也不是后续每项改动的因果对照。

这个阶段把依赖版本、数据来源、模型标识和会话身份纳入记录。尤其需要区分官方仓库、模拟器包、赛事数据包与框架包；这些不是名字相近就可以互相替代的对象。后续比较若改变这些身份，也要保留变化语境。[官方来源锁](../project/OFFICIAL_SOURCE_LOCK.md) · [运行历史](../project/RUN_HISTORY.md)

**下一步变化：**有了真实环境与基线后，研究才可以进一步询问自有 Skill 是否进入运行链，而不把“文件写完”作为能力成立的证明。

### 第二阶段：从 Skill 文件到实际运行参与

项目从最小 Skill 闭环进入 Risk 与运行链验证。需要检查的不只是材料合法，还包括安装、发现、读取与实际行为。技能存在、被安装、被加载、被应用和带来收益是不同事实。

这一阶段的工程意义是建立证据链，使后续架构不只是文档设计。当前来源对早期完整 Instruction 身份仍有缺口；不能把后来完整版本的内容倒填到最初配置，也不能把 Risk 文件引入解释为已证明提高生存率。[项目复盘](../project/PROJECT_RETROSPECTIVE.md) · [版本索引的来源缺口](../skill-evolution/00-版本索引.md)

**下一步变化：**能参与运行并没有回答怎样做长程决策，研发问题开始转向职责重叠、目标排序和策略解释。

### 第三阶段：建立事实、规划与风险分工

S04 的策略重定位与后续代表版本显示，项目开始检查“只有 Skill 是否足够”。高低差异明显的历史样本阻止了只依据一次好成绩推广策略；状态整理、策略规划和候选风险逐渐形成独立责任。

代表版本 v3c 保留四 Skill 配置，包括 career-action-trace；v4 收敛为三个 Skill；v5 延续三 Skill 并形成 evidence-driven phase policy；exact-v6 形成可审计控制循环。这里的版本名称描述实现意图，不能直接当作效果结论。[Skill 历史索引](../skill-evolution/00-版本索引.md)

**下一步变化：**架构文本可以通过静态验收，实际长程运行仍可能失败。S06 的完整运行与审计使“设计成立”和“执行正确”之间的差距更明确。

### 第四阶段：长程候选加固与执行持续性

S07 继续研究公开证据边界、长程目标与四 Skill 分工。新增 delivery-progress 将承诺、交付证据和公开确认整理为独立生命周期，但不接管规划或动作权。随后候选围绕约束、反馈、语义、恢复和执行顺序迭代。

一个重要转折是：任务局部决策结束，不等于整局游戏应结束。S07 的收口保留了执行轮次持续性的已知限制；S08 将整局持续执行与回合效率作为独立问题。冻结 Runner 的 continuation 预算不能由候选自行修改，技术停止也不能读成自然淘汰。[架构决策中的 S07/S08 收口](../project/ARCHITECTURE_DECISIONS.md)

**下一步变化：**当运行持续性足以交给策略阶段，研发焦点才转到 Survival / Continuity 约束下的高分候选，而不是无界增加运行协议。

### 第五阶段：候选赛跑转向取证与归因

S09 进行了有限候选评估，同时保留低位自然终局、完整幸存样本与技术失败。v7q 是有明确来源的自然低结果，v7m 是没有终局分数的技术部分样本，v8a 是同一冻结行为身份的两个完整样本。这些证据不能压成一列“好或坏”。

项目也开始联合审查失败下尾、资源轨迹、公开状态与执行行为。早期晋升、资源变化和高分之间有描述性关联，但轨迹、架构和状态互相混杂，没有因此恢复一个可保证收益的策略公式。[实验复盘](../project/EXPERIMENT_RETROSPECTIVE.md)

**下一步变化：**S09 以未取得稳定 75+ 突破收口，增量 prompt-hardening 环结束。下一阶段先重新评估运行上下文与架构价值，不把每个低分自动转成下一条提示规则。

### 第六阶段：替代路线先过部署或可行性门

S10 重新打开 Reviewer、Memory、确定性 helper、controller、策略挖掘与模拟器搜索等假设。研究对象不同，验证门也不同：有的先查权限，有的检查正文是否自动进入上下文，有的仅验证工具层状态，有的做历史回放，有的先检查离线基线能否支撑搜索。

这些研究没有共同证明“扩展架构无效”。它们分别停止在安全部署、自动 anchor 持续性、弱信号或可行性限制。未进入后续阶段的工作没有质量或收益结果，不能补成零收益试验。

**下一步变化：**未出现足以替换已选身份的安全、可部署、已验证增量，项目转向 final selection 与冻结。研究结束留下了明确非结论，而不是把尚未验证的机制都放入包中。

### 第七阶段：冻结方案，整理知识与证据

S10 最终冻结 historical exact-v6；S11 的任务转向仓库减量、证据与报告整理、Skill 历史原件和四条教程。新比赛实验、策略搜索与包重建保持关闭。[当前状态](../project/CURRENT_STATE.md)

这个阶段解决展示和可维护性问题：重复过程材料应由权威结论、教学资料与 Git 历史承接，最终包身份不能被文档编辑重定义。报告收口也不是许可清理 raw；保留与释放仍按独立来源审查处理。

## 4. 八条研究路线：研究了什么，实际停在哪里

### 统一索引

| 路线 | 研究问题 | 实际结果与决定 | 决定不意味着什么 |
|---|---|---|---|
| Reviewer | 冻结正式提交路径能否部署安全的建议型审查者？ | REVIEWER_NOT_SAFELY_DEPLOYABLE；安全门停止，质量阶段未运行 | 不否定独立审查价值，也没有测得其建议质量 |
| Memory | 指定 MEMORY.md 是否自动、持续地进入模型上下文？ | MEMORY_NOT_DEPLOYABLE；自动 anchor 缺正文，显式读取可用 | 不证明所有记忆机制无效，也没有模型收益结果 |
| Deterministic Helper | 有界公开状态能否在隔离工具轨道读写并保持？ | DETERMINISTIC_HELPER_CHALLENGER_SUPPORTED；仅工具层支持 | 没有正式 Candidate 部署、模型遵循或云端可移植性证据 |
| Replay Controller | 历史决策窗口能否被 controller 有意义修正？ | CONTROLLER_LOGIC_SIGNAL_WEAK / NOT_PROMISING | 不证明所有控制器无效，未产生实际部署收益 |
| Strategy Mining | 历史 review 窗口能否支持安全策略增量？ | STRATEGY_SIGNAL_WEAK；没有采纳改动 | 关联不等于因果；没有无污染的前瞻检验 |
| Simulator Policy Search | public-input harness 是否足以比较宏策略？ | SIMULATOR_POLICY_SEARCH_NOT_FEASIBLE；基线可行性门失败 | 宏策略未比较，不能说已证明宏策略不好 |
| Team/Swarm | 多角色是否值得引入正式方案？ | DEFERRED / NOT_TESTED | 不是做过实验后证明劣于单 Agent |
| Human Play Lab | 人类操作能否提供独立研究与假设来源？ | CLOSED_BY_USER；关闭原因 UNKNOWN | 不解释成策略失败，也不是正式 Agent 对照 |

### Reviewer：权限先于建议质量

被测冻结 mode=agent 路径中，构造某类 verification agent 的工厂存在，不等于它在实际 adapter 中已注册。通用 child 的继承材料、工具与共享 MCP 路径，也未建立“只给建议、绝不能改变游戏”的机械边界。

五项无副作用静态检查支持了这一部署判断，但没有真实 child dispatch 或盲评质量结果。项目因此在 Phase A 停止，Phase B/C 没有运行。合理结论是测试路径不满足当前安全部署要求；对另一条获得明确只读权限的路径，当前研究没有答案。[Reviewer 可行性来源](../project/research/S10-19R1_SUBAGENT_FEASIBILITY.md)

### Memory：文件可读不等于自动可见

Memory 研究检查的是指定自动 MEMORY.md anchor。启动、更新和模拟压缩后的系统 captures 没有正文标记；显式 read 可以返回内容。存储存在和读取成功，仍没有满足自动持续系统内容这一前提。

上述 captures 来自离线隔离 prompt harness，压缩为模拟，没有真实 Provider 请求。因此它们不能被描述成已经测量模型的记忆质量或 gameplay 行为。

没有通过持久性门，就没有继续做配对模型审查或序列收益评估。研究也没有把另一个隔离语义不同的记忆路径静默替换为“问题已解决”。这使结论保持在被测自动 anchor 范围，而不扩大为对记忆思路的否定。[Memory 可行性来源](../project/research/S10-19R2_MEMORY_FEASIBILITY.md)

### Helper 与 Controller：局部能力不能直接升级部署

确定性 helper 在隔离工具轨道支持 JSON 输出、状态跨调用及模拟压缩保留、install/reset 清除等事实。这为一个 challenger 提供工具层支持，却未证明模型会调用它、相信它或按其结果行动，也未确认云端解释器与权限。[工具层审计](../project/research/S10-19R3_NATIVE_CONTROL_SURFACE_AUDIT.md)

Controller 的历史回放包含 12 个 development 窗口与 12 个 holdout 窗口。记录有一个仅状态层修正，仍有八个 UNKNOWN，主要已知决策错误未被证明修正。项目跳过模型与工具 probe，没有把“合理替代选项”记成实际提高结果的策略。[Controller 研究](../project/research/S10-20_PROMOTION_WINDOW_CONTROLLER.md)

### Strategy Mining 与 Simulator：信号弱和做不了比较是两种结果

策略挖掘分析了 13 次运行、82 个完成窗口和 28 组事实预匹配样本。暴露、任期、状态、架构与异步结果归属仍互相混杂；这些计数说明分析范围，不代表足够统计把握度。没有安全策略增量时，决定是保留弱信号。[策略挖掘](../project/research/S10-21_REVIEW_WINDOW_STRATEGY_MINING.md)

模拟器路线定义了 12 个宏配置，但实际只评估冻结 Story baseline，16 个 episode 仅两个完成。宏筛选、确认和规划中的 holdout 没有运行。因此结论是用于本次搜索的可行性门失败；哪个宏策略更好仍未知。[Simulator Policy Search](../project/research/S10-22_SIMULATOR_POLICY_SEARCH.md)

### Team/Swarm 与 HPL：没有比较就不写优劣

Team/Swarm 的延后是架构与治理状态，不是实验结果。HPL 则是独立的人工游玩研究路线：人工选择通过不同 execution path 使用模拟器，不是把正式 Agent 模型替换成人类。

HPL 后来由用户关闭，当前权威来源没有记录具体关闭原因。其实现和证据边界已在 [Track C](../tutorial/track-c-repository-tooling/00-学习地图.md) 解释；这里仅记录研究组合中的位置，不将它归入正式候选成绩。

## 5. 五个代表取证案例

Forensics（取证分析）用于重建结果与运行链之间的联系。它的价值在于排除错误归因、说明哪里能判断和哪里仍未知，不在于为每个不理想结果找到确定原因。

| 案例 | 表面现象 | 查证与接受的发现 | 结论边界 |
|---|---|---|---|
| 过期分数与 Provider 失败 | v7i 路径出现失败，同时输出中有分数 | 首次 fresh observation 前 Provider 连接失败；分数来自更早 v7g session，被排除 | 不能当作有分数的 v7i 局，也不能据此判断策略优劣 |
| v7m 技术部分样本 | 运行停在 M20，没有终局 | 最后新鲜状态仍存活，84/84 次动作成功；Runner 技术失败，归类证据不足 | 可以保留局中事实，不能补造终局分数或确定传输根因 |
| 上下文压缩与恢复 | 最终方案完成，但恢复是否执行不清 | v6 出现压缩后未按合同重读 Skill 的发现 | 恢复规则存在不等于遵循；缺陷不转移成其它版本事实 |
| CTRL/action 配对 | transcript 中有很多控制标记 | 自由文本缺可靠 model-turn ID，无法认证准确动作配对 | 标记计数不等于唯一决策数或完整覆盖率 |
| HiddenRisk 证据防火墙 | raw payload 或分析中出现内部形态数值 | 项目规定策略只使用参赛者可见公开信息；内部/隐藏字段不因出现在工具返回中而自动可部署 | 可用于说明审计问题，不能编入事件答案或隐藏门槛策略 |

前两个案例见 [最终证据审阅](../project/FINAL_EVIDENCE_REVIEW.md)、[v7i 记录](../project/runs/v7i-run1-validation.md) 与 [v7m 记录](../project/runs/v7m-run1-validation.md)；v6 执行细节集中在 [04](04-最终方案、候选选择与工程交付.md)。公开证据边界由 [架构决策](../project/ARCHITECTURE_DECISIONS.md) 与 [实验复盘](../project/EXPERIMENT_RETROSPECTIVE.md) 支持。

这些案例改变了下一步问题。旧会话分数需要修正来源；未到终局的技术样本需要保留局中边界；恢复缺陷需要检查执行合同；标记歧义需要改善审计表面；隐藏字段需要隔离。它们都不能仅凭最终得分高低来判断。

## 6. 为什么负结果不能统称失败

| 用词 | 所描述的事实 | 应避免的改写 |
|---|---|---|
| unsupported | 当前证据没有支持所提收益或机制 | “已经证明永远无效” |
| inconclusive | 证据不足以区分竞争解释 | “没找到原因，所以策略失败” |
| technical failure | 工具、Provider 或运行链使执行中断 | “候选获得了零分” |
| weak signal | 分析存在有限现象，但不足支撑改动 | “有几个案例，所以可以部署” |
| feasibility failure | 前置能力或基线未通过，目标实验未进入 | “目标宏策略已经比较过” |
| not tested | 对应实验没有完成 | “尝试过且比现方案差” |

这些标签决定信息可以怎样被使用。Provider 失败不能直接否定政策；自然低位终局也不能直接锁定某个 Skill 为根因；工具层可行不能证明模型层收益；未测试的 Team 不能作为支持 Single Agent 的性能证据。

负结果保留后，后续研究者知道哪些假设真正受测、哪些步骤尚未发生。如果只保存完成或高分样本，就会把研究组合误读成一串持续进步的胜利；如果把所有停止都写成“无效”，又会阻断本来可以在新权限或新方法下重开的问题。

## 7. 何时选择停止

项目后期不继续无限加条款，是已有研究决策支持的收敛。增量 hardening 没有形成稳定突破；Reviewer 和自动 Memory 停在部署门；controller 与策略挖掘信号弱；模拟器未进入宏比较。新增复杂度需要可观察问题、部署证据和有限验证，不能仅凭设想进入成品。

**事实：**这些路线没有成为最终冻结包的一部分；S10 的策略搜索随后关闭。**解释：**在当时证据下，固定一个可以清楚绑定来源的成熟方案，比继续混入未经验证的机制更便于复核。这是工程选择，不是统计最优证明。

停止也保留未知。未来如果有新的安全部署边界、重复样本或可比较环境，可以重新设计实验；当前报告没有执行这些工作，更不能用将来可能的改进解释为已经获得收益。[最终方案审阅](../project/FINAL_SOLUTION_REVIEW.md)

## 8. 可保留的研发经验

- 将静态材料、实际加载、行为遵循、终局结果与因果收益分层判断，避免把早期 PASS 一路传递到最终性能。
- 用当前局公开事实支持策略；事后分析可以提出假设，不能直接变成运行答案表。
- 将技术部分样本、低分自然终局与完整高分样本同时保留，减少只选好结果展示的偏差。
- 为每条研究路线写清前置门与停止点；没有进入的阶段保持未测，缺失值不填零。
- 冻结是来源与范围决定；选择成熟候选不抹去已知遵循缺陷。

这些是项目证据支持的工程经验，不宣称所有 Agent 工程都必须采用相同结构。完整实验方法、研发史与迁移讨论见 [Track D](../tutorial/track-d-project-method/00-学习地图.md)。
